- The manager skill documented one call for appending a maintainer's verification to a pull request
  body and nothing that would notice when it did not land. `gh pr edit --body-file` resolves the pull
  request through a GraphQL query that also asks for `projectCards`, a Projects (classic) field
  GitHub now refuses: the call exits non-zero naming a field the caller never asked for, and the body
  is left unchanged. The command is loud and the *edit* is silent, so it reads as deprecation noise
  rather than as an unwritten body — and an unrecorded verification is indistinguishable from one
  nobody performed. Worse in the case the skill sends you there for: `gh-pr-create` refuses a body
  with no `Closes #N` at the earliest point anything can see it, and the documented repair then
  no-ops, so the pull request merges with the issue still open and the board reading clean. The
  section now confirms the append by re-reading the published body with `gh-pr:<N>:full` rather than
  by the command's exit — `:full` because a plain read truncates a long body and an appended section
  sits at the end, so the cheaper read is the one that cannot see what it was called to confirm.
  Two facts were measured rather than assumed, because the issue filed them as unknown and they
  decide the fix: the field is refused for **every** repository, so this does not depend on classic
  project cards existing anywhere, and it is a `gh` version accident already fixed upstream
  (cli/cli#13069), so the first move is `gh --version` and an upgrade. The REST route
  `gh api -X PATCH .../pulls/<N> -F body=@FILE` is named as a fallback with a reason and an expiry,
  deliberately not as the mechanism: pinning a lower-level call as doctrine would outlive the defect
  it routes around (#195).
