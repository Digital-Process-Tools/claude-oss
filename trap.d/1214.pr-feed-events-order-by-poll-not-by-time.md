Channel events order by when a poller noticed, not by when the thing happened,
and two watchers on the same object disagree routinely.

Observed 2026-09-06/07, three times in one evening on this repo:

  #1205  checks_failed     23:14:57   (github-pr)
         pr_opened         23:15:39   (github-pr-feed)
  #1207  checks_succeeded  00:41:10   (github-pr)
         pr_opened         00:41:25   (github-pr-feed)
  #1209  checks_succeeded  00:50:43   (github-pr)
         pr_opened         00:51:31   (github-pr-feed)

In every case the per-PR watcher reported CI results for a pull request the
feed watcher had not yet announced as open. Reading the stream naively, a
pull request reports its checks before it exists.

Nothing is wrong: `github-pr-feed` polls the open-PR list on its own clock and
`github-pr` polls one object on another, and the `ts` attribute is the poller's
observation time, not the forge's event time. But a consumer that treats the
stream as ordered will build a wrong causal story out of it, and the events look
perfectly ordered most of the time, which is what makes it a trap rather than an
obvious quirk.

Practical form: never infer "X happened before Y" from two events with different
`watcher_source` values. Within one `watcher_source` and one `id` the order does
hold, and consecutive events for that pair supersede each other, which is what
the channel docs already say. Across sources it does not.

Cost here was small -- a few seconds of confusion each time, and one paragraph
written to explain it to a maintainer. Logged because the same shape would be
expensive if the causal story mattered, e.g. deciding whether a red leg preceded
or followed a push.
