Gate-3 release audit (round 2, v0.37.1..HEAD) found: scripts/worktree_reap.py's dirt_state (lines 359-398) uses git status --porcelain --untracked-files=all, which never lists gitignored paths at all -- so nothing gitignored can ever be found dirty and reach offenders, even though the module's own docstring (lines 29-32) states the artifact allowlist (notes/, reports/, .oss-review-snapshot.json, all added to .gitignore by #1628 step 1) is checked against 'anything else found dirty', implying gitignored paths are seen and allowlisted rather than invisible.

Observed: reports/ exists in this working tree, git check-ignore -v confirms .gitignore:74 covers it, and git status --porcelain --untracked-files=all does not list it at all -- so the three allowlisted paths, and everything else .gitignore covers, are simply never examined by dirt_state.

Consequence: git worktree remove --force on a tree whose only 'dirt' is gitignored content removes files with no copy in git, without the removal ever being weighed against the allowlist the docstring describes. Ranked misreports rather than destroys because git itself (not this code's --force) is what makes an ignored-only tree look clean, and the fix is a read seam (git status --ignored) rather than the destructive call itself -- but note this composes with a second finding from the same round (lsof non-zero exit misread as 'unoccupied'): together, gitignored scratch in an occupied lane's worktree could be removed. If read as destroys once combined, this pair blocks a release; recorded here as the maintainer's call to make on re-read.

Fix shape: have dirt_state also read git status --ignored (or --ignored=matching) and decide the allowlisted paths against that, rather than relying on plain --porcelain to surface them.
