`release_ci_wait.py`'s `--require-event` filter (added fixing #1324, PR #1335) verifies a CI run's
*trigger event* (`workflow_dispatch` vs `push`) but has no route to verify the run's own *input
values* -- whether a `workflow_dispatch` run actually carried `full_matrix: true` rather than being
left at its `false` default.

Found and argued through by the developer lane that fixed #1324 itself, not by a separate audit.
Confirmed live: `gh run list --json`, `gh run view --json` and the GraphQL `WorkflowRun` type all
expose no `workflow_dispatch` input values after the fact (checked via `gh run list --help`,
`gh run view --help` and a `gh api graphql` introspection query on `WorkflowRun`).

Consequence: a stray or earlier manual `gh workflow run tests.yml -f full_matrix=false` against the
exact release-commit sha would still satisfy the `--require-event workflow_dispatch` filter and let
a release proceed verified only by the reduced matrix -- the same failure mode #1324 was filed to
close, one layer deeper. Not exploitable by an outside attacker (requires push access to trigger a
workflow_dispatch on this repo), and unlikely in the ordinary release sequence (nothing else
dispatches workflow_dispatch against that exact sha before the release step's own dispatch), so it
is reported here rather than filed as a blocking finding.

Two candidate fixes, neither picked: (a) cross-check job count via `gh run view --json jobs` against
a per-repo-read expected count, without hardcoding a repo-specific job count into shared code, per
this repo's own governing rule against baking per-repo facts into shared scripts; (b) capture the
dispatched run's own id at dispatch time in `commands/release.md` and wait on that id directly,
rather than filtering the run list by event after the fact. (b) looks like the cleaner fix on first
read -- it needs no cross-repo job-count lookup at all -- but neither has been weighed against the
other in detail.
