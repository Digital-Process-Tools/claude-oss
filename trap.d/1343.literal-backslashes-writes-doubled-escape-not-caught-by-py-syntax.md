# literal_backslashes writes a doubled escape verbatim, and py-syntax cannot catch it

While fixing #1343/#1344, hit the same mistake twice with supertool edit/paste
and literal_backslashes: writing a doubled backslash-n sequence in a TOML
payload field when a single Python-source \n escape was intended.
literal_backslashes writes exactly what is in the payload with no escape
interpretation, so the doubled sequence lands on disk as two literal backslash
characters plus n -- which is syntactically VALID Python (a string containing
two backslashes and an n), just means something different than the intended
single-escape newline. py-syntax validation passes because the file still
parses; nothing catches that the string's runtime VALUE is wrong until the
test that consumes it fails with a confusing mismatch (e.g. an Args: line
built from that string does not match the real single-newline-separated
`claude mcp get` output shape, and the test failure reads like a logic bug
rather than an escaping bug).

Hit in: tests/test_doctor_mcp_channel_registration_621.py's new run() fake
(a text = "Type: stdio\nCommand: bun..."-shaped string), and initially in
tests/test_doctor_arm_target_verify_1344.py's own paste (caught only because
the paste tool refused the SAME doubled-run pattern on a later, unrelated
write attempt for the note file, naming the exact lines and finally making
the pattern legible).

Confirmed by reading the file back with a supertool grep for the double-run
literal pattern after each incident. The tool's own error message (when it
does refuse) is unambiguous and names both possible fixes -- the trap is
specifically that it does NOT refuse when the doubled sequence lands inside
old/new/content of a .py file whose destination is a Python STRING LITERAL
rather than shell/prose content, because the payload itself round-trips as
valid syntax either way. Worth a rule (not decided here) something like:
when writing Python source containing a backslash-n or backslash-t style
escape meant to be interpreted at Python runtime, default to a SINGLE
backslash in the TOML payload (no literal_backslashes for that field) and
only reach for literal_backslashes when the destination is shell, a Windows
path, or prose documenting the literal sequence itself.
