Found by lane fix/1399's own self-review (oss:auditor, round 1), while fixing #1401's `_malformed_repo` gap in `statusline.py`/`doctor.py`.

`scripts/oss_config.py`'s canonical `REPO_RE`/`repo_problem` -- the pattern both fixed `_malformed_repo` copies are pinned against by `tests/test_statusline_watch_name_refusal_653.py` -- still admits `?` and `#` in a repo slug. Confirmed live on this tree: `oss_config.repo_problem("o/n?x")` returns `None` (i.e. "not a problem").

`scripts/cohort_freeze.py`'s own `_resolve_repo_slug` validates `.oss.json`'s `repo` field through `repo_problem` alone -- no analogous `?`/`#` guard -- before building several unescaped `gh api repos/{repo}/...` paths (tag refs, tags, commits, issues, labels) used during release tagging. Same bug class #1401 just closed in statusline.py/doctor.py, left open in this third file.

The auditor flagged a real ranking tension rather than calling this a clean non-blocking case: the loop's own "value comes from the maintainer's own config on the maintainer's own machine" reasoning (which would rank this non-blocking, like #1401) sits against `_resolve_repo_slug`'s own docstring, which calls this exact value contributor-editable and "as untrusted as a --repo argument" (#954) -- an argument for treating it as more severe. Recording this tension rather than deciding it: whoever picks this up should read `_resolve_repo_slug`'s docstring and #954 before ranking it, since the two framings disagree about how trusted `.oss.json`'s `repo` field actually is at release-tag time.

Not filed as a fresh issue: it fits the same non-blocking "splices" row #1401 was already ranked under, in a different subsystem (release tagging vs. statusline/doctor), not a new/unranked class.
