agents/tick-merge.md step 1 documents the merge call as
`gh-pr-merge:N:squash|force|cleanup`, and says nothing about what `|cleanup` does when another
open pull request is based on the branch it deletes. Hit for real in this same session, while
merging PR #1568 (`fix/1567` -> `main`) with #1569 stacked on `fix/1567`: GitHub does not retarget a
stacked pull request when its base branch is deleted, it closes it, into a state where `gh pr
reopen` refuses because the base is gone and `gh pr edit --base main` refuses because the pull
request is closed. The documented recovery is five steps through `refs/pull/N/head`.

What made it survivable here was not the prose. `gh-pr-merge` itself now detects the case: merging
#1568 without `|cleanup`, its output said "an open pull request has been found based on this
branch ... Deleting the remote branch closes that pull request and there is no clean way back" and
added "`|cleanup` refuses the remote branch item on the same ground." So the tool guards it, and an
`oss:tick-merge` spawn passing `|cleanup` on a stacked branch gets a refused cleanup item rather
than a closed sibling pull request. The file's own report shape already carries
`cleaned / skipped: reason / forced with reason`, so the refusal has somewhere honest to land.

The gap is therefore prose rather than behaviour, which is why this is a fragment and not an issue.
Two things worth deciding when somebody curates it:

- Whether `agents/tick-merge.md` should name the hazard at all, given that the spawn is autonomous
  and a maintainer reading that file is reading the loop's own account of what merging does. The
  argument against adding it: the tool refuses on its own, the file is budgeted, and a rule that
  restates a guard the tool already enforces is the kind of prose this repository keeps saying to
  cut.
- Whether the file should say that a refused cleanup item is NOT a failed merge. `gh-pr-merge`'s
  own output says so ("a refused cleanup is not a failed merge and does not move the exit code"),
  but a spawn reading its own exit code and not that sentence could report `could-not-merge` for a
  merge that landed. Nothing observed doing that; it is the shape of the mistake, not an instance.

The existing jit rule `stacked-pr-cleanup-recovery.md` carries the full recovery order and fired
correctly during the session. Its own closing note is the part that mattered most: the
`## Stacked follow-up` section prints AFTER the merge and cleanup have both run, so it reads as an
advisory about what to watch next rather than a warning about what the call just closed.
