# `gh-pr-merge:N:...|cleanup` closes any pull request stacked on the branch it deletes

Observed 2026-09-03 merging #959 (`fix/958` -> `main`) with `squash|force|cleanup` while #961
(`fix/960` -> `fix/958`) was open.

**What happened.** The merge succeeded. Cleanup deleted `fix/958` on the remote. GitHub did not
retarget the stacked pull request to the deleted branch's base -- it **closed** #961 outright.
`gh-pr:961:status` then read `state: CLOSED | mergeable: CONFLICTING`.

**Both obvious remedies refuse, and they refuse in a cycle.**

    gh pr edit 961 --base main
      GraphQL: Cannot change the base branch of a closed pull request. (updatePullRequest)
    gh pr reopen 961
      GraphQL: Could not open the pull request. (reopenPullRequest)

Reopening needs the base branch to exist; retargeting needs the pull request to be open. Neither is
reachable from the state cleanup leaves.

**What works, in this order:**

1. `git fetch origin refs/pull/<merged-pr>/head:recoverN` then
   `git push origin recoverN:refs/heads/<deleted-branch>` -- the merge op's own cleanup line already
   says the deleted branch is recoverable from `refs/pull/N/head`, which is what makes this cheap.
2. `gh pr reopen <stacked-pr>` -- now that its base exists again.
3. `gh pr edit <stacked-pr> --base main`.
4. Delete the restored branch again; harmless now that the base has moved.
5. Rebase the stacked branch off the squash: `git rebase --onto main <old-base-head> <branch>`,
   because the parent commits are in `main` only as one squashed commit and are not ancestors of it.

**The reporting order is the trap, and it is worth naming precisely.** `gh-pr-merge` *does* detect
this -- its output carries a `## Stacked follow-up` section naming #961 and saying it "needs a
poller". But that section is printed **after** the merge and cleanup have both run, so it reads as
an advisory about what to watch next rather than as a warning about what the same call just closed.
A caller who reads the whole output still learns about the stacked pull request one step too late.
Whether the right fix is refusing `cleanup` when an open pull request targets the branch, or naming
the consequence in the section it already prints, is a judgement for whoever curates this -- both
are changes to a dependency (supertool), not to this repository.

**Second, smaller trap in the same recovery.** The first `git rebase --onto main` conflicted on all
three shared files, with the `HEAD` side showing *pre-merge* byte counts. Cause: local `main` was
still at the pre-merge commit, never fetched after the merge landed on the remote. A conflict whose
`HEAD` side shows values you know were replaced is the tell -- `git fetch && git reset --hard
origin/main` before rebasing onto it, rather than reading the conflict as a real disagreement
between the two changes. Cost: one aborted rebase and about five minutes of reading a diff that was
not the diff.
