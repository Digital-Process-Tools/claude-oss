The `github-pr` watcher's `checks_failed` event fired four times on PR #1654 between
2026-09-17T21:42Z and 22:43Z, and each time the underlying check state had zero failing legs.

Read directly with `./supertool 'gh-pr:1654:status'` at 22:26Z:

    #1654 | state: OPEN | mergeable: MERGEABLE | conflicts: no
    checks: 10 total: 9 passed, 0 failed, 0 pending, 1 cancelled - NOT ALL GREEN
      cancelled: pytest (windows-latest, 3.12) (job #105401634166)

So the event name says "failed" and the board says "cancelled". A cancelled leg is a third state:
it is not green, but it is also not a leg that ran and found a defect -- a cancellation is usually
a superseded run or an infrastructure stop, and the diagnosis and the remedy are different in each
case. Collapsing the two into one event key means a scheduler or a reviewer reading the event
alone cannot tell "CI found a bug" from "CI never finished", which is this repository's own named
defect class applied to its own notification path.

Cost: one scheduler board read (`gh-pr:1654:status` plus `git-worktrees`) to establish that the
lane was progressing normally and that nothing had actually failed, after four consecutive events
that each read as a failure. Cheap once; the events repeat every ~20 minutes for as long as the
pull request stays in that state.

Not confirmed from here: whether the watcher has a separate key for a cancelled or superseded run
and chose this one, or whether it has only a binary green/not-green split and `checks_failed` is
its whole vocabulary for the not-green side. That distinction decides whether the fix is a new
event key or a renamed existing one, and it was not read -- the watcher's own source was not
opened.
