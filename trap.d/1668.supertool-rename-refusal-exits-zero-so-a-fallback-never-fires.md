`supertool 'rename:OLD:NEW'` refused a call and exited 0 while doing it.

Observed directly, 2026-09-18, renaming a trap fragment:

    $ ./supertool 'rename:trap.d/1662.<slug>.md:trap.d/1649.<slug>.md' || git mv OLD NEW && echo renamed
    --- rename:trap.d/1662.<slug>.md:trap.d/1649.<slug>.md ---
    rename: missing file path
    renamed

The op did nothing -- the file was still at its old name afterwards, confirmed with `ls` -- but
because it exited 0, the `||` fallback never ran and the `&&  echo renamed` did. The session was
told "renamed" by its own command line, and a following `git-status` showed a clean tree, which
reads as "the rename landed and was already committed" rather than "no rename ever happened".
Two readings of the same evidence, and the wrong one is the one that looks like success.

The argument shape was mine: `rename:` evidently wants a different separator or a payload route
than two colon-separated paths, and `missing file path` is the op saying so. That part is a
user error and not the finding. The finding is that a refusal exits 0, which makes it
indistinguishable, to any `||`, `&&`, `set -e` or CI step, from a rename that succeeded.

This is the defect class this repository is named after, in its own tooling: the absence produced
by the tool (no rename) rendering as the same exit status as the thing having been done. Every
other supertool op measured in this session gets this right and loudly -- `git-worktrees` exits
1/2/3 to distinguish occupied from cannot-tell from holding-work and explains in its own footer
that the integer is an answer rather than a failure, and a batch exits 1 when any op refuses.
`rename` is the outlier.

Not established: whether every `rename` refusal exits 0 or only this argument-shape one, and
whether the op has a correct invocation that would have worked (`help:rename` was not run). Either
way the exit code is the defect, not the message -- the message was perfectly clear and was simply
not what the shell was reading.

Cost: one false "renamed", one misread clean `git-status`, and a second pass to notice the file had
not moved. Caught only because the follow-up `git-commit` failed on a pathspec that did not exist.
