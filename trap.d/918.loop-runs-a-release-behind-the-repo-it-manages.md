# The loop managing this repo was running 0.19.0 while the repo was 0.20.0

Measured 2026-09-03, mid-session, after wondering why a fix would take effect.

    cat /Users/.../plugins/cache/dpt-plugins/oss/0.19.0/.claude-plugin/plugin.json  ->  "version": "0.19.0"
    cat .claude-plugin/plugin.json                                                  ->  "version": "0.20.0"

`v0.20.0` was tagged and released earlier the same day. The installed plugin every tick in this
session actually executed was the release before it.

## What that changes about a self-fix

`${CLAUDE_PLUGIN_ROOT}` resolves to the plugin cache, not to the checkout. So the split is:

| read from the project directory, effective immediately | read from the plugin install, effective after a release *and* an update |
| --- | --- |
| `CLAUDE.md` | `agents/*.md` |
| `trap.d/`, `.claude/jit-context/` | `skills/manager/**` |
| `.oss.json` | `scripts/*.py` |
| the repo's own `tests/` | `commands/*.md` |

Every sub-manager this session ran against 0.19.0's `agents/sub-manager.md` and 0.19.0's
`skills/manager/phases/dispatch.md`. The tick whose companion-search failure produced #918 was
executing prose one release older than the file that was read while diagnosing it -- and the
diagnosis was still correct, because that paragraph had not changed between the two, but nothing
checked that. It was luck, not method.

The consequence for #918's fix: `did-not-search`, the `adjacent` refusal, and the three prose
corrections reach no tick until 0.21.0 ships and the plugin updates. `grep -c did-not-search` against
the installed `scripts/dispatch_rank.py` returns 0, and will keep returning 0 after the pull request
merges.

## The check built for this cannot see it

`commands/tick.md` step 1 compares this tick's plugin identity against **the previous tick's**
(#477, #677) and answers `unchanged` / `changed` / `could-not-tell` / `route-mismatch`. A plugin
sitting a whole release behind the repository it manages is genuinely *unchanged* from tick to tick,
so it reports `unchanged` every time, forever, correctly, while being stale the entire time.

The check answers "did this move since last tick?" and nothing anywhere answers "is this the version
of the repo I am standing in?" That is this repository's own defect class landing on its currency
check: two different questions, one rendering, and the one that gets asked is the one that cannot
detect the condition.

#677 is instructive here and is *not* the same bug. It found that asking the version-pinned path for
its own version can only ever answer with the version it was pinned to, and fixed it by resolving the
recorded install instead. That made the reading honest. It did not add a comparison against the
managed repository, because that was not the question it was asking.

## Not decided here

Whether the fix is a fourth answer in the identity check (`behind-repo`), or a separate `/oss:doctor`
line, or nothing at all on the grounds that a maintainer dogfooding their own plugin *should* run the
released version and the latency is the point. That last argument is real and this fragment does not
dismiss it: the alternative is a loop that runs unreleased prose, which is worse. But a latency
nobody can observe is a different thing from a latency that was chosen, and today nothing reports it.
