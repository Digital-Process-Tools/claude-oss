While writing new prose paragraphs into `agents/tick-dispatch.md` and `CLAUDE.md` for #1750,
I twice wrote a backtick-quoted filename that my own line-wrapping split across two physical
source lines, e.g.:

```
`issue-design-question-not-
dispatchable.md`
```

CommonMark converts a line ending inside a code span into a single space, so this renders as
`issue-design-question-not- dispatchable.md` -- a filename with an inserted space in the middle,
silently wrong wherever it is rendered (GitHub, a doc viewer, anywhere that treats this as
Markdown). It is easy to introduce by accident: writing prose at a comfortable column width and
letting a backtick-quoted path or filename wrap along with the surrounding sentence, exactly the
way ordinary words wrap.

Caught both times only by re-reading my own diff carefully before committing, not by any
validator -- `ruff`, `markdownlint` and `gitleaks` (all run automatically on every supertool
`edit`/`paste`) do not flag this, since the file is syntactically valid Markdown either way; only
the *rendered* meaning is wrong.

What would have caught it faster: after writing a paragraph containing a backtick-quoted
path/filename, grep the file for that path with the literal characters that would appear if
wrapped (a hyphen or word-boundary near the wrap point) -- or just keep every backtick-quoted
path/filename reference on one physical source line, never letting the paragraph's own wrap point
land inside a code span, the same way this repository's own `.gitattributes` keeps line endings
themselves out of the content question.

Not confirmed whether any *existing* prose in this repository already has this defect from an
earlier session's own line-wrapping -- I did not sweep for it, since that is a larger, separate
search than this trap covers.
