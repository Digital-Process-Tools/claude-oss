A test that hangs inside its own body under `pytest -n auto` renders, in the CI log, exactly like a
suite that finished and then failed to exit. Four issues (#1658, #1660, #1671, #1673) read the same
`pytest (windows-latest, 3.12)` cancellation that way across fourteen consecutive runs on one
branch, and built two watchdogs (#1660's post-session stack dump, #1672's controller-side one) and
a per-step timing script (#1674) that all measured the wrong thing, because nothing in the log said
which test was running.

What it looked like: progress reached `[ 99%]` and no `[100%]` line ever printed; the two workers
that had finished dumped idle execnet stacks every 15 seconds from #1660's diagnostic, which read
as "the process is alive after the session ended"; the final `N passed in 1770s` line was printed
by pytest's own KeyboardInterrupt handler at the job cap, so it looked like a completed suite; the
stuck tests never reported, so `--durations` showed nothing slower than 16 seconds; and the summed
per-test time matched a green run to within a few percent. Every one of those is consistent with
a post-session hang, and every one is also consistent with one worker blocked inside a test.

What settled it in one run: `-o faulthandler_timeout=180` on the pytest line. pytest's built-in
faulthandler plugin dumps the stack of any test still running after that many seconds, with the
test's own file and line in the traceback -- `<frozen os>:1066 fdopen` from `plugin_update.main()`
line 1074, called from `test_plugin_update_debounce_753.py:240` and
`test_doctor_launcher_caller_1154.py:139`. The flag is now permanent in `.github/workflows/tests.yml`.

The cause underneath: `main()` probed `os.fdopen(3, "w")` on every caller to discover whether the
launcher had opened a progress channel, letting `OSError` mean "no". Under an execnet worker on
Windows, slot 3 is one of execnet's own live descriptors, and `fdopen` on it blocks forever. A
descriptor the process did not open cannot be told apart from one the caller opened on purpose, so
the channel became opt-in (`--progress-fd 3`). The general rule: never probe a low-numbered
descriptor to learn whether a caller set something up; have the caller say so.

Two reads that would have shortened this by days: a `[ 99%]` line with no `[100%]` after it means
the suite did not finish, whatever the summary line says; and `--durations` only lists tests that
reported, so a hang is invisible there by construction.
