Reading one CI leg's `--durations` block and concluding a suite's performance profile is the same
mistake as a green run on one platform. Measured 2026-09-06 on run 34049161080:

- `pytest (ubuntu-latest, 3.12)`: 234.23s measured test time, slowest test 12.73s = 5.4% of it
- `pytest (windows-latest, 3.9)`: 603.24s, slowest test 11.68s = 1.9% of it

Same test, near-identical absolute cost, 2.6x total. The ubuntu leg reads as "there are a few hot
tests worth fixing"; the Windows leg reads as "the cost is flat across 6277 tests and no individual
test is worth touching". Only the second one is true, and only the second one is where 51.6% of the
matrix's wall clock is. A fix aimed at the ubuntu profile would have been dispatched, landed, and
bought nothing on the axis that costs.

The second half, same session, worse: I proposed classifying tests as platform-invariant with
`grep -L "tmp_path\|subprocess\|monkeypatch" tests/test_*.py`. That selects 126 files and 1208
tests -- 19% of the suite -- and **none of the 25 slowest tests on either leg are in it**. The
heuristic selects the *cheap* tests by construction: a test that spawns no subprocess is a test
that costs nothing to run again. The genuinely invariant expensive tests
(`test_no_test_pins_the_current_version_350`, `test_unwired_scripts_253`, `test_spawn_guard_716`,
`test_prose_script_refs_1070` -- sweeps over this repository's own tracked bytes) were all excluded
by that grep, because sweeping the tree is exactly what needs a subprocess.

Cost: one wrong recommendation stated to the maintainer, corrected in the same session only because
the top-25 list was checked against the candidate set one file at a time. Cheap to check
(`grep -qx "tests/$f.py"` in a loop), and the check is what found it -- not rereading the heuristic.

Both halves are one rule: a proxy for "is this test expensive" and a proxy for "does this test vary
by platform" are each answerable from the real durations output, and neither is answerable from
the shape of the source file.

Filed as #1176 and #1177. `gh api .../actions/runs/<id>/jobs` gives per-job and per-step wall clock;
`supertool 'gh-job:<id>:grep:slowest test'` gives the plugin's own share line without pulling the log.
