A prior tick's own `oss_state.py --decision --plugin-identity ... --check-plugin-identity ...`
call recorded `detail.plugin_identity: "unchanged"` on the state file entry -- the literal
comparison verdict string, not the actual `doctor.plugin_identity()` reading
(`"<version>, <git-head-or-'no git HEAD here'>, content <digest> over <N> file(s)"`) the
`--plugin-identity` flag is supposed to carry. `--plugin-identity` records verbatim whatever
string is passed to it (`scripts/oss_state.py`'s `plugin_identity_flags` handling); it never
validates that the string looks like a real identity reading rather than a check verdict word.
Cost: this tick's own `--check-plugin-identity` against that stale entry reported `changed`
purely because "unchanged" != the real current identity string -- a false `changed` that had
nothing to do with the plugin actually changing. Confirmed by reading the prior entry
(`.max/claude-oss-watch.json`) and by tracing `scripts/oss_state.py`'s handling, which stores
`args.plugin_identity` unvalidated. Possible fix: `--plugin-identity` could refuse a value that
matches one of the check's own verdict words (`changed`/`unchanged`/`could-not-tell`/
`route-mismatch`) as a shape check, the same way other flags here refuse values that look like
the wrong kind of thing.
