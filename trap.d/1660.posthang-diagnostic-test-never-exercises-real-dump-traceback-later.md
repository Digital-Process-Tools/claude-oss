Release audit (v0.38.0..HEAD, round 1) found: `tests/test_posthang_diagnostics_1660.py:24-37`,
the only test for the new `pytest_sessionfinish` hang-diagnostic hook, monkeypatches
`faulthandler.dump_traceback_later` away and only asserts the call tuple -- it never
exercises the real call. The behaviour that decides whether the diagnostic actually works
(whether `faulthandler.dump_traceback_later(file=sys.stderr)` succeeds and lands in the job
log from an xdist worker under capture -- exactly how CI runs it: `pytest -n auto
--dist loadfile`, `tests.yml:318`) has no control in either direction. A green run of this
test reads as "the diagnostic is covered" for a diagnostic whose whole purpose is a
Windows/xdist-specific hang.

Mitigating: `posthang_diagnostics_1660.py`'s own docstring already discloses the
xdist-forwarding gap as reasoned-not-observed, and a raising hook would redden CI rather
than fail silently.

Remedy that would settle it: a test that calls the real `dump_traceback_later` under an
actual (even two-test synthetic) `-n 2` xdist session and asserts a dump reaches the
captured log.
