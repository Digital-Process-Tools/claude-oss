# The sub-manager's init floor, measured from one live tick

Observed 2026-09-03 by reading a tick's own sub-agent transcript rather than reasoning about it:
`~/.claude/projects/-Users-floriandavid-Documents-claude-oss/adaf3814-d141-4302-a420-957e0343786d/subagents/agent-a86de85749e693270.jsonl`
(270 lines, plugin cache 0.20.0, session model Fable 5.1). The numbers below are
`cache_creation_input_tokens` off each assistant event, i.e. what was newly loaded at that step.

| line | step | tokens |
| --- | --- | --- |
| 0-3 | spawn prompt + system floor + 2 attachments | 32,975 |
| 4 | `agent_role.py --write sub-manager` | 4,336 |
| 7 | `Skill(oss:manager)` -- `SKILL.md` whole | 21,309 |
| 11 | `cat commands/tick.md` | 955 |
| 16-27 | board reads | 9,843 / 7,120 / 1,525 / 1,166 / 212 |

**79,229 tokens of context stood in the sub-manager before its first dispatch decision.** Two thirds
of that is the 32,975 floor plus the 21,309 spine -- both loaded before the lane knows which phase it
will reach, which is the number the spine/phase split exists to cut. The spine is still the largest
single deliberate load in a tick's sub-manager.

The spawn prompt itself is three sentences plus the spawn token, so it contributes nothing to this;
everything above the spine is the harness's own floor, which `tick_cost` accounting does not see.

Two things this measurement is not: it is one tick on one model, and the 32,975 floor is not itemised
by the transcript -- system prompt, `agents/sub-manager.md`, CLAUDE.md and the attachments are summed
into one figure by the log, not separated. Anyone acting on this should re-measure rather than trust
the split.

**Method, so it can be repeated:** the `claude-log` preset is not loaded in this repo's
`.supertool.json`, so the listing came from running
`python3 /Users/floriandavid/Documents/claude-supertool/presets/claude-log/list.py` directly. Sub-agent
transcripts live under `<session-uuid>/subagents/agent-*.jsonl` beside the parent session file --
they are *not* `isSidechain` events inside the parent's own jsonl, which is where the first search
looked and found nothing. Grep the spawn token across the project directory to find the right file.
