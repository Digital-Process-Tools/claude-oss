# release_ci_wait.py has the same fixed-cadence gap #1492 fixed in pr_green.py

Self-review of #1492 (pr_green.py --wait rate-limit backoff) found a sibling
with the identical gap that was not in this lane's scope and was not fixed:
scripts/release_ci_wait.py's `wait_for_conclusion` polls at a fixed cadence
(default interval=45, same shape as pr_green.py had before #1492) with zero
GitHub REST rate-limit awareness. Its own docstring says it "keeps the same
contract pr_green.py's own wait_for_first_actionable keeps" -- so the two
were built to mirror each other, and #1492's fix only reached one half of
the mirror.

It is invoked by the releaser at gate 3 (commands/release.md,
`release_ci_wait.py --commit "$COMMIT_SHA" --wait`), which is exactly the
maintainer-loop machinery #1492's own issue body names as sharing GitHub's
5000/h REST budget with watchers, ticks and log reads. An overnight
/oss:run session that exhausts the budget during a release's own CI wait
would hit the identical symptom #1492 was filed over, just from the
releaser's own wait loop instead of a sub-manager's merge wait.

Not fixed in #1492's own lane: scripts/release_ci_wait.py sits under the
lane-release label pattern (scripts/release_*.py) rather than #1492's own
file set, and porting the same `_read_core_rate_limit`/`_rate_limit_backoff`
shape there is a second, separately-reviewable change rather than a rider
on this one. Found by the Explore self-review spawn on the #1492 diff;
logged rather than filed since it is a non-blocking efficiency/robustness
gap, not a correctness bug, data-loss or security issue.
