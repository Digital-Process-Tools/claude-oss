# `--suggest-companions` was tried for the companion search and abandoned mid-tick

Reported by a sub-manager on 2026-09-03, **not independently reproduced** — that qualifier is the
whole reason this is a fragment and not an issue.

The tick was briefed to run a real companion search after #918 (the previous tick had run only the
pairwise conflict check and recorded `no-adjacent` on the strength of it). It reached first for
`lane_setup.py --suggest-companions`, which exists for exactly this purpose (#851, `suggest_companions`
at `scripts/lane_setup.py:791`, with its own three-state docstring and a dedicated CLI mode).

Its report: the mode "returned false-positive matches (the same file cited for every candidate
regardless of actual body content)". It fell back to a manual grep over all 30 open issue bodies,
and that is what found the two real bundles the tick shipped — #780 + #833 (both in
`scripts/doctor.py`) and #892 + #895 (two halves of one helper, cross-referenced by the issue author).

## Why this matters more than an ordinary tool bug

#918's fix makes an unrun companion search impossible to report as a completed one. It says nothing
about the search being *good*. If the one tool built to perform that search cites the same file for
every candidate, then the honest post-#918 outcome for a tick that trusts it is a lane filled with
wrong companions — which passes every gate the same way, and is worse than a short lane, because a
bundle of unrelated issues shares a worktree and a pull request.

The measured alternative is not obviously worse: a grep over 30 issue bodies found real bundles. But
it is a manual step with no receipt, which is the shape that produced #918 in the first place.

## What would settle it

Run `python3 scripts/lane_setup.py <issue> --suggest-companions` against two candidates known to be
unrelated and see whether the cited file differs. If the same file is cited regardless, the next
question is whether it reads the issue bodies at all or falls back to something board-wide — #267 is
relevant here and may be the cause rather than the bug: an issue's files are not derivable from its
body, which is exactly why naming candidate lanes stays the caller's job everywhere else in this
loop. A mode that promises to derive them anyway may be promising something the repository elsewhere
says cannot be done.

If that is what is happening, the finding is not "the tool has a bug" but "the tool's contract
contradicts #267", which is a different and larger conversation — and a reason not to file this as a
bug report before looking.
