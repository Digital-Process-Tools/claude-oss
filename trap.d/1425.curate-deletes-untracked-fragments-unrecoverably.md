Observed 2026-09-14 21:36, watching a live `/oss:curate` pass from a second session. The pass
emptied `trap.d/` of 30 fragments in one step. 21 of them were tracked and show in
`git status --porcelain` as ` D`, recoverable with `git checkout` or `git show HEAD:<path>`. The
other 9 were UNTRACKED, so their deletion left no record anywhere -- not in porcelain, not in the
reflog, not in any object. They are simply gone from disk.

The 9, by name:

    1349.overnight-quota-2B-cache-read-context-growth.md
    1457.auto-mode-classifier-outage-stalls-lane.md
    1460.report-schema-cache-vs-branch-skew.md

    1508.quiet-main-leaks-real-channel-health-cache.md

Eight of those nine had been sitting untracked for two days, which is the ordinary state for a
fragment: `CLAUDE.md` sanctions writing one directly on the default branch and nothing obliges the
writer to commit it. So "untracked" here is not carelessness, it is the documented workflow, and
the curate pass consumes fragments in exactly the state that workflow produces.

Most were genuinely consumed rather than dropped -- 1493's content is now
`.claude/jit-context/vocabulary/00-manual/could-not-tell-shallow-clone.md`, 1349's is in
`sub-manager-hand-polls-ci.md`, 1499's CodeQL one is in `ci-evidence-is-about-one-commit.md`. That
is the pass working as designed. The problem is not that it deletes; it is that deleting an
untracked file is irreversible and the pass has no way to prove, afterwards, that a given fragment
was read before it was removed.

Two distinct failures follow from that.

FIRST: a fragment written while the pass is running is deleted without ever being read. The
fragment `1474.wait-text-claims-launcher-is-only-arming-route.md` was written at 21:33 and deleted
at 21:36. Grepping the whole of `.claude/jit-context/` afterwards for its distinctive content
("arms or binds", the false launcher claim, the two-row `claude mcp list` evidence) returns nothing
-- no rule carries it, no rule cites it. It was almost certainly written after the pass took its
list of fragments and before the pass deleted by a glob rather than by that list. Its content
survived only because the session that wrote it still had the text in context and could write it
back; nothing about the mechanism recovered it.

SECOND: a declined fragment and an unread fragment are indistinguishable after the fact. Declining
is a legitimate outcome and it also deletes. `CLAUDE.md` says a surviving fragment "was left there
on purpose, named and reasoned in the pass's own pull request" -- which means the record of every
decision lives in the PR body, and until that PR exists there is nothing on disk saying which
fragments were promoted, which were merged, and which were declined. At the time of this
observation no PR existed and the changes were unstaged in the main worktree, so for roughly the
whole pass the only evidence of 30 decisions was 30 absent files. This is this repository's own
named defect class: a fragment the pass never opened and a fragment the pass deliberately declined
render identically, and the rendering is an empty directory.

Worth considering for whoever picks this up, none of it decided here: `git add` the fragment set
before deleting anything, so every removal is at least recoverable; delete by the list the pass
actually read rather than by a glob over the directory, so a fragment that arrived mid-pass
survives to the next one; and write the per-fragment disposition somewhere on disk at the moment it
is taken rather than only into a pull request body that does not exist yet.
