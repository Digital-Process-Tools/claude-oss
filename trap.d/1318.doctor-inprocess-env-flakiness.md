While self-reviewing #1318 (mutualising tests/test_doctor_inprocess.py's
`test_main_labels_every_config_dependent_check_unmeasured_and_still_measures_them`), the
test started failing on this dev machine -- not from any diff, confirmed by checking out
the file at the pre-#1318 commit (c123897) byte-for-byte and running it in isolation: it
failed identically, three times in a row, with the exact same message.

The failure: the test's second phase (a `present` fixture with a real `.oss.json`, no
real git repo, `repo: "owner/name"`) asserts `"not checked" not in found` over doctor's
full stdout. It fails because `check_latest_skew` reports `WARN latest skew: not checked
-- owner/name does not appear among the installed plugins' own source repositories`. That
check reads a REAL, unscoped state file under this machine's own `~/.claude` (the
installed-plugins registry / "latest" cache), not anything under the fixture's `tmp_path`
-- so its answer depends on what is installed and cached on the machine running the test
at that moment, not on the fixture at all.

Reproduced with: `python3 -m pytest
tests/test_doctor_inprocess.py::test_main_labels_every_config_dependent_check_unmeasured_and_still_measures_them
-q --no-cov -p no:cacheprovider` -- failed every time across several runs today, both on
the original file and on this issue's own modified version. Ran clean (184/184 passed)
earlier in the same session, before something on this shared dev machine changed --
several other worktrees/sessions were concurrently active (fix/1314, fix/1312) and this
machine runs an oss loop that periodically updates the installed plugin itself, which is
exactly the kind of write `check_latest_skew` would notice.

Cost: roughly 30 minutes chasing what looked like a regression from a self-review fix
(removing `check_plugin_copy` from a stub list) before confirming, via the pre-diff
checkout, that the failure predates and is unrelated to that fix.

Not confirmed: the exact write that flipped this machine's installed-plugin state
mid-session. Worth someone deciding whether `check_latest_skew` (or this test's own
fixture) should be more isolated from real machine state -- `test_main_labels_...`'s
first phase already runs against a `missing` root and gets the "not checked" it expects
there; it is only the second phase's SPECIFIC "not checked" assertion is not scoped to
the fixture that is fragile against a real, mutable, machine-wide cache.
