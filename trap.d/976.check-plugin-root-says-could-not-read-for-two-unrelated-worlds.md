`oss_state.py --check-plugin-root` has three states, and `could-not-read` covers at least two situations
that are not the same fact. Observed across two consecutive ticks, 2026-09-04:

- **Tick one:** `could-not-read` because the snapshot sidecar
  (`.max/claude-oss-watch.json.plugin-root-snapshot.json`) was not on disk at all, and the tick checking
  it had never consumed it. Filed alongside `#972`, where a spawned auditor was reported running `rm -f`
  against the live main clone outside its worktree. Plausible deletion; never confirmed.
- **Tick two:** `could-not-read` because the sidecar had already been read once earlier in the same tick,
  reported `unchanged`, and the read consumes it. Working as designed — the snapshot answers for one tick
  and then it is spent.

One tick lost time deciding which of those it was in, and could only tell by remembering whether it had
already called the check itself. A tick that calls it twice by accident, or one resumed enough times that
nobody holds that memory, cannot distinguish "my instrumentation was deleted underneath me" from "I
already asked". Both render as the same three-state answer with the same string.

This is the repo's own defect class landing on the repo's own instrumentation, one level in: the check was
built with a third state precisely so an absence would be reportable, and the third state is now itself
overloaded. The fix is probably a fourth answer — `already-consumed` distinct from `could-not-read` — or
having the consuming read say so in a way the second read can echo back. Cheap either way; the current
shape costs a tick's reasoning every time it comes up, and costs more than that on the one occasion the
answer really is a deleted file.

Confirmed by reading both ticks' reports side by side. Neither tick was wrong about its own case; the
ambiguity is only visible from outside, holding both.
