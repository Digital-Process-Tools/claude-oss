# Raw python -c write to an already-written report JSON skips every supertool validator

While fixing two schema validation errors in an already-written report JSON
(missing `claim`/`grade` keys under `claims.items[0]`, missing a `reason` for
`tests.full.state: not-run`), I reached for `python3 -c "... json.load(...);
d[...] = ...; json.dump(...)..."` to patch the file in place instead of a
`supertool edit`/`paste` call. This is exactly the trap
`.claude/jit-context/tools/00-manual/a-write-outside-supertool-meets-no-validator.md`
(or wherever it currently lives) describes: the raw Python write matched no
supertool op, so it got no jsonlint, no gitleaks scan, no rollback-on-fail and
left no receipt -- and the PreToolUse hook fired *after* the write had already
landed (a `remind`, not a `block`), so the file was already mutated by the
time the reminder appeared.

The write happened to produce valid JSON (verified separately with
`python3 -m json.tool`), so no damage resulted this time, but the only reason
I caught it at all was the JIT-CTX-BLOCKS reminder firing immediately after
the call -- if that context injection had not matched (e.g. a slightly
different `open(...)` idiom), the file would have silently skipped every
write-time guard. Confirmed by re-doing the same edit properly afterward
(`supertool 'paste:@-'` rewriting the whole file with the corrected content),
which reported `rewrote ... (69 lines, 7094 -> 6618 bytes)` and kept a
`.bak` backup automatically -- something the raw write did neither.

Lesson for whoever curates this: when a report JSON needs a small structural
fix (add a missing required key, fix an enum value) after it has already been
written once via `supertool paste`, the correct move is a `supertool edit`
with a precise `old`/`new` anchor on the JSON fragment being changed, not a
`python3 -c` json.load/dump round-trip -- even for "just adding two keys",
because a `json.dump` round-trip can also silently reformat unrelated parts
of the file (observed elsewhere per the same jit-context note, #1075).
