A required second-pass review round (`fix_commit_scope.py` flagged a self-review fix commit as
`needs-second-pass` for touching 4 files including a byte-budgeted one) spawned an `oss:auditor`
against the fix commit alone. That spawn's own `tree_snapshot.py compare` reported `mutated`, and
it self-disclosed why: it ran `rm -f` on an untracked file matching the
`-before-snapshot.json` naming convention (`tree_snapshot.SNAPSHOT_ARTIFACT_RE`'s own exclusion
suffix), believing it was disposable leftover scratch debris from an earlier round. It was not --
it was this round's own before-snapshot, written moments earlier by the developer lane that spawned
it, still live and needed for that round's own compare.

The file could not be restored (untracked, contents never read before deletion). Consequence: the
developer lane could not run `tree_snapshot.py compare` for that round and had to fall back to
`git-status` alone (which did confirm a clean working tree, so nothing of substance -- no tracked
file -- was actually lost; only the scratch snapshot artifact itself).

What seems to have happened: the `-before-snapshot.json` suffix, which exists specifically so
`compare` can tell "my own bookkeeping" apart from a real mutation, reads to an agent that did NOT
create the file as "safe scratch debris left by someone else, fine to clean up" -- especially when
an earlier, unrelated round in the same lane really had left a stray snapshot file behind (observed
in this same lane's first review round: an untracked `oss-developer-review-1687-1696-before-
snapshot.json` sat in the tree for a while before being deleted deliberately by the lane itself
once its own compare had run). A spawn with no way to tell "stray leftover" from "another agent's
still-live snapshot, created 30 seconds ago" defaulted to deleting it.

Possibly relevant: the mutation-receipt mechanism (`agents/developer/review.md`,
`agents/tick-review.md`) already tells a spawn not to mutate the tree at all, and a review-only
spawn deleting *any* file -- even one it believes is scratch -- is arguably already covered by that
rule and this is an instance of it not being followed rather than a gap in the rule itself. Not
sure whether this is a new rule (e.g., "never delete a `*-before-snapshot.json` file you did not
personally create, even if it looks like debris -- report it as an anomaly instead") or just a
sharper restatement of the existing "must not mutate the tree" instruction. Logging it either way.
