`tree_snapshot.py snapshot` was written to `_snapshot.json` inside the lane's own worktree
(`<worktree_root>/1544/_snapshot.json`), right before spawning the two
self-review agents (Explore and oss:auditor), following the developer brief's own guidance that an
in-worktree path is not subject to whatever collects files from the shared scratchpad.

By the time both spawns had returned (roughly 6 minutes: the Explore spawn alone ran 3,328,954 ms
per its own usage report, plus the auditor's 225,663 ms, largely concurrent), the file was gone --
`could-not-compare` on `tree_snapshot.py compare --before -`, and a plain `find . -maxdepth 1 -name
"_snapshot*"` also found nothing. Neither spawn's own final report claimed to have written or
deleted anything at that path, and both were explicitly told not to mutate the tree.

Root cause unconfirmed. Candidates: something in this environment periodically sweeps
dot-prefixed-looking or underscore-prefixed scratch files at the worktree root regardless of
whether they are inside a scratchpad; one of the two reviewer spawns ran a broad cleanup command
(`git clean`, an `rm -f *.json`, or similar) that happened to catch this file without naming it in
its own report; or something about a ~3.3M-ms-long Explore spawn's own tool use touched the
worktree root in a way its final report did not surface (it ran a full `pytest tests/ -q --no-cov`
in that same worktree, which is plausible cause for something to have cleaned a stray top-level
file, though nothing in pytest's own behaviour normally does this).

Cost: one round of `tree_snapshot.py compare` returning `could-not-compare` instead of a real
`clean`/`mutated` verdict, and the fallback of reasoning from `git status` (2 files dirty, both my
own two self-review fixes, nothing else) instead of the tool's own receipt. Confirmed via `git
status` cross-check rather than the snapshot tool itself.

If this recurs, the fix is probably: never rely on an in-worktree path surviving a long
concurrent spawn without a second copy, or take the before-snapshot immediately before spawning
and read it back to confirm bytes-on-disk right when the compare call runs, not just once at
write time.
