When a fix lands on the default branch and a pull request is red because its base lacked that fix,
**re-running the pull request's checks does not pick the fix up.** Push a merge (or a rebase) instead.

Observed 2026-09-04. `#1005` fixed a stale marker on `main` that was failing
`tests/test_claude_md_currency.py` on four unrelated pull requests. The obvious next step — re-run the
failed jobs, now that `main` is fixed — would have reproduced the identical `AssertionError: assert
'0.21.0' == '0.22.0'` on every one of them.

The mechanism: `.github/workflows/tests.yml` triggers on plain `pull_request`, so the checkout is a
**merge-ref computed when the run starts**. Re-running a completed run's jobs reuses that same frozen
ref rather than recomputing it against the current default branch. The run is a rerun of the old merge,
not a new merge.

What makes this expensive is how the failure reads. A re-run that comes back red looks like evidence the
fix did not work — so the natural response is to go back and re-examine a fix that was correct all along,
or to conclude the diagnosis was wrong. The tool reports honestly; the reading is what misleads.

What was actually done: `git merge origin/main` into each of the four branches and pushed — real merge
commits, no rewrite, so no force-push and no risk to anything watching those refs. Fresh runs then
computed fresh merge-refs and went green.

Worth checking before generalising: this is a property of the `pull_request` trigger, so a workflow using
`pull_request_target`, or one triggered on `push` to the branch, may not behave the same way. The rule
that holds regardless is the shape — **a rerun re-runs what the run already was**, and if the input to a
run needs to change, something has to push.
