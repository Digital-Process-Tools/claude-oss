The absolute-home-path guard caught three separate trap.d fragments in one morning, from three
different writers, and each one turned the default branch red.

Observed 2026-09-09 in this repo. `tests/test_content_invariants.py:384` refuses a shipped,
mid-lane-written directory containing an absolute home path. It fired three times in about two hours:

- `trap.d/1333.multiple-schedulers-one-clone.md`, written by the scheduler session itself, quoting
  the maintainer's own absolute home path inside prose describing a shared clone. Red at 14af48a,
  four pytest legs.
- `trap.d/1324.report-schema-skew-pinned-plugin-cache.md`, written by a developer lane, absolute path
  at lines 2 and 18. Red at dac7451, the same four legs: macos-3.12, windows-3.12, ubuntu-3.9,
  ubuntu-3.12. Suite read 1 failed, 6874 passed, 33 skipped.
- and #1255/#1262 already record the same guard firing on
  `trap.d/1155.forgot-cd-prefix-landed-write-in-main-clone.md` earlier in the project's history --
  which is why the guard exists at all.

The guard is working exactly as designed and is not the problem. What the repetition says is that the
instruction to write a fragment and the instruction not to embed a machine path live in different
places, and the moment that produces a fragment is the moment a writer is least likely to be holding
both. A fragment gets written mid-task, in prose, about something that just cost time -- and the
natural way to say where it happened is to paste the path where it happened. Every one of these three
fragments pasted a path because the path was the evidence.

Two things make it worse than an ordinary lint failure. The write lands directly on the default
branch under the sanctioned trap.d-logging exception, so it skips pull-request CI entirely and the
first thing that observes it is main's own post-push run. And a lane branched from that red base
inherits the failure, so its own PR goes red for a reason that has nothing to do with its diff -- two
lanes here, #1336 and #1337, both red on the identical four legs while their own changes were fine.
A lane sent hunting through its own diff for that is spending a review round on somebody else's
fragment.

What would remove the class rather than catch it later: redact at write time. A wrapper that takes
fragment text and rewrites `$HOME`, the worktree root and the clone path to placeholders before the
file is created -- `HOME_PATH_PLACEHOLDER_USERNAMES` already exists and names what the guard will
accept, so the redaction target is already defined; nothing applies it on the way in. Failing that, a
pre-commit check on trap.d/ specifically, so the write is refused locally instead of turning the
default branch red for everyone.

Confirmed via `gh-job:102396875176:fail`. The three-state note that matters here: the gh-branch
watcher emitted `went_not_green` on dac7451 saying "nothing has failed", and emitted nothing at all
when those legs subsequently did fail, because the verdict never changed category -- see #1214. So
this red was found by a scheduler reading the board by hand at the 34-minute mark, not by any event.
