Gate 3 release audit (v0.37.0..HEAD, round 2) found: after #1602 (`effb9214`) dropped the
`^curate/` never-auto-merge gate and #1600 (`0fc3f70b`) added an advisory `CURATE:` line to
`agents/tick-merge.md` step 2 / `scripts/tick_handback.py`'s `_CURATE` field as the replacement
visibility, the field is optional by construction: `_find_optional_field` folds both "absent" and
"duplicated" to `curate=None`, and nothing validates that a tick which actually merged a
`^curate/`-named branch emitted a `CURATE:` line at all.

Observed: `printf 'TICK: completed\nTICK-ENDS: work-started\n' | tick_handback.py -` exits 0 with
no `curate:` line and no diagnostic -- silently indistinguishable from a tick that never touched a
curate branch. #1600's own docstring states the premise this is meant to fix ("a curate pull
request merging silently and one that never ran render identically without this line"), but that
premise still holds whenever the advisory prose chain (`tick-merge.md` -> `sub-manager.md` ->
`tick-accounting.md`) is not followed by whichever agent is composing the handback -- there is no
code path that knows the merged PR's head branch at classification time to cross-check against.

This finding is about the receipt only; the design decision to drop the `^curate/` gate is out of
scope for a release audit and not what this fragment argues about.

Fix candidates: have the merge step (`tick-merge.md` / `tick-merge` agent) pass the merged branch
name into the handback payload so `tick_handback.py` can itself detect "branch matched `^curate/`
but no `CURATE:` line was supplied" and flag it, rather than relying entirely on prose discipline.
