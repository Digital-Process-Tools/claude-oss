`commands/run.md` step 1 pins the doctor spawn as
`Agent(subagent_type: "oss:doctor", run_in_background: false)`. In a real first `/oss:run` (a
managed PHP repo, plugin 0.42.1, 2026-09-27), the scheduler's actual tool call carried
`description`, `subagent_type` and a paraphrased `prompt`, and no `run_in_background` at all. The
harness reported "Async agent launched successfully", the scheduler said "Wait for its report",
and the doctor's hand-back arrived about 10.5 minutes later as a message from another session.

Read from that session's transcript (the managed repo's project dir under the maintainer's
`~/.claude/projects/`), not reproduced. The pin sits in the command file's text, and it is the
same pin #1586/#1649/#1747 each added; what this shows is that the scheduler model can paraphrase
the call and drop it anyway. Setup's spawn in the same session was also async.

Cost here: nothing broke, but it is the exact shape those issues exist to prevent, and a
content test on `commands/run.md` cannot see it -- the text was right, the call was not.
Possibly belongs with whatever measures actual spawn calls from transcripts rather than prose.

**Correction, same day, same machine (Claude Code v2.1.280):** the dropped pin may not be the
cause at all. A scheduler session spawning `oss:sub-manager` with `run_in_background: false`
passed explicitly in the call still got "Async agent launched successfully ... The agent is
working in the background", with the completion arriving later as a notification. So on this
harness version the pin can be present and ignored; whether that is an auto-mode behaviour, a
per-agent-type setting, or a version change was not established. Either way, prose in a command
file cannot make a spawn blocking, and anything in the loop that assumes a blocking spawn (reading
a result "in the same turn") should be checked against this.
