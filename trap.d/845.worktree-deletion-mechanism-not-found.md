# #845 worktree-deletion mechanism investigated, not found in this plugin's own code

Investigated a worktree-deletion mid-run bug filed as "mechanism not
identified". Grepped scripts/ and skills/ for `worktree remove` /
`worktree_remove` / `rmtree` touching a git worktree path -- the only hits
are the two hand commands `git worktree remove --force` and `git branch -D`
that `doctor_check_worktree_reap_permission.py` checks permission for, both
typed by a human or an agent reading `skills/manager/phases/merge.md`'s reap
prose, never issued programmatically by any script here. `lane_setup.py`
itself never calls `git worktree remove`; its own `os.remove` calls only
ever touch the JSON registry records under `.oss-lanes/`, never a worktree
directory.

Conclusion: root cause is not in this plugin's own code, at least not as
far as this investigation reached. Could still be an LLM manager/sub-manager
session misjudging occupancy while following merge.md's prose by hand (the
prose already tells the reader to treat `cannot tell` as occupied, so a
misread would be an instruction not followed rather than a hole in the
instruction), or something entirely outside this repo (a human running
`git worktree prune`, an IDE, a cron). Did not fabricate a fix for an
unconfirmed cause -- built `lane_setup.detect_vanished_worktrees` /
`--check-vanished` plus a new `doctor` check instead, so a repeat is loud
rather than silent.

Time cost: most of the investigation time went into confirming the
*absence* of a mechanism (reading merge.md's reap section in full, checking
`held_from_live_lanes` and `worktree_occupancy` were not secretly deleting
trees) rather than finding one -- worth remembering that a "not found in
this repo" conclusion still needs the same grep discipline as a "found it"
one, or it is just an assumption with a grep command attached.
