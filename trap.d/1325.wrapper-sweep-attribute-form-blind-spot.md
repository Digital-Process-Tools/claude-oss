# #1325 sub-part 2: wrapper sweep misses attribute-form calls

Left unfixed in this lane and logged rather than stretched to cover:
`tests/test_bare_gh_git_spawn_sweep_1165.py`'s wrapper-mediated detection
(`_WrapperFinder`/`_Visitor`, #1295) only recognises a wrapper called as a
bare `ast.Name` -- `_run(["git", ...])`. A cross-module call of the
identical shape, `module.wrapper(["git", ...])` (an `ast.Attribute`, e.g. a
hypothetical `scaffold._run(["git", ...])` called from a different file),
is invisible to `is_wrapper_call` entirely, because that check is
`isinstance(func, ast.Name) and func.id in self.wrapper_names` -- an
`ast.Attribute` never matches. Confirmed by reading the check directly
(`tests/test_bare_gh_git_spawn_sweep_1165.py` around line 239), not
inferred from the issue text.

Self-review correction: the original wording here claimed grepping for
`scaffold\._run\(` across `scripts/` and `tests/` found nothing. That was
wrong -- `tests/test_scaffold.py:1204` calls
`scaffold._run(["gh", "label", "list"])`, the exact cross-module,
attribute-form, literal-argv shape this gap describes. The correct scoping
argument is narrower: `test_bare_gh_git_spawn_sweep_1165.py`'s own scan
only walks `SCRIPTS_DIR.glob("*.py")` (`scripts/`), never `tests/`, so a
test file calling `scaffold._run` with a literal argv is out of the
sweep's declared scope by construction and was never going to be caught
regardless of this gap -- not because no such call exists. Within
`scripts/` itself, `scaffold._run` is only ever called from inside
`scaffold.py` (bare-name form, which the sweep already catches), and the
only two cross-file imports of `scaffold` (`doctor.py`,
`doctor_check_codeql_scan.py`) import the module for other reasons, never
call `_run`. So there is still no live gap inside the sweep's own scope,
but the claim that justified that conclusion was itself false and is
corrected here rather than left standing.

The issue's own citation of `oss_config.py:2693` as a second instance of
this gap does not hold up under direct reading: that line sits inside
`_ignore_rule`'s docstring, and the nearby code
(`git_bin = gh_which.safe_which("git")` then `command = [git_bin, ...]`)
is the already-safe pattern -- `git_bin` is bound from a real resolver
call, not a bad literal, so `_Visitor.visit_Assign`'s bound-argv tracking
correctly does not flag it. Line numbers in the issue may have shifted
since the audit that filed it; worth checking against the issue's own
diff/commit rather than assuming the current line still matches.

Fixing the attribute-form gap needs the `_WrapperFinder` pre-pass to also
resolve `module.attr` calls back to a wrapper defined in another
already-scanned file -- real cross-file analysis, not the same-file,
presence-based heuristic this sweep is deliberately built as (see its own
module docstring: "grep-based is fine" was the brief). Left for a
follow-up rather than done inside this lane, per this issue's own
"decide which sub-parts you can land soundly" instruction.
