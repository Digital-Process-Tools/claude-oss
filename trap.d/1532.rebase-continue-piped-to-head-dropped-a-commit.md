# A rebase dropped a commit and still reported success

`git rebase --continue` piped through `head` silently lost the second of two
commits, then printed "Successfully rebased".

Observed 2026-09-15 in the #1532 lane, rebasing `fix/1532` (2 commits) onto
`origin/main` after two sibling PRs merged ahead of it.

Commit 1 conflicted in six files. I resolved them, staged them, and ran:

    git -c core.editor=true rebase --continue 2>&1 | head -20

The output showed commit 1's summary and stopped at 20 lines, which is what
`head -20` is for. What I did not notice is that closing the pipe early sends
`SIGPIPE` to git partway through its own output.

A later `git -c core.editor=true rebase --continue` then printed
**`Successfully rebased and updated refs/heads/fix/1532.`** and exited 0.

`fix/1532` had **one** commit on it. Commit 2 -- which carried a real bug fix,
its test, and five stale-prose corrections from the self-review round -- was
gone. No conflict was ever reported for it, and no error was printed at any
point.

The tells, none of which is loud:

- `git log --oneline <base>..HEAD` showed one commit where two were expected.
  This is the only reliable signal and it requires knowing the expected count.
- `supertool 'git-status'` said `Working tree: clean` and `vs main: 7 ahead`.
  Both true, both useless here -- "clean" is also what a correct rebase looks
  like between commits, and the ahead-count was against the local `main` ref,
  which was itself 6 behind.
- `.git/worktrees/<name>/rebase-merge/done` listed BOTH picks while
  `git-rebase-todo` was empty and `msgnum` equalled `end`. That reads as
  "finished", not as "one was dropped".

**Recovery was straightforward once noticed**, because the orphaned commit is
still a reachable object:

    git cat-file -t <sha-of-commit-2>      # still "commit"
    git cherry-pick <sha-of-commit-2>

The cherry-pick then surfaced the three genuine conflicts the rebase should
have shown in the first place, and they resolved normally.

What to do instead:

- **Never pipe `git rebase --continue` (or `--abort`, or `--skip`) into
  `head`/`tail`.** Redirect to a file and read the file, or let it print in
  full. The same applies to any git command whose exit path matters.
- **After any multi-commit rebase, count the commits**:
  `git log --oneline <upstream>..HEAD` against the number you started with.
  Do not trust "Successfully rebased".
- **Then grep for a symbol only the later commit introduced.** Counting
  catches a dropped commit; grepping catches a commit that applied as empty.
  In this case `grep _OK_STATES scripts/lane_setup.py` returned nothing, which
  was the confirmation.

Cost: roughly 15 minutes, and it would have been a silently shipped regression
-- the dropped commit contained the fix for a bug two independent review spawns
had found.
