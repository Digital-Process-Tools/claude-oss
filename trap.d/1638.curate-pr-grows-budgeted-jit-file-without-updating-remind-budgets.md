# A curate PR grew a budgeted jit-context file without updating remind_budgets

A curate pull request's own diff grew a `remind_budgets.py`-tracked jit-context file past its
declared budget with nothing in the diff updating the budget or baseline, and nothing in the
curate command checked before opening the PR.

PR #1638 (`curate/20260917T000000Z`) edited
`.claude/jit-context/tools/00-manual/supertool-payload-forms.md` from 2126 B to 3269 B (+14/-2
lines, folding in a doubled-backslash TOML caveat), but `scripts/remind_budgets.py`'s declared row
for that file still read `(2126, 2350)` -- both the baseline
(`tests/test_baseline_matches_disk_1014.py`) and the budget (`tests/test_remind_budgets_1584.py`)
went red on every CI leg (ubuntu 3.9, macos 3.12 observed directly; the same two tests run on all
13 legs). Deterministic on every leg, not flaky or platform-specific -- caught by the exact two
guards `CLAUDE.md`'s "replace, don't append" budget mechanism exists to catch -- and it cost a
full tick's review cycle (needs-fix) to notice, since nothing spawned by `/oss:run`'s curate
sub-step re-read `remind_budgets.py` / `test_baseline_matches_disk_1014.py` against the diff it
was about to commit.

What would settle it: `commands/run/curate.md` (or whatever assembles a curate PR's commit)
running `python3 scripts/remind_budgets.py --check` (or reading its own diff against
`REMIND_BUDGETS`'s declared sizes) before pushing, and failing loudly rather than leaving CI to
catch it three legs later.

Filed here rather than as an issue: CI already catches every instance before merge
(`fails-to-preserve`, non-blocking per `skills/manager/phases/findings.md`) -- the cost is
review-cycle friction, not a shipped defect.
