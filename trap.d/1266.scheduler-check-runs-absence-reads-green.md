A scheduler poll that waits on the check-runs API for a freshly pushed commit reports a clean
conclusion before the test workflow has produced a single check-run.

Observed 2026-09-07 in a /oss:tick scheduler session. After merging PR #1238, main was at
9d3d0af. A Monitor poll shaped as "read
repos/OWNER/REPO/commits/SHA/check-runs, break when no entry is in_progress or queued, then
report the conclusion tally" fired within seconds and reported {"success": 2}. The two were
`Analyze (python)` and `Analyze (actions)` -- CodeQL only. The `tests` workflow had produced
zero check-runs at that moment, so the "nothing pending" condition was true vacuously, and a
commit with 16 unstarted test legs was reported as concluded-and-green. The same poll made the
same false report on eaf2c2c one merge earlier.

The runs API tells the truth where the check-runs API cannot:
`gh api "repos/OWNER/REPO/actions/runs?head_sha=SHA" --jq '.workflow_runs[]|"\(.name)|\(.status)|\(.conclusion)"'`
returned `tests|push|pending|null` for 9d3d0af at the same instant check-runs said everything
had concluded. It also distinguishes a run that was `cancelled` by the concurrency group when a
later merge superseded it (eaf2c2c) from one that failed -- a distinction the check-runs tally
cannot make either, because a cancelled run leaves no check-runs behind.

The fix for a poll of this shape: enumerate the workflows expected to run on the ref, and require
each expected workflow to have a run whose status is `completed` before reading any conclusion.
Zero runs for a workflow is a third state -- not-yet-created -- and must not be folded into the
pass arm. Note that gh-branch's own `no_run` sentence gets this right ("zero workflow runs on
SHA; ... a run is still expected"), which is what made the discrepancy visible: the watcher said
NOT GREEN for a commit my own poll had just called green.

Cost: two false green reports on main in one tick, both stated out loud to the maintainer before
being caught and retracted. Caught only because the counts (2, not 16) looked wrong next to the
16-leg tallies the same session had read correctly on earlier heads.
