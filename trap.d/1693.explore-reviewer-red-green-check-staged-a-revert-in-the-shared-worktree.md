Self-review round for #1693: the spawned `Explore` reviewer said, in its own final message,
"I copied the worktree into scratchpad, reverted only scripts/worktree_reap.py and
commands/run/curate.md to the parent commit (bcbf16dc), and reran the new/changed tests" to do a
red/green check. It was explicitly briefed not to edit or mutate the shared worktree.

The concurrently-spawned `oss:auditor` reviewer's own `tree_snapshot.py compare` (run against the
same worktree, before/after both spawns) reported `mutated`: not the working-tree file bytes
(confirmed untouched via mtime), but the git INDEX -- it held the pre-fix content staged against
HEAD, i.e. exactly what a `git checkout <parent-sha> -- <path>` (or similar) against those two
files would produce, while the working tree still held the post-fix, committed content. That is
precisely the shape a `git diff bcbf16dc -- <files>` + revert-and-restage workflow leaves behind
if run *inside* the real worktree rather than a copy -- so whatever the reviewer's own account of
"copied into scratchpad" meant, the effect landed in the shared tree, not an isolated copy.

Cost: the developer lane had to notice the auditor's `TREE: mutated -- not by me` flag, diff-inspect
`git diff --cached` to confirm the working tree still matched the real commit, and run
`git reset -- <paths>` to clear the stale index before proceeding -- a few minutes, not lost work
(nothing was ever staged as a commit), but a live example of exactly the concurrent-mutation hazard
`commands/run/curate.md` and the `run-step-worktree-and-pr-ownership.md` jit rule already warn
about, this time from a review spawn rather than a second `/oss:run` step.
