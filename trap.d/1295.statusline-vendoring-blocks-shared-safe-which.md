While fixing #1295 (bare git/gh spawns in scripts/oss_config.py and scripts/statusline.py), the
natural fix -- `import gh_which` and call `gh_which.safe_which` -- works fine in oss_config.py but
cannot be used in statusline.py at all. scripts/statusline.py's own module docstring states "No
third-party imports: this file is vendored into `.oss/statusline.py` in repositories that install
nothing to run it" (confirmed: scripts/scaffold.py's `_owned_statusline` reads scripts/statusline.py
verbatim and writes it standalone into a scaffolded repo's `.oss/` directory, with no sibling
scripts/gh_which.py copied alongside it). So statusline.py had to get its own inlined, reduced copy
of gh_which.safe_which's resolution walk (`_safe_which`, `_win_candidate_names`,
`_WIN_DEFAULT_PATHEXT`) rather than importing the real one.

This creates a real, permanent drift risk of the same shape #570 already named for a different pair
of files (`.claude/jit-context/tools/01-oss/supertool-required.md` vs `TOOLS_SUPERTOOL` in
scripts/oss_rules.py, closed by tests/test_supertool_rule_sync_577.py comparing the two bodies): if
scripts/gh_which.py's safe_which ever gets a correctness fix (e.g. a PATHEXT edge case, or a further
Windows curdir-execution refinement), scripts/statusline.py's own copy will not get it, and nothing
today would notice the two have diverged. Did not build a sync test for this within #1295's own
scope (would be a second, separate change reaching well past a bug-fix issue's blast radius) -- but
the shape is identical to #570's own precedent, and a comparison test (comparing the actual
resolution logic -- the loop body and the PATHEXT list -- rather than requiring byte-identical files,
since the two functions necessarily have different signatures/names) would be the natural fix if
this is judged worth doing.

Confirmed by: reading scripts/statusline.py's own module docstring (lines ~20-22) and
scripts/scaffold.py's `_owned_statusline`/`OWNED_TEMPLATES` (around line 1409, 1421), which copies
statusline.py's raw text with no sibling gh_which.py reference.
