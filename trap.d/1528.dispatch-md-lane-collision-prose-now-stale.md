#1528 removed `select_issues.py`'s `lane-collision` disposition -- a candidate whose declared
files overlap the fleet's already-held file set used to be dropped outright; it now stays
`eligible`, the same as any other candidate, with no automated exclusion or replacement field
consuming the overlap at all (a per-candidate `overlap` field was built and then removed again in
the same lane, per a mid-lane maintainer scope narrowing -- see the sibling trap fragment on that
helper's own three-states bug).

Two pieces of maintainer-facing prose, both outside this lane's file set (`scripts/select_issues*.py`,
`scripts/lane_setup*.py`, matching test files only), now describe behaviour that no longer exists:

- `skills/manager/phases/dispatch.md:378-379` reads verbatim: "**Never bundle an issue a running
  lane already touches.** `select_issues.py` derives the held set itself and excludes them." That
  sentence is false as of #1528 -- confirmed by this lane's own test,
  `tests/test_select_issues_1528.py::test_lane_collision_disposition_no_longer_produced` (renamed
  across the lane's two commits, same assertion throughout: `"lane-collision" not in dispositions`).
  `dispatch.md:306-309` and `docs/pick-the-work.md:83-84` also still list `lane-collision` as a live
  per-issue disposition value; `grep` over every `.py` file confirms the string is gone from the
  code entirely.

- `docs/pick-the-work.md:118-120` goes further and tells the LLM veto step explicitly that
  disjointness is "already decided better" by step 1 upstream -- which was true before #1528 and is
  not true after it. Nothing in the current dispatch procedure reads a per-candidate overlap signal
  at all any more (there is none to read), so a maintainer following this doc as written would
  believe overlapping candidates are still screened out automatically and could dispatch two lanes
  onto the same files, which is the exact worked example (#1526 vs #1499) that motivated #1528 in
  the first place.

Both findings were caught by the self-review `Explore` spawn against #1528's diff, independently of
the `oss:auditor` spawn's own findings. Neither file is in scope for a `select_issues.py`/
`lane_setup.py` lane to edit. Whether either sentence is even worth fixing on its own, rather than
being folded into whatever #1530 leaves behind (it is deleting the underlying `lane_patterns`
derivation these sentences describe as gating dispatch, which may moot both paragraphs rather than
merely correct them), is a maintainer call.
