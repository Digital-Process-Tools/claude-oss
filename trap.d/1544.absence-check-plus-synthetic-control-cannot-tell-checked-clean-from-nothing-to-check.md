Second self-review pass on #1544 steps 3-4 (agents/tick-merge.md, agents/tick-accounting.md,
commit 442b73cb fixing findings from the first pass) surfaced a class-wide observation rather than a
defect in this diff specifically, and it is worth recording even though the finding was argued down
rather than fixed.

The shape: a test asserts "this file must never contain a command line doing X" by filtering the
file's own lines to a narrow shape (here, lines starting with `python3 `/`git `) and asserting none
of the matched lines contain the forbidden substring. When the file legitimately states its calls as
prose rather than literal command lines (agents/tick-merge.md documents `lane_setup.py <issue>
--release` and `git tag` only as backtick-quoted prose, never as a fenced bash command), the filtered
list is empty and the assertion passes vacuously -- it always has and always will, regardless of
whether the file changes, unless the file's own convention for stating commands changes too.

The first self-review round found this and asked for a positive control proving the predicate CAN
fail (a synthetic bad line fed through the same filter+assertion). That control is real and useful --
it proves the *mechanism* works -- but it does not close the actual gap: a reader of a green
`test_it_never_writes_or_clears_the_role_marker` still cannot tell "checked the real file's content
and found nothing forbidden" from "the real file's content was never in the shape this check even
looks at." Those two states render identically (green), which is exactly this project's own named
defect class (an absence produced by the tool, read as an absence in the world) applied one level
down, inside a test asserting an absence about another file.

This was not fixed in this lane because: (1) it is not unique to the two new files here -- the
identical shape already exists in `tests/test_tick_review_call_shape_1544.py`'s
`test_a_flag_pr_green_py_does_not_have_would_be_caught` and similar "must never name more than one
placeholder"/"must never appear" checks across this test suite, so fixing it here alone would be
inconsistent with an established, repo-wide convention; and (2) a real fix (asserting the file
actually states its forbidden-pattern-adjacent commands in SOME checkable shape, not just that no
command line matches a narrow filter) is a design question about how strict "must never do X" checks
should be for prose-only agent files, not a one-line fix.

Worth `/oss:curate` deciding whether this is a rule at all, and if so at what generality: e.g. "a
'must not contain X' test over a hand-filtered line subset needs either (a) a second assertion that
the filtered subset is non-empty on the real file (proving the check has something to check), or (b)
an explicit acknowledgment in the test's own docstring that the file states its commands as prose and
the check exists only to catch a future regression into literal command lines."
