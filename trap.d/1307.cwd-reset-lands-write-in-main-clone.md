While implementing #1307 (bin/oss-workspace channel-arming fix), a `supertool 'edit:@-' < /tmp/edit2.toml`
call was run with NO `cd` prefix, after a prior call in the same turn had been refused by the
raw-command guard. The refused call had included `cd /Users/floriandavid/Documents/claude-oss-wt/1307 && ...`,
and the harness's own note ("cwd resets between Bash calls") was known but not acted on for the
IMMEDIATE retry -- the retry omitted `cd` entirely, assuming (wrongly) that cwd would still be the
worktree from the successful call two calls earlier.

The bare `supertool edit:@-` ran in the SESSION'S DEFAULT cwd, which turned out to be the MAIN CLONE
(`/Users/floriandavid/Documents/claude-oss`), not any worktree -- and that main clone was, at the
time, checked out to `chore/curate-trap-d-1319`, another agent's own in-progress branch (visible in
the op's own receipt: `[branch: chore/curate-trap-d-1319]`). The edit landed and was reported as
successful. This is exactly the two things CLAUDE.md and the developer brief both warn about at
once: "never work in the main clone" and "cwd does not persist between Bash calls, prefix `cd` to
every write" -- reproduced together, in one call, despite having read both rules earlier in the same
session.

Caught immediately (not by any tooling) by running `git status`/`git branch --show-current` in the
main clone right after the op's receipt printed an unexpected branch name in its own `[branch: ...]`
line -- the receipt DOES print the branch it landed on, which is what made this catchable at all.
Reverted with `git checkout -- bin/oss-workspace` in the main clone before any other command touched
it, then confirmed `git status --short` in the main clone was clean of the change.

What would have caught this without relying on noticing the branch name in a receipt: a rule (or a
guard) that treats any `supertool` write call with no `cd` prefix in the SAME bash command as
suspect by default, rather than relying on the operator to notice after the fact. The existing
developer brief already says "prefix cd to every write, not once at the top" -- this is a case where
the rule was known, stated in the very same session's own system prompt, and still not applied on a
single retry made right after a refusal, under time/attention pressure from fixing the refusal
itself. The receipt's own `[branch: ...]` line is the thing that actually saved this -- worth
considering whether that line should be MORE prominent (e.g. a WARNING when the branch does not
match an expected pattern) rather than a plain informational field easy to skim past.
