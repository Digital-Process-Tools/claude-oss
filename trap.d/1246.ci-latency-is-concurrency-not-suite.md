"CI is slow" on this repository was, on measurement, almost never the test suite.

Measured 2026-09-07 on run 34099357435 (`tests`, `main` at `0dee1e2`), 14 jobs. Thirteen of the
fourteen started within 7 seconds of each other -- the matrix is already fully parallel -- so
wall-clock is governed by the slowest single leg (`pytest (windows-latest, 3.12)`, 311s), not by
the 35.9 leg-minutes the run consumes in total. Cutting legs changes the second number and barely
touches the first, on an isolated push.

Two things dominate instead, and neither is the suite:

1. **Runner concurrency during a merge train.** Five `tests` runs were created in the 08:05-08:12Z
   window (one PR, four `main` pushes). The owning org's plan reads `free` via
   `gh api orgs/<org> --jq .plan.name`, whose published limits are 20 concurrent jobs, at most 5
   macOS. At 14 jobs per run, two overlapping runs already exceed the cap. The observable was a run
   created at 08:12:25Z whose first job did not start until 08:16:53Z -- 4.5 minutes of pure queue,
   with nothing wrong with the run itself. Note the current matrix asks for 5 macOS legs, which
   saturates the macOS cap with a single run.
2. **Reruns caused by a flaky leg.** The one job that started late (+377s) was a rerun after
   #1228's shared-path race killed it. That rerun was 6.3 of the run's 11.5-minute span -- larger
   than any plausible saving from trimming the suite.

The method that produced this, and the part worth repeating: job start offsets, not job durations.
`gh api "repos/OWNER/REPO/actions/runs/<id>/jobs?per_page=50"` and diff each `started_at` against
the earliest. Durations alone say which leg is slowest; offsets say whether the legs ran at the
same time, and that is what decides whether removing one buys anything. A run's `created_at` versus
its first job's `started_at` is the queue, and it is invisible in every per-job duration table.

Cost of not having done this: a matrix reduction was designed, agreed and nearly justified on
"fewer legs, less time" -- which was false for the stated metric (wall-clock on push) and false for
cost too, since the repository is public and GitHub-hosted minutes are free on it. The reduction is
still right, but for the concurrency reason, and stating the wrong reason would have made the next
person unable to tell whether it had worked.
