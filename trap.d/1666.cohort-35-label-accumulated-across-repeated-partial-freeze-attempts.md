Cutting v0.39.0, `cohort_freeze_record.py --tag v0.39.0 --cohort 35 --execute` reported
`partial` twice in a row, with the two-route disagreement WORSENING between the two
attempts rather than converging (`cutoff_scan=8, label_filter=31` then, 15s later,
`cutoff_scan=8, label_filter=33`) -- not the shape a stale-search-index disagreement
usually takes (those converge toward agreement on a re-run, per every prior cohort-N
entry in the state file).

Investigated by reading the label directly (`gh api repos/.../issues -f state=all -f
labels=cohort-35 --jq '... .number'`): 33 issues genuinely carry the `cohort-35` label,
open and closed. `cutoff_scan` (what is open *right now*) sees only 8 of them. The other
25 are old, closed issues (#383, #581, #583, #1044, #1361, #1516, #1517, #1520, #1521,
#1525, #1549, #1550, #1552, #1553, #1555, #1584, #1585, #1586, #1595, #1611, #1622,
#1625, #1631, #1635, #1636) -- closed issues that still carry the label, which is normal
for a frozen cohort (labels persist through closing, that is the whole shrink mechanism).

The real defect: `cohort-35` was apparently first frozen at the `v0.37.0` tag (state file:
"froze cohort-35 at 18"), then its own freeze DISAGREED again at `v0.37.1` and again at
`v0.38.0` (state file: "cohort-35 freeze count disagreed, re-count needed" at both tags).
A freeze attempt that returns `partial` still WRITES the label to whatever the current
`cutoff_scan` set is before discovering the two routes disagree (`cohort_freeze_record.py`
runs the label write, then reads back `label_filter`, then compares) -- so three separate
partial attempts across three different tags (v0.37.0, v0.37.1, v0.38.0) each applied the
label to whatever issue set was open *at that attempt's own moment*, and none of them
ever got a chance to be the single frozen snapshot the "nothing joins a cohort ever"
invariant assumes. The label has effectively been re-stamped onto three different
successive snapshots of the open board, not one.

This is not a data-loss issue (no cohort membership is lost -- if anything, the label is
over-applied) but it does mean `cohort-35`'s own member count can never usefully answer
"how many issues were open when this cohort was decided", because it was decided (partially)
three separate times. Not fixed here: this release's cohort-freeze step for v0.39.0 is left
at `partial` (recorded in the state file), and the marker in `CLAUDE.md` continues citing
`cohort-34` (the last cohort that DID fully agree), per the citation-order rule.

Possible remedies, not chosen here: (a) accept `cohort-35`'s open-at-freeze-time semantics
have drifted and rename/retire it, freezing a fresh `cohort-36` cleanly at the next release
instead of retrying `cohort-35` again; (b) make `cohort_freeze_record.py`'s label write
conditional on the two routes already agreeing, rather than writing first and discovering
disagreement after -- this would stop a `partial` run from mutating the label set at all,
preserving `cohort-35`'s membership as it stood after its *first* partial attempt.

-- the tag and release were already complete before this was discovered, and cohort freeze
runs strictly after the tag by design). Observed via direct `gh api` reads, not by running
the suite.
