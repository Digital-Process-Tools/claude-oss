While building #1528's fix (dispatch selection no longer drops a candidate whose files overlap the
fleet's held set), the first cut added a per-candidate `overlap` field via a helper, `_overlap_info`,
that took a single `files` argument and returned `None` whenever it was falsy.

That collapses two different facts into the identical output. `overlap_by_number.get(number)` is
`None` for both:

- a candidate genuinely checked against the held set and found disjoint (`lane_overlap` returns
  `[]`, which is falsy), and
- a candidate whose own lane pattern was never derived at all -- no `lane_patterns`, no
  body-declared path, no label mapping (`select_issues.py`'s own "not derivable" posture, #267) --
  so the collision check never ran for it and the key was never set in the dict at all.

Both render as the bare `overlap: None` in the candidate's own JSON. That is precisely the fold
this repository's own three-states rule exists to catch: a check that ran and found nothing, and a
check that never ran, must never share one output.

Caught in review, independently, by both spawns against the same diff -- the `Explore` reviewer and
`oss:auditor` both flagged it without prompting from each other. Confirmed by writing a positive-
control test: `select()` given an issue with no `lane_patterns` at all, against a non-empty
`held_files`, produced `overlap: None` -- the identical shape as a genuinely checked, disjoint
candidate.

The drafted fix (not shipped -- the `overlap` field itself was removed in a later commit on this
same branch, per a mid-lane maintainer scope change: the whole per-issue file-set declaration
apparatus is being removed in #1530, so investing further in a field that would only be deleted
again was declined) distinguished the two by keying on `files is None` rather than `not files`:
`{"state": "not-checked"}` for the missing-key case, `{"state": "checked", "files": [...],
"holders": [...]}` (files possibly empty) for the real check. Worth recording as a shape regardless
of whether `_overlap_info` itself survives anywhere: a helper whose "nothing to report" case is a
falsy check (`not x`) rather than an explicit "was this computed at all" check (`x is None`, or a
sentinel/missing-key check) is the general form of this fold, and it is cheap to get right the first
time and easy to introduce by accident when the "nothing found" and "never asked" cases share a
natural default (`None`, `[]`, `0`).
