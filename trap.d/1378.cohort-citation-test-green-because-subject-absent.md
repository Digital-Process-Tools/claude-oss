`tests/test_cohort_citation_order_1220.py::test_check_repo_on_this_repos_own_claude_md` passes on
every CI leg because the thing it checks is not there, and fails on any maintainer machine that has
it. Both halves were true before and after the v0.31.0 marker rewrite, so this is not a regression --
it is a test that has never actually run where it is green.

Observed 2026-09-09 while running the two marker gates the release process requires before the
release commit:

    AssertionError: assert 'finding' == 'could-not-check'

`check_repo` reads the state file named in `.oss.local.json` (`.max/claude-oss-watch.json`).
`.gitignore:14` excludes `.max/`, so **CI checks out no state file at all**, `check_repo` answers
`could-not-check`, and the test's own `expected` is computed as exactly that. Green, vacuously, on
all twelve pytest legs. On a maintainer machine the file exists, the check runs for real, and the
assertion is against a different answer entirely.

The second half is a separate defect in the same test, and it is what makes the local run red:

    at="2026-09-07T00:00:00Z"

a **wall-clock constant** standing in for "when this citation was written". Any marker citing a
cohort frozen after that date is correctly reported as a finding -- *"cites cohort-27 whose recorded
freeze (2026-09-09T13:18:41Z) had not yet run when this citation was written (2026-09-07)"* -- which
is the check working exactly as designed on an input that lies about the date. Measured both ways:
the pre-edit marker citing cohort-26 (frozen 2026-09-08) gave `finding` at that same pinned instant,
and the post-edit marker citing cohort-27 (frozen 2026-09-09) gives `finding` too. The test was
already red locally; the release just made someone look.

So the test asserts a property -- *this repository's own marker is not checkable* -- that stops being
true the moment the marker gets better, and it is pinned to a date that guarantees the failure grows
staler every release.

What was NOT done, deliberately: the test was not adjusted to make the release commit pass. The
release's actual gate is `cohort_citation_order.py --state ... --at $(date -u +%Y-%m-%dT%H:%M:%SZ)`,
which returned `ok -- cohort-27 was already frozen`, and that is the call the release process
specifies. Tuning a test during the release commit that the release commit needs green is the exact
shape this repository refuses.

Two things a fix has to decide, and neither is obvious enough to do mid-release:

- whether `at` should be derived (the release commit's own timestamp, or `now`) rather than pinned --
  and if so, what the assertion then becomes, since a correct marker at a correct `at` is `ok`, which
  the test currently asserts it must never be;
- whether a test whose subject is gitignored should be exercising the real file at all, or should
  build a state file in `tmp_path` so it runs identically everywhere. The independent-oracle design
  the test's own docstring argues for (#1264) is good and worth keeping through either fix.

Filed alongside `#1378`'s other carry-forward findings rather than as its own issue; this fragment is
the record because it is a test defect found by the release rather than by the audit.
