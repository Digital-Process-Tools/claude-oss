`next_action.py --json` misread the board three times in one `/oss:run` window (2026-09-18),
each time for the same reason: the primary clone's `main` was behind `origin/main`.

- 03:44Z: `release` ranked `could-not-tell`, "local HEAD is 1 commit(s) behind its own upstream
  origin/main, so a range measured from HEAD would predate work already landed there". After a
  rebase the same call ranked `release` as `due`, `merged_prs` 10/10 -- the trigger had fired and
  the first read could not see it.
- 06:47Z: `release` `could-not-tell` again for the same reason, AND `curate` ranked `due` with "19
  fragment(s)" when the curate PR (#1669) had merged eight minutes earlier and `trap.d/` on
  `origin/main` held 5. A `git pull --ff-only` turned both into `not-due`.
- The first case cost a rebase and a re-read; the second would have spawned a second curate pass
  over 14 fragments that no longer existed.

The cause is structural, not an accident. Every merge the loop makes goes through the tracker
(`gh pr merge`, in `oss:tick-merge`), never through the clone, so the clone's `main` is behind
by construction after every tick that merges anything -- which is the ordinary tick. Nothing in
the scheduler procedure (`commands/run.md`) says to fetch before step 2, and `next_action.py`
does not fetch itself. The `release` source at least says `could-not-evaluate` with the reason;
the `curate` source counts `trap.d/` on the working tree and reports a number that is simply
wrong, with no third state to say it might be.

Two possible fixes, not decided here: `next_action.py` runs `git fetch` and measures against
`origin/<default_branch>` rather than `HEAD` for every source that reads the tree; or it reports
`behind-upstream` as its own state, the way `release` already half-does, and refuses to count
`trap.d/` at all in that state. The first is one network call per read; the second keeps the
read pure but makes the scheduler pull before it can proceed. Either way the scheduler procedure
should say which.

Not established: whether `curate`'s count has ever actually spawned a duplicate pass on a stale
tree. Here it was caught by reading the number against what had just merged.
