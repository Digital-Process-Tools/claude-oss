supertool's `read` op returned stale content for `tests/test_lane_setup_claim_worktree_865.py`
during this lane (fix/1069, issue #1069). `read:tests/test_lane_setup_claim_worktree_865.py`
(and windowed reads of the same path) returned a 146-line version of the file with no
`_fake_gh_bin`, no `extra_path` parameter and no `import os` in `_run` -- the version the file
carried before an earlier commit on this same branch (a8e2f0e) rewrote it. `git show
HEAD:tests/test_lane_setup_claim_worktree_865.py`, `md5` of the working file, plain `cat`/`grep`,
and `wc -l` all agreed on the real, current 205-line content with `_fake_gh_bin`/`extra_path`
present. `.oss.json` in the same worktree, read moments earlier via the same `supertool read`,
came back correct and matched disk -- so this was not a wrong-cwd problem across the board, it
was specific to this one path (or possibly a `read`-op cache keyed on relative path that a
sibling worktree/session had populated with an older revision of a file at the identical
relative path -- not confirmed, just the shape that would explain a per-path rather than
per-cwd staleness).

Cost: this would have been a serious misdiagnosis if trusted -- the stale content made it look
like the Windows CI fixture (`gh.cmd`) hadn't been added at all, when it actually had (by a8e2f0e)
and the bug was a level deeper (the fixture existed but `subprocess.run(["gh", ...])` couldn't
find it on Windows because CreateProcess doesn't search PATHEXT for a bare extensionless name).
Caught only because the CI traceback (read via `gh-job:...:raw`) quoted line numbers and code
that did not match what `supertool read` had just shown for the same file, which prompted a
`wc -l`/`grep`/`cat` cross-check.

Not confirmed: whether this is a supertool caching bug, a one-off, or something about how this
particular file was read earlier by a different agent/session sharing some cache. Logging as
observed-once; a curator with visibility across more lanes may know whether this has happened
elsewhere. Possibly worth a "cross-check supertool read output against `wc -l`/git for the one
file a diagnosis hinges on" habit rather than (or in addition to) a supertool-side fix.
