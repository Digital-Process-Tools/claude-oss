Auditor self-review finding on lane #1426 (doctor_check_statusline_unknowns.py's
_refresh_command remedy-quoting fix).

The fix (str(value).replace a literal double-quote with a backslash-escaped one) closes the
reachable case named in the issue -- a bare double-quote in project_dir breaking the
double-quoted shell string -- but is incomplete for two adjacent shapes, both confirmed by
direct shlex.split simulation:

1. A path containing a literal backslash immediately before a literal double-quote (e.g.
   /tmp/foo\"bar) renders with two consecutive backslashes ahead of the quote in the remedy,
   which shlex.split raises "No closing quotation" on.
2. A path with a trailing backslash (e.g. /tmp/foo\) renders with the closing double-quote
   escaped away, also "No closing quotation".

Both are POSIX-only in practice (a literal double-quote is illegal in a real Windows filename,
so the fix's stated reason for rejecting shlex.quote() -- Windows cmd.exe compatibility -- is
unaffected). The new test (test_refresh_command_escapes_a_double_quote_in_project_dir)
exercises only a bare double-quote, not one preceded by an existing backslash or trailing the
string, so its own docstring's claim ("the general form of that check, not just this one
example") slightly overstates what is actually pinned.

_refresh_command's output is never passed to a real subprocess argv in this codebase -- only
printed for a human to copy-paste (channel_cause is its one call site) -- so this is a
misreport (the remedy is presented as valid and for these two path shapes it is not), not an
injection into a live process.

Ranking table row: misreports, non-blocking. A proper fix needs either a documented
backslash-escaping pass (careful: naive doubling changes which characters the printed remedy
contains, worth designing rather than patching reflexively) or a stated, explicit scope
narrowing to "closes the reachable quote-breaking case, not general POSIX shell quoting".
