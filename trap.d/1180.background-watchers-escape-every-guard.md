Four defects in one background watcher, in about four minutes, 2026-09-06. The watcher was a
Monitor polling a GitHub Actions run so a paused sub-manager could be resumed when the run
concluded. Nothing about the task was hard. Every one of the four is a guard that exists in this
repository and did not reach the place I was writing.

**1. The Bash guard does not reach Monitor.** I wrote `gh run view 34054038865 --repo ... --json
status,conclusion`. Ninety minutes earlier in the same session, `gh issue list --repo ... --json
number,labels` had been refused by supertool's `raw_command_guard` with "is replaced by supertool's
`gh-issues` op". The identical class of call, handed to Monitor instead of Bash, ran unchallenged --
`raw_command_guard` hooks Bash only. I did not route around the guard deliberately; I never met it.
A rule enforced on the tool you normally use is unenforced in everything you hand to a background
watcher, and there is no moment at which you are told that.

**2. `2>/dev/null || true` turned a failed read into "not yet".** The loop's `read-failed` branch was
`:` -- a literal no-op -- falling through to `sleep 30`. An expired token, a rate limit or a wrong
run id would have polled silently for twenty minutes and then printed `STILL NOT CONCLUDED after 20
minutes of polling`, which asserts something about the run that was never measured. This is the
defect class at the top of `CLAUDE.md`, written by someone who had been quoting that section to a
maintainer all session.

**3. The match was free text, so `in progress` reported as terminal.** The grep alternation was
`completed|success|failure|cancelled|timed_out` against the whole receipt. supertool's `gh-run`
receipt contains `Status: in progress -- 14 total: 5 passed, 1 failed, 8 pending`. `failed` and
`passed` are in that line, so the watcher fired on the first poll and announced `REACHED A
TERMINAL-LOOKING STATE` for a run that was 8 legs from finishing. `trap.d/1136.content-guards-match-
per-line.md` was already sitting in the queue describing this exact shape. Reading a fragment is not
the same as it firing where you are working -- and the fragment was in `trap.d/`, which nothing
injects, so it could not have fired.

**4. `status` is read-only in zsh.** `st=$(...)` renamed from `status=$(...)` after
`(eval):17: read-only variable: status` killed the script on line 17 before the first poll. This is
the only one of the four that failed loudly, and it is the only one that cost nothing.

The ranking is the point: the three quiet defects each produced a confident, wrong, *plausible*
answer, and the one that crashed produced none. A watcher is a checker, so every rule this
repository has about checkers applies to it -- three states, a positive control, no swallowed errno
-- and none of that occurred to me until the third rewrite, because a watcher does not look like a
checker. It looks like plumbing.

What the corrected version does, for whatever is worth keeping: reads through `./supertool
'gh-run:N'` rather than raw `gh`; distinguishes CONCLUDED / READ FAILED / UNMEASURED after three
consecutive failures / NO Status: LINE (the parse failed, not the run) / NOT CONCLUDED after N
successful reads; matches `^Status:` alone rather than the receipt; and emits a heartbeat every
tenth poll so silence cannot pass for a quiet run.
