extract_references() in scripts/lane_coupling.py can hit an OSError mid-glob-walk (an
unreadable directory, a permissions problem, or a race during a doctor_check_lane_coupling.py
scan). That case is currently indistinguishable from a genuine empty match -- the function's
`problem` return is only ever set for a SyntaxError, which extends a pre-existing silent-failure
convention already present in the same function for the plain-literal is_file() check.

Reachable, not hypothetical: a real permissions problem or filesystem race during a doctor scan
would trigger it and would render as "no reference found" rather than "could not check".

Not fixed as part of #1245 because closing it properly needs a design decision about the
module's own problem/error-reporting contract -- whether an I/O failure becomes a third state
alongside "resolved" and "not resolved" for extract_references, or whether it is folded into the
existing SyntaxError-only `problem` slot with a distinct value. That's broader than #1245's own
scope (which was specifically about widening what shapes _resolve_.
