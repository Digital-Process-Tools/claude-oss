`claude-jit-context`'s own `scripts/rebuild-tsv.sh` and this repo's
`scripts/oss_rules.install()` write the SAME index file in two different shapes, and
running the first one reddens a guard written for the second.

Observed 2026-09-08 during a `/oss:curate` pass. After adding rules under
`.claude/jit-context/{paths,tools,vocabulary}/00-manual/`, I ran the dependency's
rebuild script to regenerate the indexes -- the obvious move, and the right one for
the three `00-manual` layers, which have no generator on this side.

It also rewrote `.claude/jit-context/vocabulary/01-oss/00-index.tsv`, which is an
OWNED file: `oss_rules.install()` is what writes that layer, and
`tests/test_rule_layer_sync_1063.py` compares every committed `01-oss` file against
what `install()` would write. The rebuild script emits a trailing tab on every row
(a third, empty column); `install()` emits two columns and no trailing tab. Every one
of the twelve rows differed by exactly one byte, and the whole file was reported as
drift.

    -state file<TAB>oss-state.md
    +state file<TAB>oss-state.md<TAB>

Cost: one red CI leg on four platforms, on a pull request whose subject was prose,
plus the time to read the failure as "the layer drifted" before seeing it was
whitespace. Fixed with `git checkout main -- <that file>` -- NOT `git checkout --
<file>`, which restores the already-committed drifted version and looks like it did
nothing.

Worth deciding, neither tried: whether the rebuild script should skip a layer that
declares its own generator, or whether `oss_rules.install()` should tolerate the
trailing tab, or whether this is simply "do not run the dependency's rebuild script
in a repo that owns one of its layers" and belongs in prose. Note the guard did its
job exactly right -- it caught a real one-byte divergence in an owned file, which is
what it exists for.
