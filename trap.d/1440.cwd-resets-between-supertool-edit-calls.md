Several supertool `edit`/`paste` calls landed in the MAIN CLONE
(~/Documents/claude-oss, branch main) instead of the worktree
(~/Documents/claude-oss-wt/1440, branch fix/1440), on the #1440 lane.

Observed: the very first Bash call of the lane chained `cd <worktree> && git worktree add ...`,
and the supertool edit call immediately after it (still inside a `cd <worktree> && supertool
'edit:@-' < ...` command) reported `[branch: fix/1440]`. Every subsequent edit call in the
same session that OMITTED an explicit `cd <worktree>` prefix -- reusing the earlier `cd` on the
(false) assumption the shell's working directory persists across Bash tool calls -- silently
landed in the main clone instead, reporting `[branch: main]` in its own validator output. This
ran for roughly ten consecutive edit calls (across six different files) before a routine
`git status --short` in the worktree revealed the files were missing there, and the same check
in the main clone revealed them present and dirty there.

Confirmed cause: this session's own harness note ("Agent threads always have their cwd reset
between bash calls, as a result please only use absolute file paths") is real and applies to
supertool's own resolved root too, not just to relative file arguments passed to other tools.
supertool's op string in these calls (`edit:@-`, `paste:@-`) carries no path at all -- only a
TOML payload on stdin naming a repo-relative `path` field -- so the working directory at the
moment of the call is the ONLY thing that tells supertool which repository root to resolve
that relative path against, and there is no `--root`/`--cwd` flag on the `edit`/`paste`/`git-
commit` ops to make it explicit the way `check_supertool_ops(cwd=project_dir)` and other
scripts in this same repo already do.

Cost: roughly ten calls' worth of edits made in the wrong tree, one `git diff` capture, one
`git apply --check` + `git apply` per stray batch, two `git checkout --` cleanups in the main
clone. No commit was ever made in the wrong tree and nothing was left dirty there at the end,
but it was a close call: a `git add -A && git commit` in the main clone at any point during
that window would have committed unrelated work-in-progress to `main` directly.

Confirmed the recovery mechanism: `git diff -- <files> > patch` in the polluted tree,
`git apply --check` then `git apply` in the correct worktree, `git checkout -- <files>` in the
polluted tree. `git apply` reapplied cleanly every time because the base commit was identical
in both trees (same origin/main ancestor, no divergence).

Not decided here: whether every future `cd <worktree> && supertool ...` invocation in this
family of briefs should be a single always-repeated idiom (the developer brief's own writing
convention already shows every write example this way -- `cd <worktree_root>` before the note,
the report and the pr payload -- but the mid-lane edit/paste calls documented in this same
brief's worked examples, e.g. edit1 through edit12 in this very run's transcript, do NOT all
show the `cd` prefix, which is exactly the gap that produced this incident), and whether
supertool's own `edit`/`paste`/`git-commit` op payloads should accept an explicit root/cwd
field so a caller is never one missing `cd` away from writing into the wrong tree silently.
