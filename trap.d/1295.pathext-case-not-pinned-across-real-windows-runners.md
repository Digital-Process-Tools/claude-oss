PR #1297 (fix/1295) went red on exactly the windows-latest/3.12 CI leg, on a test I wrote
myself: `test_statusline_safe_which_agrees_with_gh_which_on_a_real_directory` asserted byte-exact
string equality between `statusline._safe_which("git")` and `gh_which.safe_which("git", path=...)`
resolving the same real file. On the real runner it failed with `...git.exe` (from statusline)
vs `...git.EXE` (from gh_which) -- both resolving the identical on-disk file.

I read both implementations side by side (scripts/gh_which.py's `_windows_candidate_names` and
scripts/statusline.py's `_win_candidate_names`) and they are logically byte-for-byte identical --
same PATHEXT read, same order, same fallback constant. I could not determine, from code reading
alone (working on macOS, unable to run real Windows), WHY two identical walks over the same real
PATHEXT env var in the same process produced different extension case for the same file. Did not
chase this further -- the fix applied instead was to stop asserting byte-exact case equality and
compare via `os.path.normcase` (what `safe_which`'s own directory de-dup already uses), since
Windows execution does not care about extension case at all (`CreateProcess` resolves `git.exe`
and `git.EXE` identically) -- the property that actually matters is "do the two walks land on the
same file", not "do they spell the extension identically". This is a legitimate, defensible fix
regardless of the underlying mechanism, but the mechanism itself is an open question.

Lesson for next time: a test asserting cross-implementation agreement on a platform this suite
does not run on locally (any test gated to real Windows behavior, not mocked via `_force_windows`)
cannot be red/green verified before it reaches CI. Where the property that actually matters is
weaker than byte-identical output (case-insensitive filesystem paths, whitespace-insensitive
config, etc), assert the weaker property from the start rather than the strongest one that happens
to hold locally -- the strongest one is the one likeliest to be an artifact of the one platform
actually testing it.

Confirmed by: reading the CI failure output verbatim (quoted by the agent that resumed this lane
after PR #1297 went red), reading scripts/gh_which.py and scripts/statusline.py's resolution
functions side by side and finding them logically identical, and reproducing the assertion
divergence with a standalone script comparing `ntpath.normcase` behaviour against the reported
strings (confirms the fix resolves the reported failure shape; does not explain root cause).
