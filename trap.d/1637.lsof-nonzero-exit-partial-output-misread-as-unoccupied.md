Gate-3 release audit (round 1, v0.37.1..HEAD) found: `scripts/worktree_reap.py:164-166` `_lsof_process_cwds` captures `rc` from the `lsof` subprocess and never reads it. Only `exc is not None` (process failed to start) returns `None`; a *non-zero exit with partial output* -- lsof's normal behaviour when it is denied visibility into some processes -- falls through and returns a partial list indistinguishable from a complete one.

Consequence: `worktree_occupant` then returns `False` ("not occupied") instead of `None` ("unknown"), and `plan_reap` sends the tree to `reap()`, which runs `git worktree remove --force` and `git branch -D` -- exactly the case the module's own docstring (lines 34-38) and the function's own docstring (156-158) say must read as UNKNOWN and never be reaped past.

Observed, not reasoned: called `_lsof_process_cwds` directly with an injected runner returning `(rc=1, partial output)`; it returned the partial list, and `worktree_occupant` on a tree in that list still read `False`.

Sibling `_gh_json:204` in the same file checks `rc != 0` correctly -- this reads as an oversight, not a design choice, since the pattern already exists two functions away.

No positive control exists for the real probe: `tests/test_worktree_reap_1628.py` injects `list_processes` throughout, never a real `lsof` non-zero-exit shape.

Blast radius, why this was ranked misreports (non-blocking) rather than destroys: three independent gates still hold before a reap (tracker-MERGED, not-ahead-of-remote, dirt-outside-allowlist), and trap.d/ fragments are harvested first, so no tracked/committed work is lost by this bug alone. The one open question that would flip the ranking: whether a live lane's in-progress notes/reports output (allowlisted, .gitignore'd as disposable) counts as real data when the tree is actually occupied -- a correct reap deletes it too, but the occupied case is precisely the one where it is still being written.

Fix shape: read rc in _lsof_process_cwds and treat non-zero the same way _gh_json already does -- return None (unknown) rather than the partial list, unless the specific lsof error can be shown to always mean "no processes, full stop" rather than "some processes hidden from me".
