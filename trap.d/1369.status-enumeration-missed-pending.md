An `until ! ... | grep -q -E "queued|in_progress"` loop, written to wait on a transient state
disappearing (the correct shape per `waiting-on-a-status-line.md`), still returned early and
reported a conclusion that had not happened.

Observed 2026-09-09 waiting on the default branch's own run after a five-squash merge train:

    until ! gh api "repos/OWNER/REPO/actions/runs?head_sha=SHA" --jq '.workflow_runs[] | .status' \
      | grep -q -E "queued|in_progress"; do sleep 30; done

It exited after one iteration. The output it then printed:

    tests pending null
    Push on main completed success

GitHub's `workflow_runs[].status` returned **`pending`** -- a value the alternation did not name.
`waiting-on-a-status-line.md` already says wait on the transient disappearing rather than the
terminal appearing, and this loop DID do that; what it got wrong is one layer down. The transient
set was written as an enumeration of the transient values, and an enumeration that does not cover
a value renders that value as "not transient", which is the terminal arm. `pending` is neither
`queued` nor `in_progress`, so a run that had not started reading as concluded.

The fix used was to invert which side is enumerated -- the TERMINAL set has exactly one member and
is a closed set, while the transient set is whatever GitHub adds next:

    until ! ... | grep -q -v -E "^completed$"; do sleep 30; done

That is: keep waiting while any run's status is not exactly `completed`. Anchored, so a future
status containing the substring `completed` does not satisfy it either.

Cost: one false "green" report about the default branch, caught only because the loop printed the
run rows it had just decided were finished and `pending` was visible in them. Had the loop printed
nothing, or printed only a summary, the report would have stood.

Possibly this belongs as an addition to `waiting-on-a-status-line.md` rather than its own rule --
it is the same trap one level down, and that file's own example uses the enumerate-the-transient
shape (`grep -q "pending"`), which is correct for the tool it names and wrong here.

**Second failure in the same loop, one minute later, and it is the more embarrassing half.** The
fix above -- inverting which side is enumerated -- was written as:

    until ! ... | grep -q -v -E "^completed$"; do sleep 30; done

That exits immediately without sleeping once. `until ! X` runs its body while `X` is FALSE;
inverting the grep from "find a transient" to "find a not-completed" inverted the predicate, so the
`!` that was correct for the first form is now a second inversion. The condition reads: keep going
while there is NO incomplete run -- exactly backwards. Correct:

    while ... | grep -q -v -E "^completed$"; do sleep 30; done

So the loop reported the identical false conclusion twice, for two entirely different reasons, and
both times exited 0. `waiting-on-a-status-line.md`'s advice ("wait on a transient state
disappearing") is about which PREDICATE to write; it says nothing about keeping `until`/`while`
consistent with it, and changing the predicate without changing the keyword is the natural next
mistake. Worth naming beside it: **when you invert the grep, invert the keyword.**

Both times, the only reason it was caught is that the command printed the run rows after the loop
and `pending` was visible in them. A loop that printed only a verdict would have been believed.

**Third failure, same loop, third distinct cause -- and this one is the defect class this repository
is named after.** After fixing the enumeration and then fixing the inverted keyword, the loop

    while gh api "...runs?head_sha=SHA" --jq '.workflow_runs[] | .status' \
      | grep -q -v -E "^completed$"; do sleep 30; done

still exited while `tests` was demonstrably still running (`gh-branch:main` said so in the same
minute). The remaining hole: **if `gh api` produces no output at all -- an error, a rate limit, a
transient network failure -- `grep` selects nothing and exits 1, the `while` condition is false, and
the loop reports every run finished.** A probe that could not look and a probe that looked and found
nothing incomplete are the same exit status. Three attempts at one wait loop, three different ways to
render "I could not tell" as "it is done".

The lesson is not a fourth patch to the loop. It is that a shell pipeline's exit status cannot carry
three states, so a wait built from `cmd | grep -q` has nowhere to put "the ask failed" and will
always fold it into one of the other two. Use something that has its own exit status for the thing
you are actually waiting on -- here, `gh run watch <run-id> --exit-status` -- or capture the ask's
own status separately before interpreting its output at all.

`waiting-on-a-status-line.md` covers the predicate. This is one layer under it, and all three
failures were only ever caught because the command printed the rows afterwards.
