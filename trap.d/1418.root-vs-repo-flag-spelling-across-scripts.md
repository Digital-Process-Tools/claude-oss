Trying every new script by hand on 2026-09-11, the same argument arrived under two flags
depending on which script was being called.

    python3 scripts/next_action.py --root .           works
    python3 scripts/triage_trigger.py --root .        error: unrecognized arguments: --root .
    python3 scripts/triage_trigger.py --repo .        works
    python3 scripts/cohort_freeze_record.py --repo .  works
    python3 scripts/statusline.py --refresh --root .  works

Same concept -- the repository the script acts on -- spelled `--root` in some scripts and
`--repo` in others. Each script is internally consistent and its own `--help` is correct,
so nothing is wrong in any one file. The cost is one refused call per script the first time
it is used, paid by whoever is driving them from a command file or by hand.

Cost this time: two round trips, and it was noticed only because every script was being
exercised in one sitting. A sub-manager calling one of these from a phase file's table
cell pays the same refusal mid-tick, with less context to read it in.

Not a proposal to rename anything -- a rename touches every caller and every table cell,
and the parity guards in this repository exist because a renamed flag with one stale
mention is how the last three "runnable cell" defects started. Possibly the right fix is
each script accepting both spellings, which costs one `add_argument` alias and breaks no
caller. Left to /oss:curate to decide whether it is a rule or a rename.

Adjacent, found in the same pass: `next_action.py --record-skip` and `--take` have no
`--state-file` override, so the write path cannot be pointed at a scratch state to test
it. Every other script that touches the state file takes the path explicitly
(`triage_trigger.py --state-file`, `cohort_freeze_record.py --state`). The read path was
verified pure by hashing the real state file before and after two calls; the write path
went unexercised rather than exercised against the live file.
