# Probing whether a jit rule fires: the payload must be a *valid* supertool op form

**Observed:** driving `pre-path-hook.sh` with
`{"tool_name":"Bash","tool_input":{"command":"supertool 'paste:trap.d/904.x.md'"}}` reported
`(silent)` for a rule whose `match:` was correct — and reported `(silent)` for
`changelog.d/904.changed.md` too, which has a known-good rule that had already fired several times
in the same session.

**What it cost:** about two minutes, and it would have cost a wrong conclusion: the first reading
looked like "my new rule does not fire" and the honest reading was "my probe does not probe".

**How it was confirmed:** the same three paths with `read:<path>` instead of `paste:<path>` fired
correctly — `trap-fragments.md`, `changelog-fragments.md`, and silence for `docs/autonomy.md`. The
real write op is `paste:::PATH:::CONTENT`, so `paste:PATH` is not a form any path can be extracted
from.

**The shape, which is the reason this is worth a line at all:** a probe that produces no output and
a probe that was never understood by the thing it is probing look identical, and the first thing
this repository says about itself is that those two must never render the same. **Always include a
known-good control in the probe batch** — a rule you have already seen fire. Mine was in the batch
by luck, not by design, and it is the only reason the false reading was caught in two minutes rather
than by editing a correct rule until it "worked".

**Unjudged:** possibly this belongs in the jit-context plugin's own vocabulary skill, which is where
"prove it fires" is documented, rather than as a rule in this repository.
