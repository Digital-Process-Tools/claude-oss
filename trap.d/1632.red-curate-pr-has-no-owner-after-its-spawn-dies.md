# A red curate pull request has no owner once its spawn dies

A curate pull request that goes CI-red has nobody assigned to fix it, and the gap opened when the
`^curate/` never-auto-merge gate came off in #1602/#1604.

Observed 2026-09-16 in a `/oss:run` window. `/oss:run` step 2 ranked `curate` due (trap.d at 16
fragments, threshold 15), the `oss:scheduler-step` spawn drained all 16 into PR #1632, reported,
and died -- which is correct, and `commands/run.md` says plainly that "a pull request a step just
opened is not this session's to wait on (#1549)". Six minutes later #1632 went red on one leg
(`tests/test_rule_layer_sync_1063.py`: the curate pass's own `rebuild-tsv.sh` had rewritten
`.claude/jit-context/vocabulary/01-oss/00-index.tsv`, a generated layer owned by
`scripts/oss_rules.py`'s `install()`, filling `generic` into four verdict columns that #1372
requires to stay empty).

Nothing in the loop was positioned to notice. The curate spawn was gone. The live sub-manager's
`oss:tick-review` is spawned "with exactly its number(s)" from that tick's own dispatch, so a
pull request opened by a different spawn is outside what it reads. The scheduler is told not to
wait on it. Before #1602 the same PR would have sat waiting for a human anyway, so the gap was
invisible; now the loop is expected to merge it on green and nothing owns it when it is not green.

What the scheduler did instead, and it worked: read the failing leg (`gh-pr:1632:status`, then
`gh-job:ID:fail`), spawned a throwaway `oss:scheduler-step` with the quoted failure and an
explicit "confirm this diagnosis by reading, do not assume" instruction, and merged on the
re-run's green. Cost was ~64k subagent tokens for the repair plus two cheap reads in the
scheduler. What is not established is whether the scheduler should be doing that at all, or
whether curate's own PR belongs in the next tick's review set -- the second would keep the
scheduler flat, which is the whole point of #1414.

Also worth pinning: the repair agent was told to work "in the existing clone (do not create a
worktree)" and left the clone checked out on `curate/20260916T194721Z` after pushing. That
blocked `gh-pr-merge`'s own cleanup (`cannot delete branch used by worktree at ...`) and left the
clone on a merged branch, where any later session reading the tree would have been reading the
wrong ref. A repair spawn that touches a branch needs "return the clone to the default branch
when you are done" in its brief, or it needs a worktree after all.
