# `_supertool_tree_identity_confirmed` renders "could not tell" as "not supertool"

Found by the v0.33.0 release audit, gate 3 round 2 (dispatch token `gate3-r2-fcf88543b7a6`),
ranked `misreports` -- can ship behind this fragment, and did.

`scripts/doctor.py`'s `_supertool_tree_identity_confirmed` (added by #1459 / `60f1a4c`) returns the
same `False` for every inconclusive input -- no installed `supertool` dependency in the plugin cache,
`git` off PATH, no readable `origin`, an unrecognised remote form -- as it does for "this tree's
origin is genuinely some other repository". Declining is the right direction for the `executes`
question the function exists to answer, and nothing here argues with that.

What the caller loses: `supertool_invocation` renders both as `'not a supertool checkout'`, and
`supertool_entry_point` collapses a real supertool checkout to a non-`own-tree` state whose remedy
was written for a different situation. Inside a genuine supertool worktree with the dependency
absent from the cache, `lane_setup.read_board` silently falls back to the bare `supertool` name and
the #1409 wrong-tree receipt that `43785ca` fixed comes back with no trace of why.

`_origin_slug` already returns a reason string; the new function discards it (`slug, _reason = ...`).
The fact that settles it: whether `detail` should carry the decline reason (`own-tree declined:
<reason>`) so a diagnostic and a board read can tell "not supertool" from "could not confirm". Same
defect class as the top of `CLAUDE.md` -- an absence produced by the tool, read as an absence in the
world -- one function down from the fix that introduced it.
