# Fifty-one worktrees accumulate because every reap gate correctly declines

Read at the close of a `/oss:run` window on 2026-09-17: `git-worktrees` over the configured
`worktree_root` reports **51 trees**. Nearly all are `[merged, ...]` with `no open PR` -- their
work shipped long ago. They are still there because each individual decline was right.

Two shapes, and neither is a bug on its own:

- `[merged, clean]` trees (e.g. `fix/1389`, `fix/1426`, `fix/1428`, `fix/1435`, `fix/1595`) sit
  idle with nothing uncommitted. These are reapable and nothing reaped them: a tick only looks at
  the worktree it just merged, and at that moment the tree is inside its 15-minute activity window,
  so it declines. Nothing ever looks again. The tick that could reap it cheaply is the one tick
  structurally unable to, and no later tick has a reason to walk the whole root.
- `[merged, dirty: N]` trees (e.g. `fix/1044`, `fix/1578`, `fix/1583`, `fix/1584`, `fix/1585`,
  `fix/1586`) hold 1-2 uncommitted change records each, which `git-worktrees` describes as work
  that "exists nowhere else, and removing it destroys that work". In practice these are almost
  always the lane's own scratch output -- a `reports/fix-NNNN-*.json`, a `.coverage` file. But
  "almost always" is not a reading, and the op cannot tell scratch from unique work, so it declines
  every one. Correctly: deleting them unexamined is exactly the `destroys` row of the ranking table.

What this costs is not disk. It is that `git-worktrees` is the loop's liveness authority for claim
locking, and it now scans 51 trees and ~464 processes on every call that asks. It also means the
one genuinely interesting signal -- a tree holding work that really does exist nowhere else --
arrives in a list of fifty that do not.

What is missing is a pass that runs when no tick is mid-merge and can afford to look: reap
`[merged, clean]` unconditionally, and for `[merged, dirty]` classify the dirt before deciding --
a tree whose only uncommitted records are its own `reports/` output and coverage artifacts is
not holding unique work in any sense that matters, and saying so is a reading, not an assumption.
The existing per-tick gate should stay exactly as conservative as it is; this would be a separate
sweep, not a loosening of that gate.

Not attempted here. Force-removing 51 trees unexamined at the end of an unattended run is the
single most destructive thing this session could have done, and the gate declining them is the
mechanism working.
