Three scheduler sessions can be ticking the same clone at once, and nothing in the loop notices.

Observed 2026-09-08/09 from a scheduler session in this repo. A tick's sub-manager went to do routine
git-log reading in the shared main clone (a per-machine path under the maintainer's home directory)
and found it already checked out to a branch it had never created, chore/curate-trap-d-1319. It ran `ps aux` and
found two other live `claude /oss:tick` processes sharing that same clone. The scheduler confirmed
this independently with `ps -eo pid,lstart,etime,command | grep oss:tick`:

    43498  Tue Sep  8 18:01:17 2026     06:47:09  claude /oss:tick --dangerously-load-development-channels server:oss-channel
     5088  Mon Sep  7 00:16:26 2026  02-00:32:00  claude /oss:tick --dangerously-load-development-channels server:oss-channel

One of those had been running for two days. PR #1331 (1732 lines, 50 trap.d fragments curated into 7
rules) belonged to one of them, sat green and unmerged for 38 minutes, and was invisible to the tick
that could see it on the board -- it read as a stalled lane with no owner, which is exactly the shape
#814 records for stranded lane branches.

What went right, and is worth keeping: the sub-manager refused to guess at ownership. It did not merge
the green PR, did not touch that branch, and did all its own git work from a separate worktree
(claude-oss-wt/1307). It said plainly that it could not tell whether #1331 was live or orphaned. That
refusal is the correct behaviour and it cost nothing.

What is missing: nothing in the loop can distinguish a lane branch abandoned by a dead session from
one actively held by a live one. The board renders them identically -- an open PR with no recent
activity. Every rule this repo has about lane ownership (claim the issue, release the lane, reap the
worktree) assumes one scheduler per clone, and that assumption is neither stated nor checked anywhere.
A second scheduler's merge into a shared clone can also move HEAD under a running tick between its
read and its write, which is the #1007 race with a different cause.

Cheap things that would have helped, none implemented: a scheduler recording its own pid in the state
file at startup so a tick can enumerate live siblings; step 1 of a tick checking whether the shared
clone's HEAD is on a branch this session did not create; `doctor` reporting the count of live
`claude /oss:tick` processes against this clone, with the three-state answer this repo insists on
(one / several / could-not-tell).
