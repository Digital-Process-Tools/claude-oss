# 57 merged branches accumulated on the forge and no diagnostic ever mentioned them

**Observed:** `git branch -r` listed 58 `origin/fix/*` refs. Asking the tracker for each one's PR
state returned **57 MERGED, 1 OPEN** — so 57 branches whose work had shipped were still on the
forge, some of them months old by issue number (`fix/210` through `fix/900`).

`python3 scripts/doctor.py --root .` runs about 50 checks. **None of them is about refs on the
forge.** The nearest two, `worktree_root` and `clone HEAD`, are local-only. The count was noticed by
a maintainer asking out loud, not by anything that runs.

**What it cost:** nothing yet — merged branches are harmless and recoverable from
`refs/pull/N/head`. The cost is the shape, not this instance.

**How it was confirmed:** classified all 58 against `gh pr list --state all` by head ref; deleted
the 57 MERGED-only ones via the refs API (56 succeeded, 1 was already gone — the merge op's own
cleanup had removed it minutes earlier).

**Not a cleanup failure.** `gh-pr-merge:...|cleanup` deletes the remote branch at merge and did so
for all four PRs merged today. These 57 predate that, or came from merges where cleanup was
`refused` — and the refusal is correct behaviour, printed and visible at the time. The defect is
what happens **after** one leaks: nothing ever looks again, so the set only grows, monotonically,
with no reporter.

**The shape, which is the reusable part:** a quantity that drifts in one direction with no detector.
The same session found two others — a trap queue that would accumulate unread (now reported by
`doctor` in three states) and a status-line marker that could never read green (#914). A count
nobody reports and a count that is zero look identical, and the only difference is how long it takes
somebody to ask.

**Unjudged, and there are two live questions:**

1. Whether this is a `doctor` check or a jit rule at all. A check would need a real third state —
   an unauthenticated `gh`, a rate limit or an offline machine must report `could-not-read`, never
   `none stale`, or it reproduces the defect it was built to find.
2. Whether "merged branch still on the forge" is even worth reporting. It is not a fault; some
   projects keep them deliberately. The finding here may be narrower than it looks: *this*
   repository's own merge op deletes them, so a leftover means a cleanup that was refused and never
   revisited — which is a different, sharper thing to report than "you have branches".
