# setup.md's state_file migration paragraph is a fifth unattended-ask site #1477 did not name

Fixing #1477 (setup.md's interactive stops under an unattended /oss:run) turned up a
third genuine "ask" site the issue and my own recon did not name: `commands/run/setup.md`
lines 72-86 (the "If a file already stands where `state_file` points, read it before the
first tick... Ask instead, and if the answer is yes, run the conversion" paragraph, for
migrating a legacy pre-plugin state file into the shape `/oss:tick` expects).

This site is reached the same way the four #1477 sites are -- unattended, through
agents/scheduler-step.md, with nobody typing /oss:setup by hand -- and has the same shape:
an "ask" with nobody present to answer it. Unlike the harness-permission site (kept as an
ask because it writes into an untracked, never-diffed file with no later review point),
this one writes into `state_file`, a path outside `.oss.json` itself but still local/
untracked, so the "does a later review exist" argument that resolved the other two sites
needs its own answer here -- it isn't obviously the same as either resolved case.

Confirmed by oss:auditor during #1477's self-review (2026-09-16), reading the diff at
commit bc8a08ed against commands/run/setup.md's pre-diff blob: the same four "ask"
imperatives named in #1477 exist pre-diff at lines 75/122/130/214-215, plus this fifth one
at 72-86 that neither the issue nor my recon called out. Ranked non-blocking (`misreports`)
against skills/manager/phases/findings.md's own table, since it is the same class of fix as
the two sites #1477 already resolved, one file, one paragraph.

Not fixed in #1477 itself: the issue named four sites, this is a fifth, out of that diff's
own declared scope, and the safe-unattended-default for "was there a legacy state file and
did the human want it migrated" is not obviously "assume no" without checking whether
oss_state.py --migrate has a safe unattended fallback of its own.
