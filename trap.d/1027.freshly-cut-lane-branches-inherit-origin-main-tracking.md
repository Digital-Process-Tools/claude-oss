`git-push` on a freshly dispatched lane's branch needed `:set-upstream` in 3 of 3 cases this
tick (fix/1014, fix/1015, fix/1017) -- a plain `supertool 'git-push'` refused twice with "upstream is
origin/main, a different branch" and once (fix/1015) had no upstream configured at all.

Cause, reasoned not confirmed: `lane_setup.py` resolves each lane's base as `origin/main` (a
remote-tracking ref), and `git worktree add -b <branch> <path> <base>` -- run by the dispatched
developer as its own setup step -- inherits tracking from a remote-tracking start-point by default
(`branch.autoSetupMerge`). The new branch ends up tracking `origin/main`, not itself, even though it
was never meant to push there.

Cost: one refused push + a retry per lane (3 extra round-trips this tick). Cheap once you know the
shape (`git-push:set-upstream` retargets it in one call), expensive to rediscover cold each time.

Worth checking before generalising: whether adding `--no-track` to the `git worktree add -b`
invocation named in the developer's own setup step (or in `lane_setup.py`'s own guidance) removes
the inherited tracking at the source, versus leaving the fix at push time as it stands today.
