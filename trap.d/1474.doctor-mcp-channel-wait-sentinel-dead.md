Release audit (gate 3, round 1, v0.34.0 candidate, dispatch token gate3-r1-0c628bb6fc093764)
found: the WAIT-vs-WARN split in scripts/doctor_check_mcp_channel_connection.py:339-361 (added by
#1448/e08c311) is keyed on the env sentinel OSS_WORKSPACE_MCP_LIST_CHECKED, whose only writer in
bin/oss-workspace was removed by #1474/0731470 as a "dead relay, never read by anything else" --
which was already false at that commit for this reader.

At HEAD, `grep -rn OSS_WORKSPACE_MCP_LIST_CHECKED` finds no writer outside tests/. The condition
`env_.get("OSS_WORKSPACE_MCP_LIST_CHECKED") != "1"` is therefore always true, so the branch always
reports WAIT ("...this session was not opened through bin/oss-workspace...") and the WARN arm (the
real-gap case: something that should have bound the socket did not) is unreachable. WAIT does not
count in doctor.py's verdict arithmetic (only FAIL/WARN/NOTICE are summed), so this renders as
VERDICT: ok with no observable trace anywhere, including statusline.py's `dr` marker.

Both guarding tests are green and neither catches it: test_workspace_dead_relays_1432.py asserts the
export is never set (true, and the point of #1474); test_doctor_channel_connection_1361.py injects
the sentinel directly (LAUNCHED = {"OSS_WORKSPACE_MCP_LIST_CHECKED": "1"}) rather than going through
the real launcher, so it never notices nothing sets it in practice. The defect is in the join of the
two PRs, not in either one alone.

Ranked `misreports`, non-blocking (findings.md's table) -- did not stop the v0.34.0 tag.

Settling fact for whoever picks this up: name any process reachable by /oss:run step 1's doctor.sh
that still sets OSS_WORKSPACE_MCP_LIST_CHECKED=1. If none exists, the WAIT branch needs either a
different launched-session signal or removal.
