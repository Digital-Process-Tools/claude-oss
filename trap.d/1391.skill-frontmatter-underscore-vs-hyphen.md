Working #1391 (delist skills/manager/SKILL.md from the slash picker by flipping
`user_invocable` to `false`), the coordinator caught a defect the developer lane's own
self-review (two spawned reviewers, two rounds, tree-mutation checked) missed entirely: the
key was spelled with an underscore, `user_invocable`, and Claude Code's documented skill
frontmatter field is `user-invocable`, with a hyphen. An unrecognised frontmatter key is
silently ignored, so the pre-existing `user_invocable: true` had never been read by the
harness either -- the skill appeared in the `/` picker because appearing is the default for
a skill with no recognised visibility key, not because the file asked for it. Flipping the
same misspelled key to `false` left the picker listing exactly as it was: a change that read
as correct (frontmatter edited, byte count moved, budget tables updated, a test written and
shown red-then-green) and did nothing at all to the behaviour the issue was about.

What made this hard to catch from inside the lane: the red/green test transition was real --
`tests/test_manager_not_user_invocable_1391.py` genuinely failed when the frontmatter said
`true` and passed when it said `false` -- but it was pinning the file's own text, not the
harness's behaviour. A test asserting "this frontmatter key equals this value" proves nothing
about "the harness reads this key" unless something independently establishes that the key
name is the one the harness recognises. Grepping this repo's own installed plugin cache
(`~/.claude/plugins/cache/`) for every other instance of `user_invocable` only proved this
repo was internally consistent about the wrong spelling everywhere, never that the spelling
was right.

The general shape: **a frontmatter/config key with a silently-ignored-on-typo failure mode
is unverifiable from source alone.** Nothing in this repository's own tooling parses or
validates skill/agent/command frontmatter against the harness's actual recognised key set --
`markdownlint` and `gitleaks` (the validators supertool's `edit`/`paste` run) do not know
YAML schema, and there is no `test_content_invariants.py`-style guard checking frontmatter
keys against a documented allow-list. Before trusting a frontmatter key does anything, check
it against the harness's own documentation (https://code.claude.com/docs/en/skills for skill
keys), not just against the file's own history or other files' apparent agreement with it.

Swept this repo's whole `agents/*.md`, `commands/*.md` and `skills/**/*.md` frontmatter block
set for any other key spelled with an underscore where a hyphenated form might be the
documented one -- `commands/*.md` all use `allowed-tools` (correct), `agents/*.md` all use
`name`/`description`/`model`/`color`/`tools` (no hyphen/underscore ambiguity in any of those),
and `skills/manager/SKILL.md` was the only skill file in the repo and the only offender. No
second instance found at filing time; worth re-checking if a new agent, command or skill file
is ever added.
