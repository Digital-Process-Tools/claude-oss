Writing "does not close #N" in a pull request body closes #N.

Observed 2026-09-05, merging PR #1076 into main as 06c85e2. The body carried a section headed
"What this does not do", whose first line was, in full: "**It does not close #1075.**" The
merge output then reported:

    ## Linked issues
      #1075: CLOSED

GitHub's linked-issue parser matches a closing keyword followed by an issue reference anywhere in
the body. It has no notion of the surrounding sentence, so `not close #1075` contains
`close #1075` and closes it. The paragraph written specifically to say the issue stays open is
what closed it, and the merge output reported the closure as a normal successful outcome rather
than as anything to check.

`gh-pr-create` did not catch it either, and could not have: the payload set `no_close: true`,
which is the op's own switch for "this pull request closes nothing", and the op's create output
still printed `Linked issues (parsed from the body you just submitted) Issue: #1075` with the
note that it is "verified again at merge time by gh-pr-merge". Both readings were correct about
what GitHub would do; nothing compared them against what the body was trying to say, because
nothing can -- the intent lives in a sentence and the mechanism lives in a regex.

This is the same shape as trap.d/1066.grep-negation-contains-its-own-positive.md, merged an hour
earlier as #1072, where a poller matching `ALL GREEN` exited on `NOT ALL GREEN`. A negation
that contains its own positive as a substring is invisible to any matcher that does not parse the
negation, and the two instances are a week apart in nothing but subject: one a shell `grep`, one
GitHub's own parser. The person who wrote the first fragment wrote the second sentence.

The rule that follows, and it is narrow enough to be worth stating flatly: **never write a closing
keyword next to an issue number you do not want closed, in any form, including a denial.** Say
"#1075 stays open" or "this is not a fix for #1075", never "does not close #1075". The same
applies to "do not fix #N", "does not resolve #N" and every other spelling GitHub accepts.

Cost this time: the merge closed a live issue that was, in the same hour, ruled a precondition for
another one (#1078). Caught by reading the merge output rather than by any check, and reopened
with `gh issue reopen`. Had the merge output been skimmed, an open defect would have been
recorded as delivered, which is the shape this repository is named after arriving from the
opposite direction -- not an absence rendered as a result, but a result rendered from a denial.

Worth weighing for a fix, neither tried: whether `gh-pr-create` could warn when a parsed closing
reference sits within a few words of a negation, which is cheap and catches this exact sentence
shape; or whether `no_close: true` should be treated as a claim to verify against the parsed
references rather than as a flag that merely silences the op's own refusal."
