While implementing #1155/#1096 in a worktree (`<worktree-root>/1155`), a
`supertool 'edit:@-'` call issued WITHOUT a `cd` prefix (I forgot it on that one call, after a
sequence of calls that had all been prefixed) landed its write in the MAIN CLONE
(the main clone, branch `chore/trap-log-1177-1180`, a different lane's
own PR #1202) instead of my own worktree. The op's own receipt footer said so plainly --
`[branch: chore/trap-log-1177-1180]` -- which is how I caught it immediately; had I not read that
line I would have believed the edit landed in my own tree.

This is exactly the environment note "Agent threads always have their cwd reset between bash calls"
in practice, and it is a live instance of the #1096/#1078 class this very lane was assigned to
investigate, except here the cause is fully mundane and fully my own: no `cd` prefix on that one
Bash call, not an unreproducible harness corruption. Confirms the discipline every phase file
already asks for (every Bash call in a worktree lane must `cd <worktree>` itself, never rely on a
prior call's cwd persisting) is not paranoia -- it fired on this very lane within the same session.

Reverted cleanly with `git checkout -- scripts/oss_state.py` in the main clone (the only file
touched, confirmed via `git status --short` immediately after), then redid the edit correctly with
`cd` prefixed. No PR #1202 content was touched or lost.

Takeaway: after ANY supertool write during a worktree lane, read the op's own `[branch: ...]`
footer line before moving on -- it is the cheapest possible confirmation that the write landed on
the branch you meant, and it is printed on every write op regardless of whether you asked for it.
