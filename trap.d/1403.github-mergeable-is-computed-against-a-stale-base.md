GitHub's `mergeable: MERGEABLE / conflicts: no` is a statement about the base the reading
was computed against, not about the base a merge would use now. It goes stale the moment
another pull request lands, and nothing re-renders it before you act on it.

Observed 2026-09-10 merging three lanes in sequence. PR #1403 reported
`mergeable: MERGEABLE | conflicts: no` continuously, including after PR #1402 had already
merged into the default branch. A local `git merge origin/main` in the lane worktree
conflicted immediately, in `CLAUDE.md`.

What the conflict looked like, because the shape is the interesting part:

    <<<<<<< HEAD                     (the lane)
    | accounting.md  | 22,987 B | 23,000 B |   <- stale, the other lane grew it
    | tick-order.md  | 34,816 B | 36,000 B |   <- correct, this lane grew it
    =======                          (origin/main, the other lane)
    | accounting.md  | 23,564 B | 25,900 B |   <- correct
    | tick-order.md  | 34,266 B | 36,000 B |   <- stale
    >>>>>>>

Two adjacent table rows arrive as one hunk, and **neither side is right whole**. Taking
either wholesale silently reverts the other lane's re-baseline into a number matching
neither file on disk -- caught by `tests/test_baseline_matches_disk_1014.py`, which fires
in either direction, but only after the merge has already landed on the default branch.

Cost: nothing, because the merge was tested locally first. Would have cost a red default
branch and a second lane's re-baseline silently undone, otherwise.

The habit that made it cheap: before merging a pull request whose base has moved, run
`git fetch && git merge origin/main` in the lane's own worktree, resolve, run the guards
the change touches, and push the merge commit -- then merge. A real merge, never a rebase
and never a force-push, per this repository's own merge policy.

Possibly this belongs beside the existing `merge-gate` rule rather than as its own; the
existing rule says to read the check tally at leg level but says nothing about the
mergeability field being a different kind of claim with a different staleness.
