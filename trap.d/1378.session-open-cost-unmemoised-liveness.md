Issue #1378's gate 3 round-two audit (v0.31.0) named a sixth finding, re-ranked by the issue author as
`fails-to-preserve` rather than the auditor's own `unranked`: `_drop_dead_plugin_consumers`
introduces a `claude mcp get` call, once per `plugin:`-prefixed name, per census -- and
`channel_consumer_census_state` is called from three places (`doctor.py`'s own `/oss:doctor` run,
`doctor_check_channel_health_agreement.py`, and `bin/oss-workspace`'s own embedded census
heredoc). One `/oss:doctor` run therefore pays for the liveness ask twice in the same process, and
every launcher session-open pays for it again -- inside the exact code path whose surrounding
comment exists specifically to avoid paying for a ~1.3s `claude` binary start twice
(`bin/oss-workspace:1316` already probes the same name for its own arm decision, so a session
opened through the launcher asks about the same plugin-declared consumer three times total across
one open).

This was investigated as part of the #1378/#1359/#1416 lane and deliberately NOT fixed there: the
other five findings in that same audit round were small, independent, single-function
corrections (thread `run`/`which`/`env`, filter by population not name-prefix, wrap a lazy import,
derive a test fixture from an owned set), each testable in isolation. Closing this one properly
means adding a real cache or memoisation layer that all three call sites agree on -- a
cross-cutting change to session-lifetime state, not a point fix to one function -- and bundling it
into the same commit as five point corrections would have made that commit harder to review, not
easier.

Suggested shape for whoever picks this up: a single per-plugin-name liveness cache, keyed for the
lifetime of one `claude mcp list`/`claude mcp get` conversation (this launch's or this doctor run's
own), read by all three call sites rather than three independent asks. `bin/oss-workspace`'s own
`OSS_WORKSPACE_MCP_LIST_OUTPUT` relay is the existing precedent for this shape (one ask, several
readers, same process) -- the plugin-liveness ask needs the identical treatment, but keyed on the
resolved server name rather than on the whole listing, since a caller needs a specific name's
transport status rather than the raw multi-line output.

Not decided here: whether this needs its own jit-context rule, or is simply a fix waiting for
someone to pick it up. Logged rather than filed -- confirmed only by reading the three call sites
directly (`doctor.py`, `doctor_check_channel_health_agreement.py`, `bin/oss-workspace`'s own
census heredoc comment), not measured with a stopwatch.
