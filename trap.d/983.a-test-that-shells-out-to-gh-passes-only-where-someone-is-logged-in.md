Two things worth separating, because the obvious reading is wrong:

- **The code was right.** `select_issues.py` did exactly what its three-state contract says — it could not
  reach the tracker, so it said `could-not-select` rather than inventing a candidate list. Nothing about
  the production path needed fixing.
- **The test was environment-dependent.** It asserted a success path that is only reachable when the
  ambient environment happens to carry credentials, and nothing in the test said so. A reader of the
  green run cannot tell "the selection logic works" from "whoever ran this was logged in".

Fixed by simulating an unauthenticated `gh` and verifying red-then-green under it (`8cefcaa`). A review
spawn then found the identical live-`gh` dependency in a sibling test and fixed that too (`50d8ef0`) —
which is the more useful half: the first instance was found by CI, the second only by looking for more of
the same shape.

Generalisation, if it survives curation: CLAUDE.md already says a green run on your own platform is the
weakest evidence about the platform it was not run on, and names OS and interpreter as the two axes.
**Ambient credentials are a third axis and it is less visible than either**, because it is not a property
of the machine at all — the same laptop passes or fails depending on whether someone ran `gh auth login`
that month. Any test whose subject shells out to `gh`, `git push`, or anything else that can be
authenticated needs the unauthenticated case pinned explicitly, or it is measuring the author's session.
