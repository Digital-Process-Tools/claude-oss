#1405 gave `next_action.py`'s `curate` and `triage` sources a repeat-suppression receipt
(`_route_already_seen`, armed only for the top-ranked candidate as of the fix in this same lane) so
an unresolved backlog does not report `due` identically forever. The new `inbound` source (#1406's
`statusline.inbound_reading`, an open external issue/pull-request count) has no such mechanism, and
`DEFAULT_ORDER` puts it first, so it can occupy rank 1 every single tick indefinitely while an
outside contributor's pull request sits open and unresolved.

Observed by the Explore self-review spawn on the #1405/#1406 diff. Left as a deliberate, documented
scope gap rather than fixed in this lane: unlike curate/triage's threshold-over-a-count signal,
whether an open external issue or pull request still counts as "waiting" is a judgment about
whether the loop already responded to it (inbound_triage.py's own richer PR_OUTCOMES vocabulary --
green-and-mergeable / needs-answer / could-not-tell -- captures this; the coarser
open-and-external-author-association count this diff uses does not). Building a correct
repeat-suppression policy for inbound needs that richer signal composed in first (see the sibling
fragment on inbound_triage.py not being reused), not a second, cruder "have I shown this exact
count before" receipt bolted onto a proxy metric.
