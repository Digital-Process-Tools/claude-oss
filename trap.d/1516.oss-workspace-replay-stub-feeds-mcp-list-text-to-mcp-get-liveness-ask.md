# oss-workspace's CHANNEL_CENSUS relay feeds mcp-list text into an mcp-get liveness ask

Found while implementing #1516 (the plugin-liveness cache), not fixed in that lane -- confirmed
independently by both self-review spawns (Explore and oss:auditor), so this is not a guess.

`bin/oss-workspace`'s `CHANNEL_CENSUS` heredoc defines `_replay(argv, **kwargs)` to relay the
launcher's own already-captured `claude mcp list` output to `doctor.channel_consumer_census_state`'s
`run=` parameter, so the census does not have to shell out to `claude mcp list` a second time. The
stub ignores `argv` entirely and always returns `_list_text` (the `mcp list` output) as `.stdout`,
regardless of what command was actually asked for.

`channel_consumer_census_state` threads the SAME `run=_replay` into `_drop_dead_plugin_consumers`,
which calls `arm_target_liveness(resolved_name, run=run, ...)` in
`scripts/doctor_check_mcp_channel_connection.py`. That function calls
`run([claude_bin, "mcp", "get", name], ...)` and then scans the returned stdout line-by-line for one
starting with `Status:` -- a shape `claude mcp list` output does not produce. So whenever `_list_text`
is set (the ordinary case: any launch where `claude mcp list` itself succeeded), this one code path's
liveness ask gets back mcp-list text instead of a real mcp-get answer, finds no `Status:` line, and
falls through to `could-not-ask`. Per `_drop_dead_plugin_consumers`'s own docstring, only a positively
`failed` answer is ever dropped -- `could-not-ask` keeps the consumer counted. So a genuinely dead
plugin-declared consumer is never dropped by THIS census call site, silently reintroducing the exact
"declared-but-not-live counted as live -> false collision -> oss-channel declines to register -> zero
consumers" failure mode #1361/#1372 exist to prevent.

This predates the #1516 diff -- that diff only added an opt-in `cache` parameter alongside the
existing, unmodified `run`/`liveness` plumbing, and does not introduce or worsen this. Confined to
one of three `channel_consumer_census_state` call sites (the launcher's own embedded census), and
only manifests when a plugin-declared consumer is actually dead while `_list_text` was captured.

The fix is NOT a one-line change: `_replay` needs real per-argv dispatch (branch on
`argv[1:3] == ["mcp", "list"]` vs anything else), and the "anything else" branch needs either a real
subprocess call (defeating half the point of the relay) or its own separate relay of the
`PLUGIN_CHANNEL_PRECHECK` heredoc's own already-computed `arm_target_liveness` answer for the SAME
resolved name (computed a few hundred lines earlier in the same script, at
`_live_state, _live_detail = _live_mod.arm_target_liveness(_resolvable)`, but only relayed onward when
that ask reports `failed` -- discarded otherwise). Either shape touches `bin/oss-workspace`'s own
shell-level positional output parsing, which this repo's own conventions (posix-shell-portability.md,
shell-sources-survey.md) flag as carrying real cross-platform risk with no Windows machine on hand to
verify against -- not something to rush inside an already-large diff for a separate issue.
