Investigating #1428 (a local-only failure in
tests/test_doctor_inprocess.py's config-dependent pairing test), I found a real, populated
`~/.cache/oss-statusline/` on this developer's own machine containing cache files keyed on
several of this test suite's own shared placeholder repos: `owner-name.json`, `owner-repo.json`,
`unknown.json`, plus lockfiles `a-b.lock` and `octocat-Hello-World.lock`. These are the slugs
`statusline.cache_path()` derives from repo strings like `"owner/name"`, `"owner/repo"`,
`"a/b"`, `"octocat/Hello-World"` -- all placeholder values used across many test files in this
suite (`_config()` in test_doctor_inprocess.py, and similarly-shaped helpers elsewhere).

The fix landed for #1428 only isolates `statusline.cache_dir` inside `_quiet_main` (used by
exactly one test). A `grep -rln` for these placeholder repo strings across `tests/*.py` turned
up roughly twenty files that mention one of them without an obvious `cache_dir` /
`XDG_CACHE_HOME` isolation nearby (test_checklist_skew.py, test_config_scope.py,
test_developer_brief_duties.py, test_doctor_check_memory_external_614.py,
test_doctor_clone_head_763.py, test_doctor_check_vanished_worktree_845.py,
test_doctor_install_audit_287.py, test_doctor_mcp_channel_registration_621.py,
test_doctor_statusline_stale_fork_1373.py, test_doctor_watch_declaration_split_623.py,
test_doctor_statusline_unknowns_1311.py, test_doctor_unreadable_dir_third_state_363.py,
test_find_consumer_578.py, test_lane_count_385.py, test_lane_count_472.py,
test_lane_setup_372.py, test_lane_setup_558.py, test_lane_setup_734.py,
test_oss_state_cohort_freeze_407.py, test_oss_state_tick_cost_694.py) -- NOT confirmed to
actually write to the real cache (the grep is over-broad; many likely never touch
`statusline.refresh`/`cache_dir` at all, or already isolate it through a fixture I didn't trace
into), just flagged as candidates. Tracing every one down to a real writer was out of scope for
a single-issue fix (#1428's own blast radius is one file).

If this pollution recurs (a similarly-shaped local-only doctor/statusline test failure on this
or another developer's machine), the fast diagnostic is: `ls -la ~/.cache/oss-statusline/` and
look for a file named after a slugged placeholder repo -- the writer is whichever unstubbed
`_rig`/fixture helper in the suite exercises `statusline.refresh()` (or anything reaching
`cache_dir()`) without overriding `XDG_CACHE_HOME` or monkeypatching `statusline.cache_dir`.
