# A commit answering an audit finding ships unaudited, and the second round found real bugs

Observed on PR #921, 2026-09-03. Three commits, two audit rounds, four findings.

The sequence:

1. `04d5b14` — the change. Audited. **Two findings**: a count silently dropped in
   `oss_state.lane_fill`, and a whole cluster where the new reason word existed in code while every
   prose path a tick reads still enumerated the old three.
2. `1bb17af` — the fix for those two findings. Seven files, code and prose and a change to a guard.
   **Nothing reviewed it.** The audit round had already happened; its subject was the commit that
   existed when it ran.
3. Re-audited only because the scheduler chose to, scoped to `1bb17af` alone. **Two more findings**,
   both real:
   - The Class A fix *moved* the defect rather than closing it. `check_lane` returns `ok` for
     `size == MAX_LANE` before consulting `short_reason` or either count, so a count supplied on a
     full lane still reached neither parameter. Reproduced: `lane_fill` with `{'count': 3,
     'candidates': 5}` and without the count return byte-identical records.
   - The prose fix introduced an ambiguity while cutting bytes to stay under a budget. "A short lane
     names X, Y, Z or W; none is a defect" parses at least as readily as "none of these words is a
     problem" as it does as the intended "naming none of them is the defect". `commands/tick.md`
     kept the unambiguous form, so the drift was one-sided.

So the response to an audit is exactly the kind of commit that most needs one: written under the
pressure of a named defect, often touching more files than the original, and frequently — as here —
constrained by a byte budget that forces rewording of prose nobody re-reads for meaning.

## The general shape

An audit's subject is a diff at an instant. The fix for its findings is a later diff, and no
mechanism makes that one a subject. Whether it gets reviewed depends on whoever is driving deciding
to ask again, which is a judgment made by the same party that wrote the fix, at the moment they most
believe it is finished.

This is not the same as "review everything twice". Most fix commits are one line and re-auditing them
is waste. What made this one worth it was scope: seven files, a guard changed, and prose rewritten
under a byte ceiling. Something like that is worth naming as the trigger rather than a round count.

## Worth noting about the second audit itself

It disclosed, unprompted, that it had created and removed a worktree in the main clone via bare `git`
rather than a supertool op — a write outside its brief, caught by its own `git-worktrees` read and
reversed. It also verified the parity guard by *mutation* (adding a fifth word to `SHORT_REASONS` and
confirming the guard then failed) rather than by reading it, and confirmed the newly documented CLI
form by invoking it rather than by trusting the prose. Those are the checks that distinguish an audit
from a careful read, and they are what found the residual bug.
