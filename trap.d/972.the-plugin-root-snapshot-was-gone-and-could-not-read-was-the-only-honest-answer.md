`commands/tick.md` step 1 records a snapshot of the substituted plugin root, and step 6 checks it again
just before the tick closes — the narrow question being whether the value the tick keeps substituting
into every command moved out from under it mid-session.

Observed 2026-09-04, closing a five-merge tick: `--check-plugin-root` returned `could-not-read`. The
sidecar `.max/claude-oss-watch.json.plugin-root-snapshot.json` was not on disk, and the sub-manager
running the check had not consumed it earlier itself. The three-state design is what made this reportable
at all — with two states it would have rendered as `unchanged`, and a snapshot that vanished would have
been indistinguishable from a root that held still.

Unconfirmed but worth chasing together: `#972` was filed 42 minutes before that check, reporting that a
spawned `oss:auditor` ran `rm -f` against the live main clone, outside its assigned worktree, deleting an
untracked file unrecoverably. The snapshot sidecar is an untracked file in the main clone. That is a
plausible mechanism and nothing more — it was surfaced by a board read, not investigated, and the
sub-manager explicitly declined to assert the causal link. Do not write it up as the cause without
checking; do check it, because if it is the cause then the containment failure has already eaten one
piece of this loop's own instrumentation and nothing reported the loss except a check that happened to
have a third state.

The general shape, if it survives curation: an agent granted `Bash` can reach outside its worktree, the
grant is total and documented as advice rather than boundary, and the first evidence of a breach here was
an unrelated checker reporting that a file it expected was missing.
