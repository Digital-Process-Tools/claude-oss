lane's own session was spawned with, a per-machine path under the maintainer's home directory)
implements `scripts/report_schema.py` version 9, while this repository's own checked-out copy of the
same script implements version 11 -- three versions ahead. Running `report_schema.py` from the
pinned root against the lane's own report (which correctly used `schema_version: 11` and the newer
`plugin_root` field) came back `UNVALIDATABLE` with `unknown key 'plugin_root'`, purely because the

This repository IS the `oss` plugin (confirmed: both `.claude-plugin/plugin.json` files, this repo's
own and the cache's, name the plugin `oss`), so its own checked-out copy of `report_schema.py` is the
authority for validating its own reports, not the pinned cache path -- the same distinction
`skills/manager/phases/tick-order.md` already draws for `doctor.py` resolution (resolved-install vs
pinned-root). A sub-manager that runs `report_schema.py` from `${CLAUDE_PLUGIN_ROOT}` unconditionally,
without checking whether the managed repo is this plugin itself, gets a false UNVALIDATABLE on a
perfectly valid, newer-schema report.

The sub-manager that dispatched this lane hit exactly this and had to re-run the check against
this repository's own checked-out `scripts/report_schema.py` directly to get `ok`. Worth
settling: whether `report_schema.py`'s own call site in `skills/manager/phases/handback.md` should
