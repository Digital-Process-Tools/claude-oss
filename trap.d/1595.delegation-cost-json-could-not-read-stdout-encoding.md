Issue 1595 self-review (oss:auditor pass) found that `scripts/delegation_cost.py`'s `session`
subcommand in `--json` mode prints `result["why"]` (an `OSError` message from `open()`) via a bare
`print(...)`, with no explicit stdout encoding. On Windows, stdout defaults to the console codepage
(typically cp1252), and an `OSError` message that embeds a non-ASCII path component (a user
directory name, etc.) would raise `UnicodeEncodeError` at the `print` call -- after the whole
measurement already ran, so the crash happens on delivery, not on computation.

This is not a new pattern introduced by #1595: `scripts/loop_cost_report.py` (lines ~544-546) does
the identical `print(json.dumps(...))` / `print(render(result))` shape with no stdout-encoding
guard, so the same crash mode already exists there and is unremediated. Fixing it well would mean a
shared stdout-encoding-safety helper (e.g. `sys.stdout.reconfigure(errors="replace")` guarded for
older Pythons, or re-encoding output text before printing) used by every script in this class
(`loop_cost_report.py`, `agent_cost.py`, `delegation_cost.py`, and any future sibling), not a
one-off fix inside `delegation_cost.py` alone -- which is why this was logged rather than fixed
inside the #1595 diff.

Confirmed by reading `agents/developer.md`'s own platform-band guidance (§4, "a character the
console's codepage cannot represent... raises UnicodeEncodeError and kills the process at the
print, after the work that print was reporting already happened") and by grepping
`scripts/loop_cost_report.py` for the same `print(json.dumps(...))` shape.

No live repro was attempted (would need a real Windows console with a non-default codepage and a
transcript path containing a non-ASCII character); this is a reasoned finding from reading the
code and the existing sibling pattern, not an observed crash.
