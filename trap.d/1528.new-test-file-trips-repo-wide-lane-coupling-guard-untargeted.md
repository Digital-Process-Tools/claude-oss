PR #1531 (fix/1528) was pushed green locally -- the lane's own two new test files plus the three
guards named in the developer brief (`test_bare_gh_git_spawn_sweep_1165.py`,
`test_gate_state_consumers_328.py`, `test_unwired_scripts_253.py`) -- and came back red on CI, on
`pytest (ubuntu-latest, 3.9)`, with two real failures:

    doctor_check_lane_coupling: WARN -- tests/test_lane_setup_1528.py statically references files
      in lane-dispatch, lane-prose
    the real-suite span check: unacknowledged spans ['tests/test_lane_setup_1528.py',
      'tests/test_select_issues_1528.py']

Both new test files used a real cross-lane file path (`CLAUDE.md`, lane-prose) as fixture data
inside a file that also imports its own module under test (`lane_setup`/`select_issues`,
lane-dispatch). `doctor_check_lane_coupling.py` and its underlying `lane_coupling.py` statically
scan the WHOLE test tree's own source for literal paths matching two or more declared lanes'
globs -- an entirely separate mechanism from `select_issues.py`'s own held-lane check the lane's
brief was actually about, and a check `lane_setup.py <issue> --lane ... --derive-held` (the guard
list the brief's own file-set derivation names) has no way to surface, because that call answers
"which cross-cutting guard does THIS lane's own file set trip", never "does a NEW test file I am
about to add trip a repo-wide invariant over the whole test tree".

The gap: `scripts/lane_setup.py <issue> --lane <files>` reports guards for the files a lane's own
brief declares it will TOUCH -- it has no way to know a new test file will exist on disk, let alone
what literal strings its own source will contain, until after the file is written. Both failing
guards only run meaningfully once the new file is actually present in a full suite run; a targeted
`pytest tests/test_select_issues_1528.py tests/test_lane_setup_1528.py` plus the three named guards
never executes `test_lane_coupling_allowlist_1244.py`'s own real-suite span check or
`test_doctor_check_lane_coupling_1244.py`, because neither of those test files is in the touched
lane's own declared file set, and neither is discoverable by scanning what a lane's OWN files import
or reference.

Fix applied: replaced the real `CLAUDE.md` / `agents/developer.md` literals in both new test files'
fixture data with synthetic, non-lane-matching strings (`fixtures/example-a.md`,
`held-example.txt`) -- the tests' own subject (a candidate is not dropped on overlap; a receipt's
wording changed) never depended on the fixture path being a real, lane-owned file.

Not confirmed as a general rule (n=1): whether every new test file under `tests/` risks tripping
this class of repo-wide guard, or whether this is specific to a test whose fixture data happens to
reuse a real, well-known cross-lane path (`CLAUDE.md` is lane-prose's own headline example, used
throughout this repo's docs and other tests' worked examples) rather than an obviously synthetic
one. Worth `/oss:curate` weighing whether a developer brief should name "prefer synthetic fixture
paths over real lane-owned ones" as a standing instruction, or whether the real fix belongs one
level up: a lane-setup-side guard/reminder that fires when a NEW test file (not just a touched one)
is about to be written under `tests/`, since that is the population neither the brief's own guard
list nor a targeted run can see coming.
