Issue #1656 added an optional `superseded_by_pr` field to a developer lane's report, and a paragraph
in skills/manager/phases/handback.md instructing the maintainer loop to fold the named pull
request into the *current tick's own review set* -- the same list agents/sub-manager.md hands
`oss:tick-review`.

An oss:auditor spawn reviewing that diff (first round, whose message the mechanical
scripts/review_return.py classifier rejected as `referred-not-stated` over internal "as noted
above"-style cross-references, even though the content was fully stated -- worth a jit-context
note in its own right, since the classifier cannot tell "fully restated but cross-referenced" from
"gestured and lost") found: `agents/tick-review.md` (untouched by #1656) still states its scope as
exclusively "a pull request from this tick's own dispatch" ("Your prompt names exactly the pull
request number(s) open this tick, and nothing else"). A `superseded_by_pr` pull request is by
construction one this tick's own dispatch did NOT open -- it was opened by an earlier lane, in an
earlier tick, via the ordinary handback.md push-and-open procedure, so in the common case it DOES
carry the same report-embedded pr_body/review-section fields skills/manager/phases/review.md's
checklist expects. The auditor's own uncertainty was about the less common case -- a pull request
that predates this loop's own handback format entirely, or one opened by an external contributor --
where `review.findings`/`pr_anchor` could be genuinely absent, and nothing in #1656's new prose (nor
in tick-review.md's own unmodified scope statement) says what oss:tick-review should do then. What a
caller would see in that narrow case: a `REVIEW: reviewed` header with an empty findings line,
indistinguishable from a genuinely clean review of a loop-authored PR.

Ranked `misreports`, non-blocking (the auditor's own ranking). Not fixed in #1656's own diff: it
would mean editing agents/tick-review.md and possibly skills/manager/phases/review.md, both already
tight on their own byte budgets, for a case the auditor itself could not confirm is reachable today
(every observed instance of this pattern -- e.g. the claude-jit-context#407 example the issue itself
cites -- was opened by the same loop machinery and does carry the expected fields). Worth revisiting
if a `superseded_by_pr` value is ever observed pointing at a genuinely foreign-authored pull request.
