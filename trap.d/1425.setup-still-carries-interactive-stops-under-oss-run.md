#1425 fixed `commands/run/curate.md`'s literal "this is an interactive pass with the
maintainer... do not [decide] without the maintainer's word" sentence -- the one that made the
first-ever `/oss:run` end-to-end session stop to ask a question. A grep for that exact sentence
across the rest of `commands/run/` (`setup.md`, `scaffold.md`, `install-audit.md`, `triage.md`,
`changelog.md`) found nothing verbatim, but `setup.md` carries the same *shape* under different
wording, and it is now reached the same way curate is -- through `agents/scheduler-step.md`, spawned
by `/oss:run`'s own scheduler with nobody typing `/oss:setup` by hand.

What was found in `commands/run/setup.md`, read at `fix/1425` against `origin/main`:

- Line ~125-126: "Write the command on `ok`. On anything else, say what happened and let the human
  decide -- a `null` they chose beats a value they did not." (the test-command verification step)
- Line ~130: "Print the derived config and what each value was derived *from*, then ask before
  writing. A config the user has not seen is a set of assumptions nobody reviewed."
- Line ~153: "`--split` ... never runs `git add` -- the project half is meant to be reviewed, so
  committing it stays a human act."
- Line ~214-216: "**Ask the maintainer to add the rule; do not write it for them.** A permission
  grant arranged without asking is the tool deciding on an irreversible action, which is not this
  command's job." (the `gh-pr-merge` harness-permission rule)

None of these is obviously wrong the way curate's sentence was -- committing `.oss.json` and
granting a harness permission rule are plausibly still human acts even inside an autonomous run,
unlike a jit-context rule's promote/merge/decline/defer (which #1425 fixed to go up as a PR the
maintainer reviews after the fact, not before). But that "plausibly still" is exactly the judgment
call #1425's own issue text says belongs to each file's own decision, not to a sweep done as a
rider on this fix. Whether `setup.md` should adopt the same PR-is-the-review pattern (write
`.oss.json` unasked, let the maintainer refuse it in review) or keep asking first (because a wrong
`.oss.json` or a wrong harness-permission grant is a different risk shape than a wrong jit rule) is
undecided here -- logged for `/oss:curate` or a future issue to weigh, not resolved in this diff.
