Self-review of #1462 (pinning the scaffolded changelog workflow's action refs to a commit
SHA) found a real, non-blocking gap the fix does not close: `scripts/scaffold.py`'s
`CHANGELOG_WORKFLOW` template embeds its two `uses:` SHAs as a Python string literal, not as a
real `.github/workflows/*.yml` file in THIS repository. `.github/dependabot.yml`'s
`package-ecosystem: github-actions` watch (confirmed by reading it: `directory: /`) only scans
real workflow YAML files it finds in the repo it is installed into -- it never parses YAML
embedded inside a `.py` source string. So the two SHAs this fix just pinned
(actions/checkout, actions/setup-python) will rot exactly as the fix's own predecessor comment
warned a template SHA would: nothing here bumps them automatically, and every repository
scaffolded after they go stale inherits whatever multi-majors-old commit the plugin happened
to ship with, with no visible warning to either the plugin maintainer or the receiving repo.

This does not make the fix wrong -- a SHA that goes stale over months is still categorically
safer than a moving tag a publisher can repoint on the next release, which was the actual
finding in #1462. It is a genuine follow-up gap though: nothing here re-derives "is the pinned
SHA still the tip of the v7 tag" the way `test_ci_action_pinning_925.py`-style guards do for a
receiving repo's own real workflow file.

Possible shape for a fix, not decided here: a `doctor.py` check (or a small standalone script)
that queries `actions/checkout`'s and `actions/setup-python`'s current tag SHA (network call,
so this would need the same "not applicable in an offline/sandboxed test run" third state every
other network-touching check in this repo carries) and compares it against the SHA embedded in
`scaffold.CHANGELOG_WORKFLOW`, reporting drift rather than silently reusing a stale pin.
