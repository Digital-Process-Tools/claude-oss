Gate 3 round-1 audit for the v0.28.0..HEAD delta found a two-commit composition defect on top
of what trap.d/1295.statusline-vendoring-blocks-shared-safe-which.md already named. Commit
ac55a99 in this same delta adds
tests/test_changelog_1157_overclaim_1170.py::test_gh_which_docstring_the_one_place_claim_is_currently_true,
whose whole purpose is to keep gh_which's docstring claim -- "the one place this repo resolves
an external binary before spawning it" -- honest, by asserting an AST sweep finds zero live
bypasses. Commit b95ae4b, three commits later in the same delta, adds a second, independent
implementation of that same resolution walk in scripts/statusline.py
(`_safe_which`/`_win_candidate_names`/`_WIN_DEFAULT_PATHEXT`) for the vendoring reason the
earlier fragment already explains. Neither commit is wrong alone. Joined: gh_which is no
longer "the one place", the docstring is now false, and the very test written to catch that
going stale cannot fire -- the sweep in tests/test_bare_gh_git_spawn_sweep_1165.py only detects
*unresolved* spawns, and its `_mentions_a_resolver` helper (lines ~146-160) treats any function
containing a call named `*which*` as safe, which is exactly what makes statusline.py's own
`_run` invisible to it.

Fix shape: either a sync test comparing the two resolution walks (same precedent as #570/
tests/test_supertool_rule_sync_577.py), or reword the gh_which docstring and the test that
vouches for it so it stops claiming sole ownership.

Confirmed by: reading gh_which.py's docstring, statusline.py's `_safe_which`, and
test_bare_gh_git_spawn_sweep_1165.py's `_mentions_a_resolver` at HEAD b95ae4b.
