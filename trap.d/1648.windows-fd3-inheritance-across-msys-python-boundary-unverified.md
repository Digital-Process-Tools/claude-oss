# Windows fd-3 inheritance across the MSYS/python.exe boundary is unverified (#1648)

Issue #1648 shipped a progress-streaming mechanism for `bin/oss-workspace`'s
pre-`exec claude` plugin-currency check: the shell does `exec 3>&1` (when `oss_steps`
equals 1) around the `plugin_update.py --print-state` call so a subprocess started
inside the command substitution inherits fd 3 pointing at the real terminal, and
`plugin_update.main()` opens `os.fdopen(3, "w", closefd=False)` to write progress lines
there.

An auditor spawned during this lane's own self-review round (oss:auditor, on commit
61814f9e) raised a reasoned-not-observed concern: `bin/oss-workspace` is `#!/bin/sh`,
tested under both bash and dash per its own header comments, and also documented
elsewhere in the same file as running via Git Bash (MSYS) on Windows CI (see the
dirname-splitting-on-backslash handling a few hundred lines in). Standard Win32
`CreateProcess` semantics only propagate handles explicitly marked inheritable via
`STARTUPINFO`'s std-handle slots (fds 0/1/2) -- MSYS's own fd-passing protocol for a
descriptor beyond that is understood only by other Cygwin/MSYS-aware binaries, not
necessarily by a plain hosted `python.exe` from `actions/setup-python`. If that reasoning
holds, `os.fdopen(3, ...)` would raise `OSError` on Windows and the code degrades safely
(the same `progress=None` path every other caller already takes, covered by
`test_fd_3_not_open_is_the_ordinary_case_and_passes_no_progress`) -- so nothing crashes,
but the streaming half of #1648's fix may be silently inert on Windows specifically,
which is exactly the platform the issue's own timing measurements never covered (they
were taken on macOS).

Neither this diff's own tests nor any pre-existing test spawn a real cross-process fd 3
to settle this either way: `tests/test_plugin_update_progress_fd3_1648.py` deliberately
monkeypatches `os.fdopen` rather than opening a real fd 3 (a real-fd test would be
POSIX-only and skip on Windows for no reason, per that file's own docstring), and
`tests/test_workspace_plugin_progress_1648.py` stands `printf` lines in for what Python
would write and never spawns Python at all. `.github/workflows/tests.yml` does run a
`windows-latest` leg, so Windows is a covered platform generally, but nothing in that
leg exercises this specific fd-3 path.

What would settle it: either a real run of `bin/oss-workspace`'s `plugin` branch on
Windows CI with a working `python_bin`, checking whether streamed lines actually reach
the terminal, or a narrower claim in the commit/changelog text that the streaming half is
confirmed on POSIX only. Ranked `misreports` against `skills/manager/phases/findings.md`'s
table (does not block a release) -- logged here rather than fixed inline, since settling
it needs either Windows CI access this lane does not have, or a scope decision (narrow the
claim) that is small but not this lane's alone to make silently in a fix commit.
