# Three lanes, one issue each, 31 issues open -- and every gate was satisfied

Observed 2026-09-03, on a live tick. The sub-manager dispatched three developer lanes:

| lane | issues carried | files claimed |
| --- | --- | --- |
| `fix/845` | #845 only | `scripts/*`, `skills/manager/phases/*` |
| `fix/699` | #699 only | `scripts/assemble_changelog.py`, `.claude/jit-context/paths/01-oss/changelog-fragments.md` |
| `fix/897` | #897 only | `scripts/oss_config.py` |

Its own account of why: each `lane_setup.py --against` check came back `available` with no overlap
against the other two, so there was "no adjacent same-lane issue to fold in" -- `no-adjacent`, the
declared short-lane reason.

`supertool 'gh-issues:per=100'` at the same moment: **31 open issues, uncapped footer.** Obvious
adjacent candidates were sitting on the board -- #895 and #892 are both the reap-permission wildcard
helper; #896 (`tick_handback`) and #846 (`dispatch_rank`) are both loop scripts under `scripts/`;
#898 (`lane_setup`) sits beside #897 (`oss_config`), which was dispatched alone.

This is the exact state #799 says was wrong -- "the loop picked one issue and then went looking for
companions, so most lanes ended up carrying one" -- reproduced in full, with every gate green.

## The fill step did not run -- as opposed to running and finding nothing

The sub-manager's own account of its check, verbatim: each `lane_setup.py ... --against` came back
`available` with no overlap **against the other two**.

That is the conflict check, pointed at the two other lanes it had already chosen. It is not the
companion search. `dispatch.md` distinguishes the two explicitly, in the paragraph that introduces
`--against` at selection time:

> read the other way from the disjointness rule above: overlap there means conflict, and overlap
> here, at selection time, against a *candidate's* declared lane rather than a running one, means the
> two are worth bundling

Overlap between running lanes means avoid. Overlap between a candidate and the top issue means take.
Same op, opposite meaning, decided entirely by what it is pointed at. This tick pointed it at the
running lanes, got `no overlap`, and wrote `no-adjacent` -- a word that asserts something about the
board, on the strength of a measurement that never looked at the board.

**So board size is irrelevant to this failure.** With 100 open issues the same sequence produces the
same result: pick N primaries, verify they do not collide with each other, report `no-adjacent` N
times. The number of issues never enters the computation. That is the shape to test any fix against.

`dispatch.md` asks for both halves at once -- "one developer per available file-disjoint lane,
**and** each lane's brief carrying" three issues, and it says "on **both**". The first half was
satisfied, and its satisfaction was then allowed to stand as the explanation for the second half's
absence.

**And this is the repository's own defect class, landed on dispatch.** `no-adjacent` has two
readings and one rendering: a companion search that ran across the board and found nothing, and a
companion search that never happened. There is no third state -- no `did-not-search` -- so the
closed set of three words that #773's reasoning made closed on purpose is missing the one state
that would have caught this. `could-not-tell` is documented as "adjacency could not be computed",
which is a failed computation, not an omitted one.

**Rank-then-hunt makes it worse but is not the cause here.** #799 changed the default from one issue
to three and wrote "Fill to three", without changing the selection order: `dispatch_rank.py` still
returns a top *issue*, and companions are then sought adjacent to it, "whatever their own rank".
So even when the search does run, an isolated top-ranked issue pins the lane at one while adjacent
trios sit elsewhere on the board. The loop selects the best issue and hopes it has neighbours; it
never selects the best bundle. That is a real defect and it is second, not first: today the search
did not run at all.

## `no-adjacent` is also unchecked, and #871 already fixed this exact hole one word over #871's
whole finding was that `board-exhausted` was a *shape* refusal -- one of three declared words, never
asked whether it was true -- so a one-issue lane could write it while 35 issues sat open.
`--lane-fill PRIMARY:COUNT:board-exhausted:CANDIDATES` closed that. `scripts/dispatch_rank.py:318`
says in as many words: **"`no-adjacent` and `could-not-tell` are untouched."** So the same lazy
refusal is still available; it just needs a different word. This tick used it three times.

Whether `no-adjacent` is even checkable in the same way is a real question -- `board-exhausted`'s
check counts file-disjoint candidates, which the sweep already produces, while `no-adjacent` would
need an adjacency count against the top issue, which is a different computation. But "harder to
check" is not the same fact as "checked", and today the two render identically.

## Adjacency is a proxy for a saving that does not actually require it

 #799's 16%-per-issue
figure comes from #499, measured across 237 lanes, and the mechanism it names is fixed overhead paid
once regardless of how much the lane carries -- "a turn-1 baseline, an orientation phase, two
self-review spawns, a full suite run". A shared worktree is what buys that. **File adjacency is not
what buys it.** Measured on this same tick (see [[915.developer-floor-dominates-lane-cost]]): each
developer lane's turn-1 floor is 57.8-58.3k tokens, dominated by `agents/developer.md`, and it is
paid per lane, not per issue. Three one-issue lanes paid that floor three times; one three-issue
lane pays it once.

The honest counter-argument, which this fragment is not in a position to settle: #499 measured
*adjacent* bundles. Extending the 16% to non-adjacent issues is an extrapolation, and there is a
mechanism that could eat it -- a lane carrying three unrelated issues accumulates all three file
sets into its working context, so its later turns are more expensive than an adjacent bundle's. The
floor is paid once either way; the accumulated work context is not. Whether the net is still
positive is measurable and has not been measured.

## Why nothing reported it

Every gate passed. `lane_fill` refuses an unreasoned short lane; all three lanes carried a reason.
`dispatch_rank.check_lane` refuses a fourth issue; none had four. `--lane-fill`'s candidate check
fires only on `board-exhausted`. `lane_fill_trend` exists and counts how often the reason is
`could-not-tell` rather than the other two -- so a run of `no-adjacent` reads as the *healthy* end of
that distribution.

Three one-issue lanes with 31 issues open is a defect that renders, at every checkpoint the loop
has, as a correctly-reasoned tick.

## Not decided here

Whether the fix is bundle-first selection, a candidate check on `no-adjacent`, dropping the adjacency
requirement in favour of disjointness-against-other-running-lanes, or first measuring whether a
non-adjacent bundle is actually cheaper. They are not the same change and the last one gates the
third.
