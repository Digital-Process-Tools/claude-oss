# The #1670 curate worktree fix trades a stranded clone for a leaked worktree

Found by a self-review spawn (Explore) reviewing the #1670 fix to `commands/run/curate.md`
(making curate cut and work in its own worktree instead of the primary clone).

The #1670 fix removes one symptom of a still-unfixed root cause: a pull request a step opens has
nobody whose job it is to merge it. `.claude/jit-context/paths/00-manual/run-step-worktree-and-pr-
ownership.md` names this half explicitly and it is untouched by #1670 -- `next_action.py`'s
`inbound` source still filters to outside authors, so a loop-authored curate PR still does not rank
as pending work for any tick to pick up and merge. Related but distinct from
`trap.d/1632.red-curate-pr-has-no-owner-after-its-spawn-dies.md`, which is about a CI-red curate PR
specifically; this is about an ordinary green-but-unmerged one.

Before #1670: an unmerged curate PR left the *primary clone* checked out on `curate/<timestamp>` --
loud and blocking (PR #1575 hit exactly this: `gh-pr-merge` cleanup refused both worktree removal
and branch delete).

After #1670: an unmerged curate PR instead leaves an abandoned worktree directory at
`<worktree_root>/curate-<UTC timestamp>` that nothing in the loop is positioned to reap, since
nothing merges the PR that would make the worktree eligible for `worktree_reap.py`'s
merged-and-clean cleanup gate. Quieter, easier to miss, same root cause.

Not fixed as part of #1670: it needs a design decision (an explicit "wait on and merge what my own
step opened" obligation in `commands/run.md`, or folding step-authored PRs into `next_action.py`'s
own inbound source) that is out of scope for a curate-only worktree-isolation fix and would double
that diff. Left for /oss:curate to decide whether this merges into the existing
`run-step-worktree-and-pr-ownership.md` rule's second half (it already names the PR-ownership gap,
just not this specific new manifestation) or gets its own rule.
