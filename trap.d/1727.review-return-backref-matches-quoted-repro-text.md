# review_return.py's own backref regex fires on quoted repro text, not just prose

While running the self-review's own reviewer final message through `scripts/review_return.py
--framed` (per `agents/developer/review-return.md`, "do not read tone, pipe it through the
classifier"), the Explore reviewer's own message -- which genuinely, fully states both of its two
findings, `FINDINGS: 2` followed by two complete finding blocks with mechanism, severity and
reproduction -- was classified `referred-not-stated` by the tool itself, EXIT 3, quoting
`"As shown above, nothing else touched."` as the decisive back-reference.

That quoted line is not a gesture by the reviewer about its own message. It is literal
reproduction fixture text, inside a fenced code block, inside finding #1's own body -- the
reviewer was quoting one of the two example messages it used to demonstrate the very defect it
found (issue #1727's own subject: `_BACKREF` over-triggering). `_BACKREF`/`_BLOCK` operate on raw
bytes with no awareness of a fenced code block, so a back-reference-shaped phrase quoted as
example/repro content inside an otherwise fully-stated finding reads identically to a genuine
dangling gesture.

This is a new instance of the same class #1727 fixed (a message that legitimately states its
content in full still gets `referred-not-stated`), one level removed: not "the message contains
an incidental phrase describing an already-enumerated finding" (which #1727's fix now shields,
when confined to a block's own span) but "the message quotes example/repro text, inside a code
fence, that happens to contain the back-reference regex's own trigger words." Confirmed by direct
reproduction: classifying the reviewer's verbatim final message (piped through `--framed`) returns
`VERDICT: referred-not-stated`, quoting exactly that line, while the message manifestly,
completely states two real findings I went on to read, verify and fix in full.

Cost: none really -- I had the full verbatim message already (delivered via SubagentHandback, not
merely a transcript I was inferring from), so I could read it directly and confirm both findings
were genuinely present rather than trust the mechanical verdict blindly. But it is exactly the
shape `agents/developer/review-return.md`'s own "do not read tone, pipe it through the classifier"
instruction would otherwise have me treat as lost findings, when they were not lost at all.

Possible direction for whoever curates this: `_BLOCK`/`_BACKREF` could exclude fenced code-block
spans (paired \`\`\` markers) from both the block count and the back-reference search, the same
way `_BLOCK` already excludes indented sub-bullet lines from counting. Not designed here -- this
is a trap, not a fix, and it is #1727's own module, so whether it is worth a fifth hardening round
of the same heuristic (#1270, #1327, and now this) or whether a fenced-code exclusion is the right
shape is a judgement for /oss:curate or a fresh issue, not this lane.
