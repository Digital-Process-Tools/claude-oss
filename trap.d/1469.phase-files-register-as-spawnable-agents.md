Observed 2026-09-14. The maintainer reported seeing "a dev starting another dev" in a live loop
session. The mechanism is that the developer phase files, and the shared audit fragment, are
registered by the harness as SPAWNABLE AGENT TYPES, not merely as documents a lane reads.

From this session's own agent-type listing at session start, verbatim:

    oss:developer:report          (Tools: All tools)
    oss:developer:review          (Tools: All tools)
    oss:developer:review-return   (Tools: All tools)
    oss:audit:shared              (Tools: All tools)

Those four names correspond to `agents/developer/report.md`, `agents/developer/review.md`,
`agents/developer/review-return.md` and `agents/audit/shared.md`. Each of those files begins with a
plain markdown heading and carries no frontmatter at all -- line 1 of `agents/developer/review.md`
is `# Self-review: the two spawns against your own committed diff`. The registry's description for
each is the fallback string "Agent from oss plugin", which is what a registration with no
description frontmatter renders as. So the harness discovers `agents/` RECURSIVELY and registers
every markdown file under it, frontmatter or not.

Three separate consequences, and they do not depend on each other.

1. A lane instructed to READ `agents/developer/review.md` can instead spawn `oss:developer:review`,
   because a name resembling the instruction exists in the registry. That spawn's system prompt is
   the phase file itself, whose own line 10 instructs "spawn two agents against your own committed
   diff, in the same message" -- so the thing that starts behaves like a developer and spawns
   further agents underneath it. This is #1469's defect one layer down: there, a sub-manager read
   `commands/tick.md`, whose first line is a spawn instruction, and spawned a second sub-manager
   under itself. #1469 was fixed by naming that file as the scheduler's own wrapper. Nothing
   equivalent protects the developer phase files, and unlike #1469 the confusable thing here is a
   real registry entry rather than a document that merely looks like one.

2. Each registers with `All tools`. This repository withholds tools deliberately and per agent --
   the triager is denied Edit and Write, the auditor holds only Bash and TodoWrite. A phase file
   spawned as an agent holds everything, including the harness Read/Edit/Write tools that every
   real agent definition here is denied in favour of the supertool route.

3. `tests/test_agent_grant_is_total.py` and `tests/test_agent_definition_budget_491.py` both glob
   `agents/*.md`, non-recursively. CLAUDE.md states that `agents/audit/shared.md` lives one
   directory down specifically to stay off that glob, "the same reason `agents/developer/*.md` sits
   below `agents/` rather than beside it". That reasoning holds for those two tests and is false
   for the harness, which registers recursively. So the move chosen to exempt these files from the
   byte budget also exempted them from the grant guard, while the harness went on treating them as
   agents the whole time. A guard that appears to cover every agent reads a set narrower than the
   set that exists -- this repository's own named defect class.

Not confirmed here: which of the three actually produced the observed spawn, since the maintainer
reported it from the loop session's own display rather than from a transcript. Consequence 1 is the
hypothesis that fits the report; consequences 2 and 3 are established directly from the listing and
from the two tests' own globs, independent of what happened in that session.

Possibly belongs upstream rather than here: whether a frontmatter-less markdown file under an
`agents/` subdirectory SHOULD register as an agent is a harness question, and if the answer is no,
this is a harness bug and the repo-side fix is only a workaround. If the answer is yes, then every
multi-file agent split in this repo needs an explicit non-registration mechanism, and none exists
today -- `user-invocable: false` is a skill key, and the frontmatter spelling trap already recorded
in `.claude/jit-context/paths/00-manual/frontmatter-key-spelling-is-unverifiable-from-source.md`
says not to assume any frontmatter key works without checking the harness documentation.
