On the v0.39.0 release commit `a06c323b`, run #35300101111 (`tests`, event `push`) came back
5 passed / 1 failed. The single failing leg was `pytest (ubuntu-latest, 3.12)`
(job #105460757030):

    E  AssertionError: these test files pin 0.40.0, the next minor release, so they would
       redden the release commit that bumps to it -- and 2 colliding literal(s) were seen
       alongside them, which are not a defect: test_doctor_install_audit_287.py:176,183,199,207,213,
       test_plugin_update_dependencies_605.py:117,143,458,459,490,491
    tests/test_no_test_pins_the_current_version_350.py:792: AssertionError

The finding itself was real and was fixed forward in `0c1de3a4` (the `0.40.0` literals were a
fixture value for an unrelated dependency's version, changed to `8.8.8`).

What is NOT explained is the distribution. Three sibling legs on the same commit --
`pytest (windows-latest, 3.12)`, `pytest (macos-latest, 3.12)` and `pytest (ubuntu-latest, 3.9)` --
all completed 12/12 steps and reported success, against the identical checked-out tree. The guard
in `tests/test_no_test_pins_the_current_version_350.py` reads repository files and compares string
literals against a version derived from the manifest. Nothing in that description is
platform-dependent or interpreter-dependent, so four legs reading the same bytes should return the
same verdict, and they did not.

That means one of two things, and which one matters:

- the three passing legs did not actually run this test (skipped, deselected, or lost to a
  collection or xdist-sharding difference), in which case the guard's coverage is a good deal
  thinner than a green leg suggests and a future real pin could ship on a fully green run; or
- the guard's own inputs differ per platform (a path-separator assumption, a glob that resolves
  differently, a version read that falls back to something else when some tool is absent), in which
  case its verdict is not reproducible and a red leg is partly luck.

Both readings are this repository's own named defect class -- a check that did not run rendering
identically to a check that found nothing -- applied to the guard whose entire job is to protect a
release commit.

Not investigated here: the passing legs' own logs were not opened to see whether the test appears
in their collected set at all, which is the one read that separates the two explanations above.
Cost so far: nothing beyond noticing; the release was already unblocked by the fix-forward.
