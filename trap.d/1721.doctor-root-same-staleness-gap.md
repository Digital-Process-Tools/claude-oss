Fixing #1721 (gate 3's resolved plugin root can be stale) surfaced that the
identical gap exists one directory over and was left untouched, on purpose,
because the issue's own title scoped it to gate 3.

`skills/manager/phases/tick-order.md` (around the `DOCTOR_ROOT` resolution,
roughly lines 71-83) resolves the plugin root for `doctor.py` the exact same
way gate 3 used to resolve `GATE3_ROOT`: `plugin_update.py
--print-resolved-root --root .`, which is built from the version THIS
project has recorded -- not necessarily the newest copy of the plugin
actually cached on the machine. #1721's fix added
`plugin_update.newest_cached_version` / `--print-newest-cached-version` and
`checklist_skew.compare_root_freshness` / `--compare-root-freshness`
specifically to answer that question for gate 3. Neither is wired into
`tick-order.md`'s `DOCTOR_ROOT` resolution, so every ordinary maintainer
tick that runs `doctor.py` against a resolved root still has no way to know
whether that root is stale -- the same silent-luck failure mode #1721's own
incident report describes, just for a lower-stakes caller (doctor annotates;
it does not gate a release).

Confirmed by reading `skills/manager/phases/tick-order.md` directly (an
oss:auditor-adjacent finding from a spawned Explore reviewer during #1721's
own self-review round, cross-checked against the file).

Whether this is worth closing depends on how much a doctor run actually
cares about checklist vintage -- unlike gate 3, `doctor.py` is not auditing
against a checklist version at all, it is running scripted diagnostics, so
the blast radius of a stale `DOCTOR_ROOT` may be smaller than a stale
`GATE3_ROOT`. Left for /oss:curate to weigh rather than decided here.
