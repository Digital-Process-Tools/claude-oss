While implementing #1389/#1390/#1392 (the /oss:run entry point and the launcher surgery that
removes bin/oss-workspace's own prompt-selection and pre-launch setup diagnostic), self-review
(an Explore reviewer spawn and an oss:auditor spawn, both run against the committed diff) found
that four env relays -- OSS_WORKSPACE_MCP_CHECKED, OSS_WORKSPACE_CENSUS_CHECKED,
OSS_WORKSPACE_MCP_LIST_CHECKED, OSS_WORKSPACE_CHANNEL_ARM_TARGET -- now have no reachable
consumer inside bin/oss-workspace, because their one consumer was the launcher's own synchronous
`doctor.sh` invocation, which #1392 deleted (that diagnostic now runs from inside the session,
via /oss:run's own step 1).

The relays are still computed and still unset right before `exec claude` (unchanged behaviour;
only the surrounding comments were corrected to stop claiming a `doctor.sh` call exists "a few
lines below" in this file). #1392's own issue text says explicitly to "keep the env relays; they
hand a computed reading forward rather than replacing a prompt" -- and I did keep the code, but
its *effect* is now dead: nothing downstream ever reads these four variables again, since they are
unset before the session (which is the only remaining place that runs doctor.sh) ever starts.

Whether this is actually a problem is a genuine, open design question, not something I decided
here:

- If the relay is meant to help the session's own /oss:run diagnose step (commands/run.md step 1)
  avoid a redundant `claude mcp list`/`claude mcp get` call the same way it once helped the
  launcher's own synchronous doctor.sh call, then NOT unsetting it before `exec claude` would let
  it flow into the session -- but only for the SESSION'S FIRST doctor.sh call. Every Bash tool
  call in a Claude Code session inherits the `claude` process's own environment (verified: shell
  state does not persist between Bash calls, but the *process env* does, since each call is a
  fresh subprocess of the same `claude` process), so a value exported at launch time would answer
  every LATER `/oss:doctor` run for the rest of the session too -- reproducing exactly the
  reading-taken-once-and-treated-as-fresh-forever defect the existing `unset` calls were written
  to prevent (see the `#629`/`statusline.py` history cited in the surrounding comments).
- If it is not worth the complexity of threading a "first-call-only" consumption rule through
  commands/run.md, the four relays and their `unset` calls could instead be deleted outright now
  that their one real consumer is gone -- fewer moving parts, and the "asking twice" cost they
  guarded against is a few subprocess spawns at session start, not something the codebase has
  otherwise treated as expensive.

I did not implement either direction: the first needs new plumbing in commands/run.md (how would
a shell command inside an agent's own turn *know* it is the session's first doctor.sh call?), and
the second is a deletion decision on infrastructure this lane did not otherwise touch. Confirmed
by direct grep that `scripts/doctor_check_mcp_channel_registration.py` and
`scripts/doctor_check_mcp_channel_connection.py` are the only two places that actually read any
of these four variable names -- `scripts/doctor.py` itself never does.
