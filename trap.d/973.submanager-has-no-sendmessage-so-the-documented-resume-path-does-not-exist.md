The loop documents lane resumption as `SendMessage` to the lane's own agent, and says re-dispatching
fresh at the same issue is a defect unless the agent is genuinely `agent-unreachable`. `commands/tick.md`
step 5 says it (#880), and `skills/manager/phases/dispatch.md` carries the argument and the state names.

A sub-manager cannot do it. `agents/sub-manager.md`'s frontmatter grants `Bash`, `TodoWrite`, `Skill`
and `Agent` — not `SendMessage`. Observed 2026-09-04, mid-tick: a sub-manager needing to send a lane
back for a regression reported it had no `SendMessage` tool available and fell back to a fresh `Agent`
call aimed at the same worktree and branch. It named the gap itself rather than silently re-dispatching,
which is the only reason this was visible at all.

So the documented path is not merely unused, it is unavailable to the one role the instruction is
written for. The fallback works — a fresh agent into the existing worktree does resume the branch — but
it pays a full context re-derivation, which is exactly the cost #880's resume rule exists to avoid, and
it renders identically to the re-dispatch that rule calls a defect. Nothing anywhere reports the
difference.

Note that the scheduler *does* hold `SendMessage`: this same tick used it repeatedly to resume the
sub-manager itself across CI waits, and it worked every time with context intact. The gap is one level
down, between sub-manager and developer lane.

Worth checking before writing a rule around it: whether `SendMessage` can be added to the sub-manager's
grant at all, or whether the prose in `tick.md` and `dispatch.md` should instead name the fresh-Agent
fallback as the sanctioned route for a sub-manager and reserve `SendMessage` for the scheduler. Either
fix is small; leaving both documents describing a tool the role does not have is the thing that costs.
