# `git stash push -u` then `pop` silently un-stages a `git rm`

Observed 2026-09-15 in the #1532 lane, on `fix/1532`.

I needed to know whether two failing doctor tests were my own fallout or
pre-existing, so I ran `git stash push -q -u`, ran them against the base, and
`git stash pop -q`. That answered the question correctly and cheaply -- both
failures were pre-existing and environmental -- and it is a good technique.

What it also did, invisibly: every file I had removed with `git rm` came back
**in the index**. `git status --short` afterwards showed them as ` D` (deleted
in the working tree, still tracked) rather than `D ` (staged deletion).
Eighteen test files and one script.

Nothing failed at the time. It surfaced about 25 minutes later, at the end of a
full suite run, as a single unrelated-looking failure:

    tests/test_git_count_proxy_236.py::test_no_piped_git_log_count_in_...
    E  FileNotFoundError: .../scripts/doctor_check_vanished_worktree.py

That test enumerates governing files with `git ls-files` and reads each one.
`git ls-files` reports the index, so a file deleted from the worktree but
restored to the index is listed and then cannot be opened. The error names the
file, not the cause, and reads like a missing-file bug in the test itself.

Two things worth knowing:

- **A stash round-trip is not transparent to staged deletions.** If a lane uses
  one mid-run to check something against its base, `git add -A` afterwards, and
  check `git status --short` for ` D` entries before believing the tree.
- **`git ls-files` is an index read, not a filesystem read.** Any guard built on
  it inherits this and will fail with a confusing `FileNotFoundError` far from
  the cause. A guard of that shape could skip a listed path that does not exist,
  or say so in as many words, rather than raising.

Cost: roughly 25 minutes, almost all of it a full suite run whose one real
finding was this. Confirmed by `git ls-files | grep <deleted names>` returning
the files, and fixed by `git add -A`.
