Found during #1241/#1242/#1253's own lane (bundled lane-doctor dispatch), self-review pass.

#1242's fix gave `doctor_check_merge_permission.py`'s covering-wildcard scan a
`cannot-tell-whether-covered`/`-forbidden` third state, matching `SUPERTOOL_COMMAND_HEADS =
frozenset({"supertool", "./supertool"})`. But the pre-existing literal-match `SUPERTOOL_ENTRY_RE`
in the same module already recognises a THIRD spelling: an absolute path ending in
`.../supertool`. A covering-wildcard rule spelled the same absolute-path way (e.g.
`Bash(/usr/local/bin/supertool *)`) silently falls through to `absent` instead of
`cannot-tell-whether-covered` -- the exact class #1242 itself was filed to close, one spelling
form over.

The same gap exists in `doctor_check_worktree_reap_permission.py`'s identical git-only usage
(an absolute-path `Bash(/usr/bin/git *)` wildcard has the same latent hole, and was never
reported against #886/#895 either).

Not fixed as part of #1241/#1242 because it needs a design decision about the shared wildcard
helper's own matching contract -- moving from exact-equality-against-a-set to something that also
recognises an absolute-path form ending in one of the heads (mirroring `SUPERTOOL_ENTRY_RE`) -- a
change to both files' shared contract, not a one-line fix in one.

Severity: low in practice (a maintainer is far more likely to write `Bash(supertool *)` than an
absolute-path wildcard rule) and it is currently untested either way.

Ranked: misreports (a check answers a narrower population than it believes it covers) --
non-blocking per skills/manager/phases/findings.md's ranking table. Logged here per that routing
rule rather than filed as a fresh issue.
