A python heredoc that writes a file bypasses every configured supertool validator, and the
raw-command guard does not catch it.

Observed 2026-09-05 in this repository, editing `.oss.json` to record a measured lane label
vocabulary. `.supertool.json` configures `jsonlint` with `match: "*.json"`,
`rollback_on_fail: true`, hooked into `edit`, `replace`, `replace_lines`, `paste`, `append`
and `vim` -- plus `gitleaks` on `*`, also with rollback. None of it ran, twice, because the
write went through:

    python3 - <<'PY'
    open('.oss.json','w').write(...)
    PY

The first of those two writes round-tripped the file through `json.dumps(indent=2)` and
reformatted three unrelated inline arrays -- 15 insertions for a 5-item list edit. That was caught
by reading `git diff` afterwards, not by anything in the tool chain, and a validator would not
have caught it either since the reformatted file is still valid JSON. The second write was
surgical and correct. Neither was validated at write time; `jsonlint` was run by hand afterwards
and passed, which is the "reached green afterward" reasoning `skills/manager/SKILL.md` rejects
for the default branch one level up.

The raw-command guard is not the backstop here. It hooks Bash and maps known invocations -- in the
same session it correctly refused `gh label list` and named `gh-labels` as the replacement -- but
a heredoc that opens a path and writes it matches no op, so it passes unmapped and unmentioned.
The guard's own refusal text says this plainly: "any other route to this file gets no op, no
validator and no rollback, which makes it a worse write rather than a way past this one". So the
gap is documented at the point of refusal, and reaches nobody who never triggers a refusal.

What would have been correct, and is printed at the foot of every `read:` of the file:

    ./supertool 'edit:OLD:NEW:.oss.json'

Worth weighing, none of it tried: whether the guard could match a write-shaped heredoc at all
(`open(...,'w')`, `>` redirection to a tracked path, `tee`) without drowning in false positives
on scratch files; or whether this is simply the cost of a total Bash grant, which `CLAUDE.md`
already names as advice rather than a boundary. The observation worth keeping either way is that
a configured validator with `rollback_on_fail: true` reads as protection over a file, and it is
not -- it is protection over a route.
