Across four merges in one tick (2026-09-03/04, PRs #961, #965, #969, #968), the default branch was
never once observed GREEN between them. Every squash produced the same three-event sequence from the
`gh-branch` watcher — `no_run` on a commit one second old, then `went_not_green` on the grounds that
`tests` had not concluded, then nothing further, because the next merge landed and moved `main` before
its run finished.

Measured on one of them: the sub-manager polled `main` at `61f3772` six times over roughly 2.5 minutes
and found it stable at 11/13 passed, 0 failed, 2 pending. Not red. Not concluded either.

The gate held anyway, and the reasoning is worth keeping because it is what makes the pattern tolerable
rather than alarming: each PR was merged on its own concluded run, and that run was against exactly the
tree being merged (the PR's rebased head), so the combination was validated by the PR's own green
regardless of whether main's separate run on the prior commit ever concluded. The sub-manager stated this
explicitly rather than assuming it.

What the pattern actually costs is the second hedge. When a rebase is skipped on file-disjointness
grounds — as it was for #968 against #969, correctly by this repo's own lane-bundling standard — the
combined content has been run nowhere, and main's own run is the only thing that would catch it. If that
run is always outpaced by the next merge, the backstop never fires. In this tick it did fire, but only
because #968 was the last merge and nothing followed it: `main` reached GREEN at `7e3b1e4` (13/13),
covering #968 and #969 together for the first time. Had a fifth PR been ready, that observation would
not exist.

So: a green default branch after a merge train is an artefact of the train ending, not of the train
being safe. Possibly the rule worth writing is that the last merge of a tick must be watched to
conclusion before the tick closes — which this tick did, but by instruction rather than by anything
written down.

Separate and unresolved, visible in every one of these readings including the green one: the `changelog`
workflow is declared in `.github/workflows` and produces no run, so it is excluded from the coverage
sentence every time. That is the steady state here, not a regression from this round.
