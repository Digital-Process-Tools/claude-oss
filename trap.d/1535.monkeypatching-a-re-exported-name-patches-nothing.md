# Monkeypatching a re-exported name patches the copy nobody calls

Found during #1535's self-review, by the `Explore` reviewer, on a test that had been
green and meaningless for some time.

`scripts/lane_setup.py` imports its submodules and **re-exports every name at module
level** so `lane_setup.<name>` keeps working for existing callers. Its own docstring says
so. But `compute()` does not call the re-exported alias -- it calls through the submodule:

    base = lane_setup_worktree.resolve_base(repo, remote, default_branch)

So `monkeypatch.setattr(lane_setup, "resolve_base", ...)` rebinds an attribute nothing
reads. The patch applies, pytest reports nothing, and the **real** `resolve_base` runs
against the test's throwaway git repo, which has no `origin`. It returns
`state: "could-not-resolve"`, `blocked(payload)` fires, and `main()` exits
`EXIT_COULD_NOT_RUN`.

That is the trap: the exit code the test asserts is the one it expected, arriving from a
code path the test was not testing. In
`tests/test_claim_label_fold_1143.py::test_main_end_to_end_refuses_the_agent_call_on_a_structural_brief_finding`
this hid a genuine regression -- #1535 changed the brief schema so the test's fixture was
no longer a structural finding at all, `compose_claim_label` returned `rendered`, the full
`Agent(...)` line was printed, and the test stayed green throughout because the dead patch
was supplying the exit code by itself.

**How it was confirmed**, rather than reasoned: patch corrected to
`monkeypatch.setattr(lane_setup.lane_setup_worktree, "resolve_base", ...)`, fixture changed
to a real structural finding, and a paired positive control added in the same fixture -- the
identical CLI call with the marker removed now exits `EXIT_OK` and prints the `Agent(...)`
line. Before the repair that arm would also have exited `EXIT_COULD_NOT_RUN`, which is the
whole proof that the assertion had been measuring nothing.

**Two more instances are still on disk**, not fixed by #1535 because they sit outside that
issue's footprint and each needs its own check that the test still proves what it claims:

  * `tests/test_lane_count_385.py:202`
  * `tests/test_lane_claim_705.py:57` (inside the shared `_patch_reads` helper, so every
    test in that file routes through it)

Both currently pass. Nothing establishes whether they pass for their own reason or for this
one -- that is the question to answer before touching them, and answering it is the work.

**The general shape, which is what makes this worth keeping:** a module that re-exports
submodule names for compatibility has two bindings for one function, and `setattr` on the
wrong one fails silently in the direction of "the test still passes". Grepping for
`setattr(<module>, "<name>"` finds the sites; only reading the *call* tells you which
binding is live. A test that patches a dependency and then asserts an error code is the
shape most exposed to it, because the unpatched real dependency usually fails too, and
fails into the same code the test was hoping to see.
