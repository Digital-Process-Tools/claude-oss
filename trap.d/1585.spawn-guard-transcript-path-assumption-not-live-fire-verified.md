PR #1594 (#1585) added `_is_subagent_transcript()` to `scripts/sub_manager_spawn_guard.py`,
short-circuiting the spawn guard to `DECISION_ALLOW` whenever `payload["transcript_path"]` does
not look like `.../subagents/agent-<id>.jsonl`, on the premise that a main-session caller (the
scheduler) never carries that segment and a nested sub-manager spawn always does. The fallback
shape is sound -- an absent, non-string, or `subagents/`-shaped path still falls through to the
existing marker-based decision unchanged, so the new code path only ever widens what is allowed,
never what is denied. But the premise itself is the issue's own investigation, not independently
re-verified in this session against a live harness-captured PreToolUse payload the way
`tool_input.subagent_type` was confirmed against published SDK docs before #1520 built on it (see
`.claude/jit-context/paths/00-manual/00-README.md`'s `1520.spawn-guard-docstring-cites-wrong-field-count`
/ `1571...` entries -- this exact module already got a harness-payload-shape fact wrong once).

If the real `transcript_path` shape for a nested spawn ever diverges from `subagents/agent-<id>.jsonl`
(a singular `subagent-<id>.jsonl`, no `subagents/` segment at all, anything this module has not
seen), `_is_subagent_transcript()` would misread a genuine nested sub-manager spawn as a
main-session caller and the guard would fail open for exactly the case #1520 exists to deny.

What would settle it: a real nested-spawn attempt run post-merge, with the actual PreToolUse
payload's `transcript_path` read back and compared against `_SUBAGENT_TRANSCRIPT_RE` -- the same
live-fire confirmation #1520 itself got, rather than a synthetic test payload. #1585 was closed by
merging #1594; nothing currently tracks this follow-up as an open task once the issue closes.
