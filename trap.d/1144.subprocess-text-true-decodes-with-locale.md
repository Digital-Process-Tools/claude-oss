`subprocess.run(..., text=True)` with no `encoding=` decodes the child's output with the
**locale** encoding, which is cp1252 on a Windows runner and UTF-8 almost everywhere else. Any file
in this repository carrying an em dash -- most of the loop's own markdown does -- comes back as
mojibake on Windows and matches nothing.

Observed 2026-09-06 on PR #1144, `pytest (windows-latest, 3.12)`, one leg of eighteen:

    E  AssertionError: PRIOR_PR_PAYLOAD is not the pre-change subsection: it says it is
       un-elided apart from em dashes, and it does not appear verbatim in
       f58aed3:agents/developer.md after that one substitution

`tests/test_developer_brief_duties.py::_blob` shells out to `git show <commit>:agents/developer.md`
with `text=True` and nothing else. The file is UTF-8; U+2014 is three bytes; cp1252 turns each into
three separate characters, so the test's own `EM_DASH -> "--"` normalisation never fires and the
passage cannot be found. The fix is one keyword: `encoding="utf-8"`.

**What made it expensive to read.** It passed on macOS and on every Linux leg, and it passed on
`main`. The obvious reading was "our change broke it" -- and the change under review had touched
neither that test nor the file it reads. The tell was that only one platform failed, and the
assertion mentioned em dashes.

**Why it had not fired before.** `_blob` returns `None` and the test *skips* when `git show` cannot
produce the old commit, which is what a depth-1 `actions/checkout` normally looks like. So the
decode path is only reached on a runner whose checkout is deep enough to hold `f58aed3`. A test that
usually skips is a test whose bugs surface at random, on one platform, months later.

**Worth grepping for.** Any `subprocess.run(..., text=True)` reading repository content is the same
defect waiting for a Windows leg. `capture_output=True` plus `text=True` is the common shape.
