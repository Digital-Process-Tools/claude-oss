#1254 (scripts/fix_commit_scope.py): a trailing `--` separator does NOT close an option-injection
hole in a git revision argument, even though it is the natural first fix to reach for and is what
the issue itself originally suggested.

`git diff --name-only "{base}..{head}" --` still lets an attacker-controlled `base`/`head` starting
with `-` (e.g. `base = "--output=/some/path"`) be parsed as an OPTION rather than a revision,
because `--` only disambiguates a PATHSPEC section from a revision section -- it does nothing to
stop an option-shaped token that appears BEFORE it from being consumed as an option. I verified this
empirically: `git diff --name-only --output=X..HEAD --` still wrote a file (named `X..HEAD`, since
the whole joined "{base}..{head}" string becomes the `--output=` value -- another trap below).

The actual fix is `--end-of-options` (git >= 2.24, Nov 2019), placed BEFORE the revision argument:
`git diff --name-only --end-of-options "{base}..{head}"`. This closes option parsing entirely at
that point, so an option-shaped revision string is refused by git itself
(`fatal: option '--output=...' must come before non-option arguments`, exit 128) rather than
silently obeyed. Confirmed this doesn't break the ordinary case: `git diff --name-only
--end-of-options <sha1>..<sha2>` still reads a real diff correctly.

Putting `--` BEFORE the revision (instead of `--end-of-options`) also "works" in the sense that it
blocks the injection, but it breaks legitimate usage: git then treats the whole "{base}..{head}"
string as a PATHSPEC rather than a revision range, so a real `<sha1>..<sha2>` silently returns an
empty diff instead of the real one. Confirmed this with a real two-commit repo.

Second trap in the same investigation: if you build the git argv as a single joined string
"{base}..{head}" (rather than two separate revision arguments), an injected
`base = "--output=/tmp/pwned.txt"` does NOT write to `/tmp/pwned.txt` -- it writes to
`/tmp/pwned.txt..HEAD`, because the WHOLE joined string after `--output=` (including the literal
`..HEAD` suffix) becomes the option's value. A negative-control test asserting
`not Path("/tmp/pwned.txt").exists()` is vacuous for this reason: that path's absence is true both
before AND after the fix, since the actual file created under the vulnerable code has a different
name (`...pwned.txt..HEAD`). Assert against the REAL injected filename, or you get a test that
"passes" against the vulnerable code, then still "passes" after the fix, for two different (both
wrong) reasons. Both a spawned `Explore` reviewer and a spawned `oss:auditor` independently caught
this same defect in my own first-draft test during self-review.

Third, smaller trap: to actually observe raw UTF-8 bytes from `git diff --name-only` on a filename
containing non-ASCII characters (to reproduce a locale-decode UnicodeDecodeError), you must set
`git config core.quotepath false` in the test repo first. By default git quotes any path containing
a non-ASCII byte as a backslash-octal-escaped, double-quoted string (e.g. "caf\303\251.txt"), which
is pure ASCII on the wire and will never trigger a decode error under any locale. Also: to force
Python's subprocess text-mode decoding into a specific codec for testing, you must monkeypatch
`locale.getencoding` (not `locale.getpreferredencoding`) on Python >= 3.10 -- `subprocess.run(...,
text=True)` with no explicit `encoding=` resolves the default encoding via
`subprocess._text_encoding()`, which calls `locale.getencoding()` (PEP 597) when
`sys.flags.utf8_mode` is off, not `locale.getpreferredencoding(False)`.
