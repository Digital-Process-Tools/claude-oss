A CI wait loop exited immediately because its success pattern is a substring of the failure message.

2026-09-05, watching PR #1066's checks to conclusion before merging. The loop was:

    until ./supertool 'gh-pr:1066:status' | grep -qE "ALL GREEN|failed: [1-9]|[1-9] failed"; do sleep 45; done

It returned in seconds with 12 checks still pending. `gh-pr:N:status` prints, verbatim:

    checks: 18 total: 6 passed, 0 failed, 12 pending ⚠ NOT ALL GREEN — oldest pending 1m

`NOT ALL GREEN` contains `ALL GREEN`. The wait was satisfied by the exact sentence saying it should
keep waiting, and the next step in the plan was a merge. Nothing about the output looked wrong --
the loop exited, exit code 0, and the status text it printed at the end was the true, still-pending
one, so the failure was only visible by reading the number rather than trusting that the loop had
ended for the right reason.

What makes this worth keeping rather than filing as a one-off typo: it is this repository's own
defect class wearing a shell-quoting hat. A check that never ran and a check that found nothing
render identically -- and here a check that matched the negation and a check that matched the
assertion render identically too, because a substring match cannot see the word in front of it.
Any positive-signal grep over human-readable status text has this hazard whenever the tool also
prints the negated form, which good status output routinely does (`NOT ALL GREEN`, `not configured`,
`no findings`, `could not`).

What worked instead: invert the test and wait on the absence of the transient state rather than the
presence of the terminal one --

    until ! ./supertool 'gh-pr:1066:status' | grep -q "pending"; do sleep 45; done

`pending` has no negated form in that output, so there is no sentence that can satisfy it wrongly.
The general habit: match the word the tool prints ONLY in the state you are waiting for, and prefer
waiting on a state disappearing over a state appearing, because absence has no antonym to collide
with. Where a positive match is unavoidable, anchor it (`grep -qE '[^T] ALL GREEN'` is fragile too;
a field-aware read of the count is the honest version).

Second, smaller thing from the same call: `gh pr checks ... --jq` is refused by supertool's raw
command guard and replaced by `gh-pr:N:status`, so the polling loop cannot be written with `gh`
directly here. That is fine, but it means the loop's condition has to be a text match over a
human-readable line rather than a JSON field -- which is precisely what makes the trap above
reachable. Worth weighing whether the op should expose a machine-readable pending count.
