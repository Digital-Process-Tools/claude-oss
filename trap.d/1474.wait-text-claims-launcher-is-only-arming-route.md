Second, independent defect in the same WAIT arm that `trap.d/1474.doctor-mcp-channel-wait-sentinel-dead.md`
already covers -- that fragment is about the sentinel being unreachable, this one is about the
sentence the arm prints being false on its own terms. Both would have to be fixed; fixing the
sentinel alone would leave a correct branch printing a wrong excuse.

Observed 2026-09-14 in an interactive session opened by hand (not through `bin/oss-workspace`),
diagnosing the loop session running alongside it. `bash scripts/doctor.sh --findings` printed:

    WAIT channel MCP connection: every MCP server resolving to the claude-channel consumer reports
    a failed transport (oss-channel -- bun .../notifiers/claude-channel/channel.ts - ? Failed to
    connect ? CONNECTION_CLOSED: Connection closed), and this session was not opened through
    bin/oss-workspace -- nothing in a session opened another way arms or binds the consumer, so
    this is the expected reading rather than a fault. Settles the next time a session is opened
    through the launcher.

The claim "nothing in a session opened another way arms or binds the consumer" is false, and the
counter-evidence is in the same module. `arm_target_liveness`'s own docstring in
`scripts/doctor_check_mcp_channel_connection.py` (the `plugin_channel_arm_decision` paragraph)
states that an installed plugin DECLARES a claude-channel consumer in its own `.mcp.json`, and
that `bin/oss-workspace` then declines to register `oss-channel` on top of it. A plugin-declared
server is started by the harness at session open regardless of how the session was opened. A
launcher-written `oss-channel` registration also persists in settings and is likewise started on
every later session, launcher or not.

Confirmed directly in the hand-opened session: `claude mcp list | grep -i channel` returned two
rows, not zero --

    plugin:supertool:claude-channel: node --experimental-strip-types ./notifiers/claude-channel/start.mjs - ? Failed to connect -- CONNECTION_CLOSED: Connection closed
    oss-channel: bun <plugin cache under the maintainer's home>/notifiers/claude-channel/channel.ts - ? Failed to connect -- CONNECTION_CLOSED: Connection closed

so two consumers were armed in a session the WAIT text asserts can have none. "Settles the next
time a session is opened through the launcher" is the same error restated: nothing about the next
launcher open changes whether these two registrations start, and a genuinely dead transport here
would survive it.

What it cost: the loop session read this WAIT line as a settled non-fault and moved on. That is
the whole failure mode -- the line is written to be believed, and it was.

Not decided here: whether the right fix is to delete the WAIT arm and restore the WARN (which
would also remove the dead sentinel), or to derive launcher-vs-not from something actually
observable in-session. Flagging one hazard for whoever takes it: the arm above this one already
suppresses a `failed` listing to OK when `channel:health` reports `forwarding`, for the
fork-cannot-bind-an-exclusive-socket reason, so the real-fault WARN below is narrower than it
looks and the two arms have to be read together.
