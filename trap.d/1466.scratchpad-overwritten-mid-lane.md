While working issue #1466, a lane staged a commit message in its own session scratchpad file,
verified it with `cat`, then called `git-commit` referencing that same path -- and the commit that
landed carried a completely unrelated message, verbatim from a different issue's fix (#1462). Root
cause, reasoned rather than confirmed: the scratchpad file was overwritten between the verifying
`cat` and the `git-commit` call, most likely by a concurrent lane running on the same host in the
same tick, writing to a path that collided or was reused.

Caught only by a routine `git log -1` check after the commit, not by anything mechanical -- the
commit succeeded, the message was syntactically fine, and nothing in the tool chain flagged the
mismatch. Fixed by amending before it was reported.

This is the same shape as `trap.d/1345.tmp-toml-collision-blocked-heredoc.md` /
`.claude/jit-context/paths/00-manual/refused-bash-call-is-all-or-nothing.md` (a scratch path is not
reliably private across a session, or even within one session's own concurrent lane fan-out), but
the concrete instance here is a genuinely different failure mode from that fragment's own two
examples: no refused-call retry was involved, and the file's own path was inside the session
scratchpad directory that convention already recommends -- collision happened anyway, apparently
from another lane's concurrent write. Worth a second look at whether the scratchpad directory
itself is unique enough per lane, or whether each dispatched lane should namespace its own writes
inside it (e.g. by issue number) rather than relying on the directory alone.
