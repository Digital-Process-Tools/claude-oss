While self-reviewing lane 383's diff, one `supertool edit:@-` call landed on
the wrong file: `.claude/jit-context/tools/00-manual/a-write-outside-supertool-meets-no-validator.md`
got edited (a duplicate application of an unrelated block already inside
that file) instead of `scripts/doctor_check_statusline_unknowns.py`, the
intended target.

Mechanism, as best reconstructed: a single Bash call ran two commands back
to back -- `cd <worktree> && python3 - <<'PYEOF' ... open("/tmp/e5.toml",
"w").write(payload) ... PYEOF` followed immediately by
`supertool 'edit:@-' < /tmp/e5.toml | tail -30`. The `| tail -30` on the
second command tripped this repo's own "do not cut a supertool op's
output" raw-command guard, and the guard refuses the WHOLE Bash call, not
just the offending command -- so the `python3` heredoc that should have
(re)written `/tmp/e5.toml` never ran either. On retry (same command, no
`| tail`), `edit:@-` read `/tmp/e5.toml` and it turned out to already
contain unrelated content (from something else on this machine using that
exact path, not from this session) that happened to match an `old` block
present in the jit-context markdown file. The edit "succeeded" against the
wrong file with no error, because the `old`/`new` anchors matched cleanly
there too.

Caught immediately by a habitual `git status --short` right after the
"successful" edit -- the diff showed a modification to a file this lane
never intended to touch. Reverted with `git checkout --
<path>`. No lasting damage, but it could easily have gone unnoticed if the
post-edit `git status` habit had been skipped, since the edit command's own
success output gave no indication anything was wrong (validators all
passed, because the resulting jit-context file was syntactically fine).

Two things this suggests, left for `/oss:curate` to weigh: (1) `/tmp/*.toml`
scratch files are not reliably private to one session/call -- they should
never be reused as a payload path across a refused-and-retried Bash call,
since a refused call may partially execute (the second command in the
chain effectively "ran" against stale/foreign content); the session
scratchpad directory (`/private/tmp/claude-501/.../scratchpad/`) is safer
and is what this repo's own developer brief already directs writes toward.
(2) When a Bash call is refused by the no-`| tail` guard, nothing signals
which of the several commands in that call actually executed vs. which
were entirely skipped -- the refusal names the offending command but the
call is all-or-nothing, and a session that assumes "the guard just strips
the pipe" rather than "the guard refuses everything" will act on stale
state from an earlier partial write.
