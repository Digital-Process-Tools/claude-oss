Release audit (round 1, v0.27.1..HEAD) found a composition defect between two individually-clean
commits: 209300d (#1246, "reduce the push/PR CI matrix, make the full matrix a blocking release
gate") and ace4a98 (#1266, "wait on the release commit's own CI before tagging"). #1246 reduces
push/PR CI to five legs (ubuntu 3.9, ubuntu 3.12, macos 3.12, windows 3.12, shell) and reserves the
full 3 OS x Python 3.9-3.12 matrix for `workflow_dispatch` with `full_matrix: true`. #1266 adds a
wait on the release commit's own CI, but that wait runs AFTER the release commit is written and
pushed (commands/release.md: "## Then" around line 451, "## Wait for the release commit's own CI"
around line 484), and it accepts any set of concluded-and-passed runs on that sha --
scripts/release_ci_wait.py classifies GREEN by conclusion only, never by which workflows or legs
ran (lines ~185-218). The only `gh workflow run ... full_matrix` instruction anywhere in
commands/release.md is inside gate 1 (around line 73), which runs BEFORE the release commit exists.
Net effect: the commit that actually gets tagged is verified only by the 5-leg reduced matrix, and
changelog.d/1246.changed.md's own claim -- that the full matrix is "the input a release run sets
when it dispatches the workflow against the commit about to be tagged, so a release gate is the only
place the full matrix's coverage is required to pass" -- does not describe what the procedure
actually does. Neither diff contains the defect on its own; the composition does. Fix: the #1266
section in commands/release.md should dispatch `workflow_dispatch` with `full_matrix: true` against
the release commit's own sha (after it is pushed) and wait on that run, not just on whatever
push-triggered run happens to exist. Ranked `misreports` (non-blocking) by the round-1 release
audit -- this release (v0.27.2 or whatever tag follows) ships without this fix, per the two-round
audit protocol.
