# The parity guard named its own source of truth in a comment and compared something else

Found by an audit spawn on PR #921, 2026-09-03. The jit-context rule for this exact class already
existed and fired on the files being edited.

`tests/test_spawn_token_fill_parity_828_867.py` held:

    #: The three short-lane reasons, as a closed set -- `dispatch_rank.SHORT_REASONS`
    #: is the actual source of truth for the vocabulary; this only checks that both
    #: prose documents name the same three words for a human reading them.
    SHORT_REASONS = ("board-exhausted", "no-adjacent", "could-not-tell")

The comment names `dispatch_rank.SHORT_REASONS` as the source of truth and the code then does not
read it. It compares `agents/sub-manager.md` against `commands/tick.md` -- two prose copies, against
each other -- so both naming the same stale set is indistinguishable from both being right.

#918 added a fourth word to `dispatch_rank.SHORT_REASONS`. The guard went on reporting parity. Every
prose path a real tick reads still described the pre-#918 world, including `agents/sub-manager.md`,
which `this same test file's own docstring` calls "the file whose own brief is the only thing a
sub-manager actually reads before dispatching". So the new refusal shipped as code no dispatching
agent had been told about: a guard nominally on and effectively off, which is the shape #918 was
filed about one layer up, reappearing inside #918's own fix.

Changing the tuple to `tuple(_dispatch_rank.SHORT_REASONS)` made it fail immediately on both briefs.
The prose fixes were then found rather than guessed at -- which is the whole difference between a
guard and a comment.

## The rule was already written, and it did not prevent this

`.claude/jit-context/paths/00-manual/loop-prose-parity.md` matches
`agents/*.md` and `skills/manager/**` and says, in its first bullet:

> Two copies of a brief agreeing with each other proves nothing about whether either is right. ...
> **Pin the measured tool output**, not the parity -- parity alone passes this case.

That rule was written from #-the-`batch op missing 'op' field` incident, where two briefs drifted
into agreement on a wrong string. This is the same defect with a different subject: not two briefs
agreeing on a wrong string, but two briefs agreeing on a stale *set* while the code that defines it
moved. The rule fires on the documents; it does not fire on the test that checks them, because
`tests/` is a different match. So the guidance was present in the session and pointed at the wrong
file.

Worth considering whether the rule's match should extend to the tests that assert over those
documents, or whether the lesson is narrower: **a test whose comment names a source of truth should
import it.** The second is mechanically checkable and the first is not, which is an argument for the
second, but it is a judgment for the pass and not for this fragment.

## The other half, same audit

`oss_state.lane_fill` dropped a count supplied alongside `did-not-search` or `could-not-tell`.
`check_lane` reads `candidates` only for `board-exhausted` and `adjacent` only for `no-adjacent`, so
a count offered for either of the other two reached neither parameter. The written receipt was
byte-identical to one from a caller who measured nothing. Settling check the auditor named: call
`lane_fill` twice, once with the count and once without, and compare the records.

Both findings are the same sentence in different places: **a thing that was not done renders exactly
like a thing that was done and found nothing.** That is the repository's stated defect class, and it
landed twice in one pull request whose entire subject was that defect class.
