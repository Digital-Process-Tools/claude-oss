Lane #1530 asked: group select_issues.py's dispatch bundling by GitHub lane label instead of
per-issue declared-file overlap, then delete the machinery that computed that overlap
(`_derive_lane_patterns_from_labels`, `lane_patterns_source`, `.oss.json`'s `labels.lane_patterns`,
`scripts/doctor_check_lane_patterns.py`, `scripts/lane_pattern_coverage.py`) on the premise that,
once grouping keys on the label, nothing else needs a per-issue file set.

That premise was checked against the concurrently live #1528 (worktree `claude-oss-wt/1528`,
uncommitted at the time of this read: `scripts/select_issues.py` diff inspected via
`git -C <path> diff`, never entered directly per the "never work in another agent's worktree" rule)
and found false for anything landing after #1528 merges.

#1528 turns the held-set collision check in `select()` from a hard block (`lane-collision`, drops
the candidate) into an informational field (`overlap: {"files": [...], "holders": [...]}` via a new
`_overlap_info` helper) attached to every surviving candidate. That field is computed from
`resolved["files"]`, which is `resolve_lane(Path("."), lane_patterns)` -- the SAME per-issue file
set `_derive_lane_patterns_from_labels` produces via its three-deep precedence (declared /
derived-from-body / derived-from-label). #1528 does not touch `_derive_lane_patterns_from_labels`,
`lane_patterns_source`, or the `resolve_lane` call at all; it only changes what happens after the
overlap is computed. The maintainer's own review comment on #1528 (posted the same day, before this
lane was dispatched) says as much directly: "the derivation already exists... every candidate
carries `lane_patterns_source` naming which of the three applied," and recommends re-reading
`scripts/lane_pattern_coverage.py` / `scripts/doctor_check_lane_patterns.py` before acting on #1528
-- both scripts #1530 was briefed to retire.

So `labels.lane_patterns` and its resolution chain are NOT solely feeding the grouping partition
#1530 set out to make redundant; they also feed a held-set overlap field #1528 is building as a
permanent, informational (never-blocking) part of every candidate's payload. Deleting the derivation
once #1528 lands would silently blank that field for every candidate whose lane pattern is
label-derived (tier 3 of the precedence) -- the majority case, since #1068's own history (cited in
both issues) is that almost no real issue ever declares `lane_patterns` explicitly.

Net: #1530's Step 1 (bundling by label rather than companion-overlap search) looks implementable in
isolation and does not appear to conflict with #1528's diff region (`_group_candidates` at
scripts/select_issues.py:330-515 is untouched by #1528). #1530's Step 2 (the deletion) cannot land
as scoped once #1528 merges, because the thing it calls dead is not dead. Confirmed by reading, not
run -- no code in this lane's worktree was changed.
