Working #1389 (moving six commands/*.md files into commands/run/ and fixing roughly twenty test
files' literal path constants), a supertool edit/batch call with a TOML single-quoted (literal)
string containing a two-character backslash-n between two lines silently did NOT match, even though
the file's actual content, read back with supertool read, looked byte-identical to what I had typed.
The error message each time was "old string not found ... nearest match at line N (70%)" -- a
partial match score, not a hard 0%, which reads like a fuzzy-anchoring problem rather than what it
actually was: TOML literal strings (single-quoted, including a triple-single-quoted block) do not
process backslash escapes at all, so a typed backslash-n inside one is the two literal characters
backslash and n, not a real newline. My old value was therefore searching for a string with a
literal backslash-n in the middle of it, which of course was never in the file.

Fix: for any multi-line old/new payload, use a triple-single-quoted TOML string with a REAL embedded
newline (an actual line break typed inside the heredoc between the two lines), never a typed
backslash-n inside a non-literal-newline context. A single-line old/new with no line break at all
works fine either way, which is why several early single-line edits succeeded and masked the pattern
until a two-line one failed.

This is a real gap in the developer brief's own "payload content is parsed, never evaluated" section
-- it says a chr(10) call is not evaluated (true, and I did not hit that), but does not separately
warn that a typed backslash-n inside a TOML value needs the string to actually be a literal block
with a real newline in it, rather than assuming backslash-n "just works" as an escape the way it
would in a raw Python string or a JSON string.
