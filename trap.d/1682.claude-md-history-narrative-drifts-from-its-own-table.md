# CLAUDE.md's re-baseline history narrative can drift from its own enforced table

Found while self-reviewing the #1682/#1683 fix: `CLAUDE.md`'s "This file has a size budget too"
section carries a chain of "Re-baselined for #NNNN" paragraphs, each one supposed to record the
actual measured before/after byte counts for the file. At least one link in that chain has drifted
from the code-enforced truth: the "Re-baselined at the v0.40.0 release" paragraph (immediately
before the #1682 paragraph this fix adds) ends with "66,796 B became 69,200 B, past the 67,000 B
ceiling. Ceiling moves to 69,500 B" -- but the actual committed state at that point (verified with
`git show c5a6e8c2:CLAUDE.md | wc -c` and `scripts/claude_md_budget.py`'s own `BUDGETS["CLAUDE.md"]`
tuple at that same commit) was `(68784, 69000)`: baseline 68,784 B, ceiling 69,000 B -- not
69,200/69,500.

`tests/test_claude_md_own_budget_1556.py` and `tests/test_baseline_matches_disk_1014.py` only check
the *table's* declared baseline against the real file size on disk -- they never parse or
cross-check the free-text narrative sentences against either the table or the code constants. So
this kind of drift is invisible to every existing guard and will keep happening as long as each new
re-baseline paragraph is drafted by eye against the *previous paragraph's claimed ending number*
rather than against the actual enforced value.

A reviewer (Explore spawn) caught this live: I had written a new paragraph continuing the false
"69,200 became X" thread, and had to rewrite it to start from 68,784 (the real prior baseline)
instead. I did not go back and fix the pre-existing v0.40.0 paragraph's own numbers -- that is a
larger, separately-scoped edit (rewriting release-marker history prose is its own kind of change,
and CLAUDE.md's hand-curation rule discourages incidental edits to unrelated sections in a lane
already scoped to two specific issues).

Possible fix for a future pass: either (a) a lightweight test that extracts the last "B became" /
"Ceiling moves to" figures from each numbered re-baseline paragraph in this section and cross-checks
the final one against the live `BUDGETS["CLAUDE.md"]` tuple (loose coupling: only the very last
paragraph's ending number needs to match, since intermediate ones are historical narrative that
can legitimately describe a since-superseded state) -- or (b) just accept these paragraphs as
best-effort narrative with no correctness guarantee and say so explicitly at the top of the section,
so a reader does not trust arithmetic in the middle of the chain. Not sure which; flagging for
/oss:curate to decide.
