Release audit (round 1, v0.27.1..HEAD), platform band: scripts/doctor_check_lane_other_label.py:91
calls `subprocess.run(..., universal_newlines=True)` against `gh label list` with no explicit
`encoding=`, so stdout is decoded with the runner's locale codec at the default `errors="strict"`.
A label name carrying a character that codec cannot represent (concretely: cp1252 on Windows) raises
`UnicodeDecodeError`, which is a `ValueError` and is NOT caught by the surrounding
`except (OSError, subprocess.SubprocessError)` at line 94 -- it escapes `check_lane_other_label` and
takes down a diagnostic whose whole contract is "exit 0 always, one VERDICT line", so
`bin/oss-workspace`'s VERDICT parse gets nothing instead of a warning. This is the identical pairing
`scripts/fix_commit_scope.py` gained in this same delta for #1251
(`encoding="utf-8", errors="replace"`) -- the fix here is the same one-line change. Marked "not
covered" rather than "covered" because the windows 3.12 CI leg stubs `run` in the test and never
decodes real `gh` bytes, so the failure mode is untested on the one platform it would fire on. The
pre-existing sibling `doctor.label_vocabulary_state` (scripts/doctor.py, near line 8560) carries the
same shape and was out of scope for this finding (outside the audited diff and its immediate
callers). Ranked `misreports` (non-blocking) by the round-1 release audit.
