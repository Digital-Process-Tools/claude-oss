Gate 3 release audit (v0.37.0..HEAD, round 1) found: `tick_handback.py`'s `--clear-marker-root`
block (lines ~637-681, added by #1585) resolves the role marker path via `git rev-parse
--git-dir` rather than `--git-common-dir`. In a linked worktree, those two resolve to different
paths -- `.git/oss-agent-role` at the main clone vs `.git/worktrees/<name>/oss-agent-role` from
inside the worktree. Measured in a throwaway repo: with a live `sub-manager` marker written at the
main clone, invoking `--clear-marker-root <worktree>` prints `marker: nothing to clear`, exits 0,
and leaves the marker on disk with `current_role()` still reporting `sub-manager` -- so "no marker
was ever written" and "the marker is live at a git dir this call did not resolve" render
identically.

On the ordinary path (this harness resets cwd between Bash calls, and a sub-manager's handback
runs from the main clone) this does not fire -- which is why the auditor ranked it `misreports`
rather than higher. But if a sub-manager's cwd at handback time is ever a linked worktree, a marker
can outlive a clean tick and block the scheduler's next legitimate `oss:sub-manager` spawn -- the
exact symptom #1585 was written to fix.

Fix candidates: switch to `git rev-parse --git-common-dir` in `agent_role._marker_path` (or
wherever `--clear-marker-root` resolves the marker path), or add a fourth `marker:` state that
names the git dir actually resolved so a caller can tell "nothing to clear" from "resolved the
wrong root."

site and scripts/tick_handback.py's `--clear-marker-root` implementation.
