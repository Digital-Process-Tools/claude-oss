While running the self-review's tree_snapshot receipt (agents/developer/review.md), `cd
/Users/floriandavid/Documents/claude-oss-wt/1078 && python3 .../scripts/tree_snapshot.py snapshot
> before_snapshot.json` -- run as one Bash call, `cd` and the python invocation joined with `&&` --
recorded `"root": "/Users/floriandavid/Documents/claude-oss-wt/1042"`, a sibling lane's worktree
named in this lane's own brief as "do not touch", not the `/1078` worktree the command explicitly
`cd`'d into. `tree_snapshot.py`'s `snapshot(root=".")` resolves `.` at the python process's own
cwd, so the process that ran was not standing where the shell line said it was.

Not diagnosed further (this session has no visibility into whatever rewrites the shell command
before it runs -- the user's global CLAUDE.md documents an "rtk" transparent command-rewriting
hook that intercepts git and other commands), but the effect is exactly what
`agents/developer/review.md` already warns `compare` can do to a *later* Bash call after cwd
resets (#971) -- this hit `snapshot` itself, on the very same call that `cd`'d.

What caught it: the `compare` step reported `clean` when the working tree in `/1078` was
actually dirty (three files edited in response to review findings) -- a `clean` verdict landing on
a state that could not possibly be clean is the tell. Confirmed no harm done by cross-checking
`git status --porcelain` directly in both worktrees (`/1078` showed only my own edits; `/1042`
showed nothing) rather than trusting the compare verdict.

Takeaway for the next lane: after a `snapshot` call, read the `root` field back out of the JSON
before trusting anything `compare` says later -- if it does not match the worktree you meant, pass
`--root <path>` explicitly to both `snapshot` and `compare` rather than relying on `cd` inside the
same call.
