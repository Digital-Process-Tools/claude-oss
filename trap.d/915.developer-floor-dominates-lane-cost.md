# A lane's cost is `agents/developer.md` re-sent, not the work it does

Measured 2026-09-03 from the subagent transcript JSONLs of one live tick — the sub-manager plus the
three developer lanes it had dispatched, all still running at the time of the reading. Per assistant
turn, `cache_creation_input_tokens + cache_read_input_tokens`; "floor" is that sum on the agent's
very first turn, before it had made a single tool call.

| agent | turns | floor | cache write | cache read | output | peak ctx |
| --- | --- | --- | --- | --- | --- | --- |
| sub-manager | 99 | 31,644 | 393,297 | 9,864,038 | 13,070 | 154,300 |
| lane #845 | 23 | 57,862 | 148,061 | 1,485,293 | 1,288 | 82,207 |
| lane #699 | 23 | 57,829 | 82,702 | 1,582,578 | 124 | 79,532 |
| lane #897 | 14 | 58,316 | 65,354 | 850,112 | 114 | 71,231 |

At Sonnet rates ($3.75/M cache write, $0.30/M cache read, $15/M output): $4.63, $1.02, $0.79 and
$0.50 respectively — about $6.94 for one tick, not yet finished.

**A developer lane's floor is 57.8-58.3k tokens, nearly double the sub-manager's 31,644.** The
difference is `agents/developer.md`, measured at 89,144 B on disk this session -- roughly 22k
tokens, the largest file in either budget table -- held in context for every turn the lane runs.

Floor as a share of each agent's total `cache_read`, floor multiplied by turn count:

| agent | floor x turns | share of cache_read |
| --- | --- | --- |
| lane #897 | 816,424 | 96% |
| lane #845 | 1,330,826 | 90% |
| lane #699 | 1,330,067 | 84% |
| sub-manager | 3,132,756 | 32% |

The lanes are almost entirely floor re-send. Lane #897 had emitted 114 output tokens across 14 turns
and cost $0.50, of which about 96% was re-sending a definition it already held. The sub-manager's
share is far lower only because it accumulates real board data — issue bodies, PR diffs, radar
output — which is work, not floor.

## Why the byte budget does not show this

`scripts/agent_budgets.py` measures `len(path.read_bytes())` once per file, and the budget is a
ceiling, not a cost. `developer.md` sits at 89,144 B against a 91,300 B budget. But the cost a lane
actually pays is **bytes x turns x lanes**, and CLAUDE.md's own #491 note already records the
multiplier: median 55 turns, observed max 329. At 329 turns that single file is about 7.3M tokens of
`cache_read` and $2.20 for one lane. Three lanes in a tick multiply it again.

(The table's stale baseline for this file is a separate finding -- see
[[915.budget-table-baseline-column-unchecked]].)

So the budget table's rows are not comparable to each other as costs, even though they are printed
in one table as though they were. `sub-manager.md` at 14,032 B is read for the length of a tick;
`developer.md` at 83,014 B is read for the length of a lane, and there are one to three lanes per
tick. A byte cut in `developer.md` is worth several times a byte cut anywhere else in the table, and
nothing in the table or in the tests says so.

Not proposed here, because this fragment is not the place to decide it: whether the fix is a
turn-weighted column in the budget table, a split of `developer.md` into a spine plus phase files
the way `skills/manager/SKILL.md` already went (#491's successor), or nothing at all on the grounds
that the content is load-bearing. The counter-argument CLAUDE.md already states stands: this
repository's history is expensive lessons written down, and a trim that removes a live trap costs a
review round that will not show up next to the tokens it saved.

## Route

These numbers were only obtainable by reading the subagents' JSONL transcripts from outside the
running tick. Nothing inside the loop can take this measurement: `accounting.md`'s `tick_cost`
records `unknown` for `start_ctx`, `calls` and `context_carried`, and it has no per-lane dimension
at all — a tick that dispatched three lanes records the same shape as one that dispatched none. See
[[915.tick-md-unbudgeted-and-read-twice]] for the same gap measured on the sub-manager's own floor.

## An unexplained 6k, larger than most of the savings anyone would chase

Breaking the two floors down against the files on disk, at a 4:1 byte-to-token estimate -- only the
floor totals and the byte counts are measured, the split between them is derived:

| source | sub-manager | developer lane |
| --- | --- | --- |
| `CLAUDE.md` (33,072 B) | ~8,270 | ~8,270 |
| own definition | ~3,850 (15,393 B) | ~22,290 (89,144 B) |
| spawn prompt / lane brief | ~66 (266 B) | ~1,950-2,240 (7,783-8,961 B) |
| system prompt + tool schemas (residual) | **~19,450** | **~25,360** |
| measured floor | 31,644 | 57,862 |

The residual is the largest single line in the developer column and it differs by about 6,000 tokens
between two agents with nearly the same tool grant -- `Bash`, `TodoWrite`, `Skill`, `Agent` for both,
per their frontmatter. Nothing in the transcripts accounts for the difference. It may be an artefact
of the 4:1 estimate rather than a real gap, which is itself the point: the estimate cannot tell those
apart, and 6,000 tokens per turn is larger than most byte cuts anyone would propose to the files
above.

Worth resolving before optimising anything smaller. A component-level reading -- rather than a
subtraction against estimated byte-to-token ratios -- is what would settle it, and this fragment does
not have one.

## The break-even, and why turn count is the variable nobody records

Cost is floor x turns, so a bundle only wins if the bundled lane runs fewer turns than the separate
lanes summed. Against this tick's own measurements -- 58k floor, 23 turns per single-issue lane:

| shape | turn-floors | cache_read | vs today |
| --- | --- | --- | --- |
| 3 lanes x 1 issue, 23 turns each | 69 | ~4.0M | baseline |
| 1 lane x 3 issues, 50 turns | 50 | ~2.9M | 27% saving |
| 1 lane x 3 issues, 69 turns | 69 | ~4.0M | break-even |
| 1 lane x 3 issues, 70+ turns | 70+ | ~4.1M | worse |

Break-even sits at about 69 turns for a three-issue lane. #499's independently measured cliff at
four issues -- 141 median turns, 68% worse per issue -- is roughly double that, which is weak
corroboration that the two readings describe the same curve rather than contradicting each other.

The consequence: **turn count decides whether bundling saves anything, and nothing in the loop
records it.** `tick_cost` has no per-lane dimension and writes `unknown` for `calls`. The figures
above came from subagent JSONL read from outside the tick. A bundling change shipped without that
instrumentation cannot be evaluated after the fact, only argued about.

Note what is proven and what is extrapolated. #499's 16%-per-issue saving was measured on *adjacent*
bundles. A non-adjacent trio accumulates three unrelated file sets into working context, so its later
turns are more expensive and its turn count probably higher -- which is exactly the axis the table
above is sensitive to. Adjacent bundling is the proven case; non-adjacent bundling is an
extrapolation whose sign is not established.
